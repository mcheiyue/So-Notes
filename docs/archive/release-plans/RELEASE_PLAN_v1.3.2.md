## 1. 与校准版路线图的对齐结论

`D:\Github\A-Docs\SoNotes 版本更新规划 v1.2.8-v1.4.0.md` 已把 `v1.3.2` 明确定位为：

> **状态结构规范化与 selector 收敛**：建立 O(1) 查询和细粒度订阅底座，避免在旧 `notes: Note[]` 上继续叠高频功能。

结合当前仓库基线，这个定位是成立的，而且优先级明确高于批量操作与搜索扩展。原因不是抽象上的“结构更优雅”，而是当前真实代码已经暴露出三个直接问题：

1. **按 id 读单便签仍依赖数组查找**，会把单卡片更新和整份集合绑定在一起。
2. **看板过滤与视口裁剪仍以整份 `notes` 为输入**，数据规模上去后会持续放大渲染与筛选成本。
3. **运行时、导入导出、冷启动迁移都围绕数组结构运作**，如果不先收敛底座，后续批量操作、搜索索引、模板系统都会继续叠在旧模型上。

进一步说，旧结构的问题不只是“查找慢”，而是它天然放大 **不可变更新带来的引用扩散**：只要修改一张便签，更新路径就很容易退化为对整份数组执行 `.map()`、`.filter()` 或重建派生数组，从而制造新的集合引用。这样一来，凡是订阅 `state.notes` 或依赖整份数组派生结果的组件，都会被一起拖入 React 调和流程。`v1.3.2` 的任务，本质上是在运行时状态层切断这种“单点改动 -> 整体引用抖动 -> 级联重渲染”的传播链。

因此，v1.3.2 的任务不是“顺手做一点结构优化”，而是把状态结构收敛为后续版本的明确前置条件。

## 2. v1.3.2 核心目标（收敛后）

1. **冷启动迁移进入边界层**
   - 旧版 `notes: Note[]` 只能出现在读取、导入、恢复等输入边界。
   - 一旦进入 Store，立即转为规范化结构。

2. **运行时只保留单一真相来源**
   - 禁止在运行时长期并行维护 `notes: Note[]` 与 `notesById` 双真相。
   - 所有便签更新、移动、删除、恢复都应转为以 `id` 为核心。

3. **selector 粒度收敛**
   - 单便签订阅只追踪自身数据。
   - 看板列表、画布可见集、小地图、搜索结果等订阅路径只消费必要切片。
   - 当前看板的主数据切片默认由 `boardNoteIds` 提供，避免把全量筛选留在 selector 层。

4. **兼容边界明确化**
   - 导入、导出、备份、恢复必须仍可兼容旧数据。
   - 若主存储格式同步升级，必须有明确版本识别与迁移路径；若暂不升级，必须在持久化边界完成结构转换。

5. **为 v1.3.3 / v1.3.4 打底**
   - v1.3.3 的批量操作不能继续压在旧数组模型上。
   - v1.3.4 的搜索与索引也不能建立在全量线性扫描的运行时心智上。

### 非目标（明确不纳入 v1.3.2）

- 不做批量操作 MVP（归 `v1.3.3`）。
- 不做搜索索引下沉 Rust / Worker（归 `v1.3.4`）。
- 不做模板系统、云同步、AI、原生窗口特效回归。
- 不为了兼容而在运行时引入“数组与 Map 按阈值切换”的双结构方案。

## 3. 当前结构问题与改造动机

| 维度 | 当前实现 | 直接问题 | v1.3.2 应对方向 |
|---|---|---|---|
| **运行时主结构** | `State.notes: Note[]` | 单便签读取、批量更新、看板筛选都容易退化成数组扫描 | 引入 `notesById + allNoteIds + boardNoteIds` 规范化结构 |
| **冷启动加载** | `init()` 读取后直接操作数组 | 迁移逻辑和运行时结构耦合，难以清晰分层 | 把旧数组识别与迁移收口到输入边界 |
| **单卡片订阅** | `NoteCard` 使用 `state.notes.find(...)` | 单卡片渲染和整份 notes 订阅绑定，放大无关更新 | 改为按 id 精确订阅 |
| **画布可见集** | `Canvas` 从整份 `notes` 过滤可见便签 | 视口裁剪依赖整份集合，后续批量能力会进一步放大成本 | 先通过 `boardNoteIds` 取得看板切片，再做可见 id 计算 |
| **数据边界** | `dataTransfer` 仍以 `Note[]` 组织导入导出 | 若直接改主结构，兼容和落盘策略会变复杂 | 先定义兼容层合同，再决定持久化格式是否一起升级 |

这也是为什么 v1.3.2 必须放在 v1.3.1 之后、v1.3.3 之前：性能基线已经告诉我们问题值得收敛，而高频功能扩展还没有把结构债务进一步放大。

## 4. 实施路线（建议拆为 5 个工作流）

### 工作流 A：定义规范化状态契约与迁移边界

**目标**：先明确“新结构是什么”，再开始改 Store 和组件订阅。

**建议改动点**：
- `src/store/types.ts`
- `src/store/useStore.ts`
- 必要时新增结构转换辅助模块（名称待实现时确定）

**落地要点**：
1. 定义运行时规范化结构，例如：
   - `notesById`
   - `allNoteIds`
   - `boardNoteIds`
2. 旧 `StorageData.notes: Note[]` 的识别与迁移只出现在输入边界。
3. 明确“运行时主结构”和“导入导出兼容结构”不是同一层职责。
4. 给结构版本升级预留标识，避免未来再次进行无界数组补丁。

### 工作流 B：Store 动作全面改为以 id 为核心

**目标**：让新增、编辑、移动、删除、恢复等行为不再依赖全量数组扫描作为默认路径。

**建议改动点**：
- `src/store/useStore.ts`

**落地要点**：
1. 所有便签动作以 `id -> note` 为基本访问模型。
2. 需要维持排序、层级、看板归属时，明确相应索引的唯一职责。
3. 禁止在核心更新路径中继续把结构退回整份数组再重建。
4. 保存前的序列化与兼容转换应收口在边界，而不是散落在动作内部。

### 工作流 C：组件 selector 收敛与渲染扩散控制

**目标**：让单便签更新尽量只影响单便签，而不是顺带刷新整片 UI。

**建议改动点**：
- `src/components/NoteCard.tsx`
- `src/components/Canvas.tsx`
- `src/components/MiniMap.tsx`
- `src/components/Spotlight.tsx`
- 其他直接消费 `notes` 集合的组件

**落地要点**：
1. `NoteCard` 改为按 id 精确订阅自身数据，不再在 selector 内做 `find()`。
2. `Canvas` 等父组件优先只获取 **id 列表**，不要在 selector 中通过 `.map(id => state.notesById[id])` 动态组装对象数组。
3. 当前看板数据默认通过 `boardNoteIds[currentBoardId]` 获取，禁止把整份 `allNoteIds` 过滤留在渲染热路径。
4. 与选择、多选、拖拽相关的 selector 保持最小依赖面。
5. 必要时配合浅比较，避免引用变化导致无意义刷新。

### 工作流 D：导入、导出、备份、恢复的兼容层收口

**目标**：结构改造不破坏现有数据安全路径。

**建议改动点**：
- `src/utils/dataTransfer.ts`
- `src/store/useStore.ts`
- Rust 侧持久化读取/写入入口（若主存储格式一起升级）

**落地要点**：
1. 明确 v1.3.2 的存储策略：
   - **推荐主方案**：运行时先完成规范化；导入导出边界继续兼容数组结构。
   - **可选增强**：若评估风险可控，再把主存储也升级到规范化格式，并补版本识别。
2. 无论采用哪种策略，旧数据都必须可冷启动迁移。
3. 导入/恢复后进入 Store 前先完成结构归一化，不能把旧数组长期塞回运行时。
4. 备份与恢复链路继续沿用 `v1.3.0` 的安全语义，不因结构改造弱化保护。

### 工作流 E：回归测试与性能门禁

**目标**：证明结构改造真的减少了订阅扩散，而不是只把复杂度藏起来。

**建议改动点**：
- `src/store/useStore.test.ts`
- `src/components/NoteCard.test.tsx`
- `src/components/Canvas.test.tsx`
- `src/utils/dataTransfer.test.ts`
- 必要时补充针对迁移与 selector 的测试

**至少覆盖场景**：
1. 旧数组格式可在冷启动时成功迁移。
2. 导入、导出、备份、恢复路径在新结构下仍兼容。
3. 单便签编辑不会导致所有便签卡片重渲染。
4. 看板切换、废纸篓切换、拖拽终态提交在新结构下保持正确。
5. `v1.3.1` 的性能样本和诊断能力可继续用于比较结构改造前后差异。

## 5. 关键决策点（必须在实现前说清）

### 决策点 A：主存储格式是否随 v1.3.2 一起升级

这是本版本唯一真正会影响范围大小的选择。

**方案 1：仅运行时规范化，磁盘主存储继续沿用数组结构**
- 优点：兼容风险更低，导入导出与恢复链路更容易平滑过渡。
- 风险：每次加载/保存都需要边界转换，长期会保留一层适配成本。

**方案 2：运行时与主存储一起升级为规范化结构**
- 优点：结构心智统一，后续版本维护成本更低。
- 风险：会同时影响读取、写盘、导入导出兼容、备份恢复验证，范围更大。

**当前建议**：
先按 **方案 1** 规划并落地运行时收敛，把“运行时双结构”问题先解决；是否同步升级主存储格式，作为实现阶段的二级决策项。这样更符合 v1.3.2“先稳住底座”的版本目标。

### 决策点 B：`boardNoteIds` 不再作为可选项

如果运行时只有 `notesById + allNoteIds`，那么 `Canvas`、`MiniMap`、搜索结果分组等场景仍然很容易退化为：

`allNoteIds.filter(id => notesById[id].boardId === currentBoardId)`

这等于把 `O(N)` 全量扫描从更新路径平移到了 selector 路径，并没有真正切断渲染热路径上的线性筛选成本。对 `v1.3.2` 这种“状态结构规范化与 selector 收敛”版本来说，这个妥协不可接受。

**当前建议**：
- `notesById + allNoteIds + boardNoteIds` 应作为运行时最低基线。
- `boardNoteIds` 的职责是把“当前看板切片”从全量扫描中抽离出来，而不是等性能再次恶化后再补。
- 索引设计仍需克制，但看板维度索引已经属于本版本底座，而不是未来优化项。

## 6. 验收标准（v1.3.2 完成定义）

满足以下全部条件才可视为 v1.3.2 达标：

1. Store 运行时不存在长期并行的 `notes: Note[]` 与 `notesById` 双真相。
2. 当前看板的便签切片可直接通过 `boardNoteIds` 获取，而不是在渲染热路径上从全量 id 或全量对象再次过滤。
3. 旧数据可冷启动迁移，导入/导出/备份/恢复路径通过兼容验证。
4. 单便签编辑、改色、折叠、拖拽终态提交不会导致所有卡片一起重渲染。
5. 父组件不通过 selector 动态组装整批 note 对象数组，子组件按 id 精确订阅自身状态。
6. 画布可见集计算、看板切换与选择状态在新结构下行为正确。
7. `v1.3.1` 已引入的性能基线与诊断能力可继续复用，且能观察到结构收敛带来的正向变化。
8. 本版本没有顺手混入批量操作、搜索重构、模板系统等超范围功能。
