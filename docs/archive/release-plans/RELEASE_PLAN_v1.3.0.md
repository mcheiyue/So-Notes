## 0. 当前基线

- 当前已发布：`v1.2.9`（`e0febc7`, tag `v1.2.9`）。
- 当前 Rust 写入主命令为 `save_content`（`src-tauri/src/lib.rs`），具备 `tmp + rename + retry + direct write`，但无 OS 级文件锁。
- 当前前端写盘主链为 `saveToDisk`（`src/store/useStore.ts`），存在多入口并发触发风险。
- 当前目标：进入 **v1.3.0（数据安全与并发写保护）** 的实施准备，而非立即发版。

## 1. 对 `问题.md` + `补充.md` 的审视结论（是否接受）

| 问题点 | 结论 | 处理方式 |
|---|---|---|
| A：前端串行队列是“纸老虎” | **接受** | 单写入口下沉到 Rust；前端仅做意图派发，不做最终 I/O 调度。 |
| B：仅“同进程互斥”不够 | **接受** | 将 **OS 级排他锁** 提升为 v1.3.0 必做项，不再“预留到以后”。 |
| C：恢复前保护备份存在新竞态 | **部分接受** | 接受“流程必须事务化”结论；v1.3.0 落地最小事务阶段语义（prepare/commit/rollback），保证中断可恢复。 |
| D：UI 状态机与 ACK 时序错位 | **接受** | 引入单调递增 `generationId`，UI 仅消费最新代际 ACK，拒绝旧回执覆盖新状态。 |
| E：MPSC 队列可能引发背压灾难 | **接受** | 不采用双通道并发监听；改为“**单意图队列 + 消费者端批处理折叠**”，在保持顺序前提下消除写债堆积。 |
| F：纯 JSON 事务化过重，建议直接 SQLite | **部分接受** | 认可长期方向；但 v1.3.0 不做全量存储迁移，新增“存储引擎演进闸门”并输出迁移决策结论，避免本版本失焦。 |
| G：锁失败直接抛错会造成误报闪烁 | **接受** | Rust 侧锁竞争引入指数退避重试，仅在重试耗尽后再上抛失败，并绑定最新 `generationId`。 |
| H：双通道调度可能导致恢复后又被旧脏数据覆盖 | **接受** | 明确禁止 `watch + mpsc` 双通道并行调度同一 I/O 资源，采用单通道全序消费。 |
| I：Windows 下锁目标文件与 rename 可能冲突 | **接受** | 采用“**锁文件与数据文件分离**”策略：锁 `data.json.lock`，不锁 `data.json` 本体。 |

## 2. v1.3.0 核心目标（修订后）

1. **Rust 单写入口**：保存/导入/恢复/备份最终都进入 Rust 写入调度器。
2. **全序背压模型**：所有写意图进入单队列，消费者端折叠连续保存消息，保证顺序不倒流。
3. **锁文件机制 + 指数退避**：使用独立锁文件实现跨进程排他，锁竞争可重试、可诊断、可控失败。
4. **最小事务语义**：导入/恢复具备 prepare/commit/rollback 阶段标记与恢复能力。
5. **代际一致性回执**：前端状态仅跟随最新 `generationId` ACK。
6. **结构化错误与重试路径**：从文本报错升级为可区分错误类型。
7. **存储演进决策闸门**：给出 v1.3.x 是否迁移 SQLite/libsql 的可执行结论。

### 非目标（明确不纳入 v1.3.0）

- v1.3.0 内不做全量数据迁移到 SQLite/libsql。
- 性能基线/诊断面板（归 v1.3.1）。
- 状态结构规范化（归 v1.3.2）。
- 批量操作扩展（归 v1.3.3）。
- 搜索索引、模板系统、云同步等更大特性。

## 3. 实施路线（修订为 6 个工作流）

### 工作流 A：单意图队列与消费者端折叠（单通道）

**目标**：解决覆盖写背压，不让中间态堆积成写债。

**建议改动点**：
- `src-tauri/src/lib.rs`
- 新增 `src-tauri/src/persistence.rs`（建议）
- `src/store/useStore.ts`

**落地要点**：
1. 所有写意图（save/import/restore/backup）进入**唯一**意图队列。
2. 消费端每次唤醒先 `try_recv` 抽干积压，并将连续 `Save` 折叠为最后一次。
3. `Import/Restore` 不可跨越重排，必须保持与前后 Save 的原始顺序关系。
4. 禁止对同一 I/O 资源使用 `watch + mpsc` 双通道并行 `select!`。
5. ACK 统一包含 `generationId` 与结果类型。

### 工作流 B：OS 级排他锁与指数退避重试

**目标**：防止 Defender/同步盘/多实例导致的锁冲突直接击穿体验。

**建议改动点**：
- `src-tauri/src/persistence.rs`（建议）
- `src-tauri/Cargo.toml`（文件锁依赖）

**落地要点**：
1. 不锁 `data.json` 本体，改为锁 `data.json.lock`（锁源与数据源分离）。
2. 锁冲突时采用指数退避（含上限与随机抖动）。
3. 在持有锁文件期间执行：写 `data.tmp` -> `fsync(data.tmp)` -> rename 覆盖 `data.json`。
4. 仅在退避耗尽后返回 `LOCK_BUSY` 等结构化错误。
5. 返回失败时携带代际信息，防止前端错配状态。

### 工作流 C：导入/恢复最小事务阶段语义

**目标**：避免“保护备份本身失败”造成流程半残。

**建议改动点**：
- `src-tauri/src/persistence.rs`（建议）
- `src/store/useStore.ts`
- `src/components/BoardDock.tsx`

**落地要点**：
1. 导入前预览影响范围（新增/覆盖/跳过）。
2. 写入前记录阶段标记（prepare）。
3. 保护备份与正式写入在阶段语义下完成，并写入 commit。
4. 崩溃/中断后可依据标记执行恢复或回滚。

### 工作流 D：前端代际状态回显收口

**目标**：消除“显示已保存但实际未落盘”的错位。

**建议改动点**：
- `src/store/useStore.ts`
- `src/components/BoardDock.tsx`

**落地要点**：
1. 每次写意图附带单调递增 `generationId`。
2. UI 只接受“最新 generation”的 ACK。
3. 旧 ACK 仅记录日志，不更新可见状态。
4. 状态文案统一：`保存中 / 已保存 / 保存失败 / 等待重试`。

### 工作流 E：并发与故障回归门禁

**目标**：用自动化测试证明模型真实生效。

**建议改动点**：
- `src/store/useStore.test.ts`
- `src/components/BoardDock.test.tsx`
- `src/utils/dataTransfer.test.ts`
- Rust 侧测试（调度、锁竞争、事务恢复）

**至少覆盖场景**：
1. 高频保存下内存与待处理数量不无界增长。
2. 导入与保存交错时不发生错序覆盖。
3. 锁冲突时退避重试后再决定失败。
4. 崩溃/中断后事务阶段可恢复。
5. 旧 `generationId` ACK 不得覆盖最新 UI 状态。

### 工作流 F：存储引擎演进闸门（决策输出）

**目标**：在不拖垮 v1.3.0 主线的前提下，完成 SQLite/libsql 迁移决策。

**建议产出**：
1. 列出 JSON 持续演进与 SQLite/libsql 迁移的成本/收益/风险对照。
2. 给出触发条件（如：并发场景复杂度、恢复逻辑维护成本、缺陷率阈值）。
3. 明确结论：继续 JSON（并说明边界）或在 v1.3.1+ 启动迁移。

## 4. 验收标准（v1.3.0 完成定义）

满足以下全部条件才可视为 v1.3.0 达标：

1. 写盘最终入口在 Rust 调度器，前端不承担最终 I/O 调度。
2. 写入调度为单通道全序消费，不存在双通道引发的时序倒流。
3. 覆盖写无无界堆积风险，消费者端折叠能消除写债。
4. `data.json` 写入采用锁文件机制，并满足“锁文件持有期间 fsync(tmp) + rename”时序。
5. 导入/恢复具备预览确认与最小事务阶段恢复能力。
6. 保存状态回显与 `generationId` ACK 严格一致。
7. 并发与故障回归测试通过，不存在未知覆盖与错序成功提示。

## 5. 执行顺序建议（5-7 天）

1. **第 1 天**：工作流 A（单通道队列 + 消费者折叠骨架）。
2. **第 2 天**：工作流 B（锁文件机制 + 退避重试 + 错误结构化）。
3. **第 3 天**：工作流 C（导入预览 + 阶段语义 + 恢复路径）。
4. **第 4 天**：工作流 D（代际 ACK 对齐）+ 工作流 E（回归测试）。
5. **第 5 天**：工作流 F（存储演进闸门结论）+ 稳定性修补。
6. **机动 1-2 天**：极端故障场景补测与发布前收口。

## 6. 发布门禁（对齐 `RELEASE_GUIDE.md`）

当 v1.3.0 开发完成后，发布仍严格走以下流程：

1. 本地构建验证：`npm run build`、`npm run tauri build -- --debug`。
2. 三处版本号统一：`package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`。
3. 更新 `CHANGELOG.md`（作为 Release Notes 单一事实来源）。
4. README 同步检查。
5. 提交发布准备 commit。
6. 打 tag 并推送，观察 release workflow 成功。
