# SoNotes v1.4.4 实施计划：Undo/Redo 批量操作与旧机制迁移

---

## 1. 背景

`v1.4.3` 已经建立了通用 Undo/Redo 历史基础设施，包括 Command / patch 历史模型、容量裁剪、编辑会话提交点和快捷键边界。该版本只接入了低风险、单便签、意图边界清楚的 **Domain state** 操作：新建便签、编辑标题 / 正文、移动、改色、折叠 / 展开。

当前项目中仍存在两块未被通用历史覆盖的能力：

1. **批量操作**：选中多张便签后批量移动、批量改色、批量软删除，目前不支持撤销。
2. **组织类操作**：归拢（arrange）、拆分（split）、合并（merge），目前仍依赖局部 `undoLastArrange` toast 回退机制，不走通用历史。

此外，`v1.4.3` 的 `DomainPatch` 只描述单便签的字段和位置差异，不支持复合补丁（例如同时涉及多张便签的批量操作），也不携带 `deletedAt` 信息，无法表达软删除与废纸篓还原的可逆变更。

`v1.4.4` 的目标是补齐这些缺口：扩展 patch 形态以支持复合操作和软删除语义，将批量操作和组织类操作全部接入通用 Undo/Redo，并最终移除旧的 `undoLastArrange` toast 机制。

本版本仍然明确排除 **TRASH（废纸篓）** 视图下的 Undo/Redo 和永久删除的可逆性。

---

## 2. 目标

### 2.1 扩展 DomainPatch 形态

当前 `DomainPatch` 只描述单张便签的字段与位置差异。`v1.4.4` 需要扩展以下能力：

- **复合 patch**：一次历史记录可以同时描述多张便签的变更（批量操作、归拢、拆分、合并）。
- **deletedAt 支持**：patch 能表达便签的 `deletedAt` 字段变化，从而覆盖软删除与废纸篓还原的可逆语义。
- **向后兼容**：已有 `v1.4.3` 的单便签 patch 继续正常工作，不需要迁移旧历史记录。

### 2.2 接入软删除与废纸篓还原

- 软删除便签后，Undo 可恢复便签到原所属 **Board**，Redo 可重新将便签移入 **Trash（废纸篓）**。
- 从 **Trash（废纸篓）** 还原便签后，Undo 可将便签重新放回 **Trash**，Redo 可恢复还原操作。
- 软删除和还原都作为 **Domain state** 变更记录进历史。
- 便签在软删除 / 还原过程中的位置和字段信息应被正确保存与恢复。

### 2.3 接入批量操作

以下批量操作应支持 Undo/Redo：

- 批量移动多张便签。
- 批量改色多张便签。
- 批量软删除多张便签。

批量操作作为一个用户意图整体入栈，不拆分为逐张便签操作。撤销时，所有受影响的便签一起恢复。

### 2.4 迁移归拢、拆分、合并到通用 Undo/Redo

- 归拢（arrange）操作接入通用历史，Undo 可将便签恢复到归拢前的位置。
- 拆分（split）操作接入通用历史，Undo 可将拆分产生的多张便签还原为拆分前的原始便签。
- 合并（merge）操作接入通用历史，Undo 可将合并后的单张便签还原为合并前的多张便签。
- 迁移完成后，旧的 `undoLastArrange` toast 回退机制将被移除或降级。

### 2.5 移除 / 降级旧 arrangeUndoToast 机制

- 归拢、拆分、合并的撤销入口统一收敛到通用 Undo/Redo 快捷键和按钮。
- 旧的 toast "撤销"按钮不再作为这些操作的回退入口。
- 如果保留 toast，它只能作为操作成功的视觉反馈，不提供回退能力。

### 2.6 调整便签尺寸（最后一个提交）

- 支持通过便签右下角拖拽手柄调整单张便签的宽度和高度。
- 调整尺寸作为一个可撤销的 **Domain state** 操作接入历史。
- 拖拽调整时，从开始到结束合并为一个操作，不记录中间帧。
- **TRASH（废纸篓）** 视图、折叠态便签不显示尺寸调整手柄。
- 该功能必须在所有其他提交完成后实现，作为 `v1.4.4` 的最后一个提交。

### 2.7 快捷键与体验保护

- `v1.4.3` 的快捷键边界完全延续：`Ctrl+Z` / `Cmd+Z` 撤销，`Ctrl+Y` / `Cmd+Y` 或 `Ctrl+Shift+Z` / `Cmd+Shift+Z` 重做。
- 输入框聚焦时仍然不劫持原生文本编辑撤销。
- **TRASH（废纸篓）** 视图下仍然不响应全局 Undo/Redo 快捷键。
- **Spotlight** 或快速捕获层打开时仍然不触发画布 Undo/Redo。

---

## 3. 非目标

本次不做以下能力：

- **TRASH（废纸篓）** 视图下的 Undo/Redo。废纸篓视图继续只读管理，不响应撤销 / 重做。
- **永久删除** 的撤销 / 重做。永久删除继续依赖明确确认，不提供撤销承诺。
- 画布平移、画布缩放、看板视口位置撤销。
- 搜索输入、菜单开关、选区、框选过程、hover、高亮、toast 显隐撤销。
- Board 创建、重命名、排序、删除的撤销 / 重做。
- 跨看板移动便签接入通用历史。
- 历史记录持久化到磁盘。
- 可配置历史容量。

## 4. 业务边界决策

### 4.1 TRASH 视图快捷键继续禁用

`v1.4.3` 确认的废纸篓安全边界在 `v1.4.4` 完全延续：

- `TRASH` 视图下不响应全局 Undo/Redo 快捷键。
- `TRASH` 视图下按 Undo/Redo 默认静默无动作，不弹 toast。
- 永久删除继续依赖明确确认，不提供撤销承诺。

软删除和废纸篓还原可以分别由 **Board（看板）** 视图与 **Trash（废纸篓）** 视图中的显式操作产生历史记录；但全局 Undo/Redo 快捷键只在 **Board** 视图下生效，**Trash** 视图下继续静默无动作。

### 4.2 软删除的撤销语义

软删除便签时，Undo 表示"把这张便签从 **Trash（废纸篓）** 恢复到所属 **Board**"。这不是新建便签，而是恢复一张已存在的便签。

推荐边界：

- Undo 恢复便签时，必须恢复到它被软删除前的所属 Board、位置和所有字段。
- Redo 重新执行软删除时，将便签移回 **Trash**，位置和字段信息保持不变。
- **Trash** 视图仍是只读浏览与管理入口，不提供便签内容编辑；软删除的 Undo/Redo 不需要处理 Trash 内编辑冲突。
- 如果原所属 Board 已不存在，恢复操作不连带恢复已删除 Board；应降级恢复到当前 Board。
- 如果当前 Board 也不可用，应降级到第一个可用 Board。
- 如果没有任何可用 Board，恢复操作失败并保持当前状态不变，不推进历史栈。

### 4.3 废纸篓还原的撤销语义

从 **Trash（废纸篓）** 还原便签时，Undo 表示"把这张便签重新放回 **Trash**"。

推荐边界：

- 还原操作将便签从 **Trash** 移回所属 Board，恢复到还原前的位置和字段。
- Undo 将便签重新放回 **Trash**。
- 还原后的便签应出现在画布中它原来的位置，如果原来的位置已被其他便签占据，应选择最近的可用位置或保持原位。
- 还原目标 Board 的 fallback 规则与软删除 Undo 相同：优先原所属 Board，其次当前 Board，再其次第一个可用 Board；全部不可用时失败且不推进历史栈。

### 4.4 批量操作的原子入栈

批量操作作为一个用户意图整体入栈，不拆分为逐张便签操作。

推荐边界：

- 批量移动：记录所有参与便签的起始位置和结束位置，作为一个 Command 入栈。
- 批量改色：记录所有参与便签的旧颜色和新颜色，作为一个 Command 入栈。
- 批量软删除：记录所有参与便签的当前 Board 归属和字段，作为软删除操作入栈。Undo 恢复所有被软删除的便签。
- 如果批量操作中存在不可应用的便签状态（例如便签不存在），应在生成历史前过滤并确认实际生效集合；patch 应用阶段不得出现部分应用后留下不一致状态。

### 4.5 归拢的撤销语义

归拢操作将多张便签按规则重新排列位置。

推荐边界：

- 归拢前记录所有参与便签的原始位置。
- 归拢后记录所有便签的新位置。
- Undo 将所有便签恢复到归拢前的位置。
- 归拢操作接入通用历史后，旧的 `undoLastArrange` toast "撤销"按钮不再作为归拢的回退入口。

### 4.6 拆分的撤销语义

拆分操作将一张便签按规则拆分为多张便签。

推荐边界：

- 拆分前记录原始便签的完整信息（id、标题、正文、位置、颜色等）。
- 拆分后记录所有新便签的完整信息。
- Undo 移除所有拆分产生的新便签，恢复原始便签的完整状态。
- Redo 重新执行拆分，移除原始便签，创建所有新便签。
- Undo/Redo 必须恢复原始 UUID；不得为了恢复等价内容而生成新便签 ID。
- 如果待恢复的目标 ID 已被其他便签占用，或参与操作的关键便签已不满足预期状态，本次 Undo/Redo 应失败并保持当前状态不变。
- 拆分操作中的标题继承、正文分割规则不在本版本变更，只确保历史能正确记录和恢复。

### 4.7 合并的撤销语义

合并操作将多张便签合并为一张便签。

推荐边界：

- 合并前记录所有参与便签的完整信息。
- 合并后记录合并产生的单张便签的完整信息。
- Undo 移除合并产生的单张便签，恢复所有原始便签的完整状态。
- Redo 重新执行合并。
- Undo/Redo 必须恢复合并前原始便签和合并后便签的原始 UUID；不得生成新 ID 替代。
- 如果目标 ID 已被占用、缺失或状态不满足预期，本次 Undo/Redo 应失败并保持当前状态不变。
- 合并操作中的内容拼接规则不在本版本变更，只确保历史能正确记录和恢复。

### 4.8 调整便签尺寸的命名与语义

本功能在代码层面涉及便签的宽度和高度调整。在实施计划和用户可见的表述中，统一使用 **"调整便签尺寸"** 而不是"缩放便签"。

命名变更原因：

- "缩放"在 **Viewport state（视口状态）** 语境中通常指画布整体缩放（pinch / Ctrl+滚轮），容易与视口操作混淆。
- "调整便签尺寸"明确表示这是修改单张便签的宽度和高度属性，属于 **Domain state（领域状态）** 变更。
- 该操作修改的是便签自身的显示属性（宽度、高度），不是改变用户观察画布的视角。

推荐边界：

- 调整尺寸记录变更前和变更后的宽度、高度。
- 拖拽调整时，从开始到结束合并为一个操作，不记录中间帧。
- 只在 **BOARD（看板）** 视图对单张便签生效；**TRASH（废纸篓）** 视图不显示尺寸调整手柄。
- 折叠态便签不显示尺寸调整手柄，不允许调整尺寸，避免与折叠高度语义冲突。
- 尺寸调整只修改便签的 `width` / `height` 及对应 `layoutNotesById`，不记录画布缩放、平移、选区、hover、手柄激活态或 toast。
- 松手时宽度或高度确实发生变化才入栈；取消拖拽、尺寸无变化、目标便签不存在时不入栈。
- 尺寸调整应使用 pointer 生命周期建模：pointer down 捕获起始尺寸，pointer move 只更新预览尺寸，pointer up 提交最终尺寸，pointer cancel / Escape / 目标便签消失时取消会话并丢弃暂存。
- 尺寸调整期间应使用指针捕获或等价的全局结束监听，避免光标离开窗口后丢失结束事件而污染历史栈。
- 最小宽高必须保证标题栏、正文区域和操作按钮仍可用；折叠高度仍由 `LAYOUT.NOTE_COLLAPSED_HEIGHT` 控制。
- Redo 必须恢复同一张便签的同一组宽高，不生成新便签。
- 该操作作为 `v1.4.4` 的最后一个提交实现。

### 4.9 编辑提交点延续

`v1.4.3` 确认的编辑提交点规则在 `v1.4.4` 完全延续：

- 标题 / 正文以获得焦点到失去焦点作为一次可撤销编辑会话。
- 如果用户编辑后没有失焦，但触发全局按钮、窗口失焦或全局 Undo/Redo，应先尝试提交该编辑会话。
- 只有旧值和新值确实不同才入栈。

### 4.10 Store 写入目标延续

`v1.4.3` 确认的 Store 写入目标在 `v1.4.4` 完全延续：

- 运行态 patch 应用目标仍然选择 `useStore`，不直接写入 `domainStore`。
- 这是过渡期决策，等运行态领域写入迁移完成后，再评估是否把历史应用目标从 `useStore` 切回 `domainStore`。

## 5. 技术设计约束

### 5.1 DomainPatch 复合扩展

当前 `DomainPatch` 是以 `add-note`、`remove-note`、`update-fields`、`update-position` 为核心的联合类型。`v1.4.4` 需要在此基础上扩展 `compound-patch`，用于表达一次用户意图下的有序多 patch 变更：

```ts
type DomainPatch =
  | AddNotePatch
  | RemoveNotePatch
  | UpdateFieldsPatch
  | UpdatePositionPatch
  | CompoundPatch;

type CompoundPatch = {
  type: 'compound-patch';
  patches: DomainPatch[];
};
```

复合 patch 必须按数组顺序应用。用于 Undo 的复合 patch 与用于 Redo 的复合 patch 可以顺序不同，以保证拆分、合并这类先移除再新增的操作能稳定恢复。

复合 patch 的应用必须具备原子性：

- 应先基于当前领域状态在局部变量中计算完整的下一份领域状态。
- 只有所有子 patch 都可应用时，才能用一次 store 写入提交完整结果。
- 任一子 patch 不可应用时，整个复合 patch 失败，返回原状态，不推进历史栈。
- 不允许对子 patch 逐个触发 Zustand `set()`，避免半完成状态泄漏到 React 渲染周期。
- patch 应用阶段不得部分更新 `notesById`、`allNoteIds`、`boardNoteIds` 或 `layoutNotesById` 后提前退出。

### 5.2 deletedAt 支持

`UpdateFieldsPatch.fields` 中可以包含 `deletedAt` 字段，用于表达软删除语义：

- 设置 `deletedAt` 表示软删除。
- 清除 `deletedAt` 表示从 **Trash（废纸篓）** 还原。
- 历史层应用 patch 时，需要同步更新 `notesById`、`allNoteIds`、`boardNoteIds`、`layoutNotesById` 等集合的一致性。

### 5.3 向后兼容

`v1.4.3` 已有的历史记录格式不需要迁移。新旧 patch 格式在应用层通过类型收窄兼容：

- 如果 patch 是旧格式（单便签新增、移除、字段和位置变更），按旧逻辑处理。
- 如果 patch 是 `compound-patch`，在单次原子计算中按 `patches` 数组顺序应用子 patch。

### 5.4 容量与裁剪延续

`v1.4.3` 确认的容量策略在 `v1.4.4` 完全延续：

- 默认历史容量为 100 条。
- 超过容量时丢弃最旧记录。
- 新操作入栈后清空 redo 栈。
- 历史记录不持久化到磁盘，应用重启后清空。

### 5.5 失败处理延续

`v1.4.3` 确认的失败处理在 `v1.4.4` 完全延续：

- 撤销 / 重做执行时，如果目标便签不存在或状态不满足，应失败并保持当前状态不变。
- 返回 `true`（成功）或 `false`（失败），不抛出用户可见异常。
- 不部分应用 patch。

## 7. 验收标准

### 软删除与还原

- 软删除便签后，Undo 可恢复便签到所属 Board 的原始位置和状态。
- 废纸篓还原便签后，Undo 可将便签重新放回 Trash。
- 软删除和还原过程中，Board 和 Trash 集合保持一致。
- **TRASH** 视图下按 Undo/Redo 无动作、无 toast、无 **Domain state** 变化。

### 批量操作

- 批量移动后，Undo 可将所有参与便签恢复到移动前的位置。
- 批量改色后，Undo 可将所有参与便签恢复到改色前的颜色。
- 批量软删除后，Undo 可恢复所有被软删除的便签。
- 批量操作作为整体入栈，不产生逐张便签的中间历史。

### 归拢、拆分、合并

- 归拢后 Undo 可将便签恢复到归拢前的位置。
- 拆分后 Undo 可将拆分产生的多张便签还原为原始便签。
- 合并后 Undo 可将合并后的单张便签还原为合并前的多张便签。
- 迁移后，旧的 `undoLastArrange` toast "撤销"按钮不再作为这些操作的回退入口。
- 归拢、拆分、合并都通过通用 Undo/Redo 快捷键触发撤销 / 重做。

### 调整便签尺寸

- 拖拽调整便签尺寸后，Undo 可恢复到调整前的宽度和高度。
- 拖拽调整过程中不产生中间历史记录。
- TRASH 视图和折叠态便签不显示尺寸调整手柄。
- 尺寸无变化或取消拖拽不产生历史记录。
- 该功能通过通用 Undo/Redo 快捷键触发撤销 / 重做。

### 通用边界

- 输入框聚焦时，`Ctrl+Z` / `Cmd+Z` 只触发文本框原生撤销，不触发全局 Undo。
- Spotlight 打开、快速捕获层打开时，全局 Undo/Redo 不改变看板便签。
- 执行新操作后 redo 栈被清空。
- 历史栈超过 100 条后会裁剪最旧记录，且不破坏当前可撤销 / 可重做边界。
- 现有测试与新增测试通过。

## 8. 风险

- 复合 patch 需要同时维护多张便签的一致性（`notesById`、`allNoteIds`、`boardNoteIds`、`layoutNotesById`），如果部分应用失败可能导致集合不一致。
- 软删除和废纸篓还原涉及 Board 和 Trash 集合的交叉变更，如果集合同步逻辑不准确，可能出现便签"消失"或"重复出现"。
- 拆分和合并的操作结果依赖标题继承、内容分割等规则，这些规则的变更可能影响历史记录的正确性。
- 归拢、拆分、合并的迁移涉及旧代码的移除，如果旧逻辑与其他功能存在隐式耦合，移除可能引发回归。
- 调整便签尺寸如果放在最后实现，但前面的提交已经改变了便签的渲染逻辑，可能需要额外适配。
- 旧历史记录（`v1.4.3` 产生的）和新历史记录（`v1.4.4` 产生的）在混合使用时需要确保兼容。

## 9. 已采纳的关键决策

### 9.1 归拢、拆分、合并迁移

归拢、拆分、合并将从旧的 `undoLastArrange` toast 机制迁移到通用 Undo/Redo 历史。这是用户确认的决策，不在 `v1.4.4` 重新评估。

### 9.2 TRASH 视图快捷键继续禁用

`TRASH` 视图下仍然不响应全局 Undo/Redo。这是 `v1.4.3` 确认的安全边界，`v1.4.4` 完全延续。

### 9.3 永久删除排除

永久删除不提供撤销承诺。这是跨版本一致的安全原则。

### 9.4 调整便签尺寸最后实现

调整便签尺寸作为 `v1.4.4` 的最后一个提交。原因是该功能的实现可能依赖前面提交中对 patch 形态的扩展，且它是独立的低风险操作，不需要前置依赖。

### 9.5 命名：调整便签尺寸

在实施计划和用户可见的表述中，使用"调整便签尺寸"而不是"缩放便签"。原因是"缩放"容易与画布整体缩放（**Viewport state**）混淆，而该操作修改的是单张便签的宽度和高度属性（**Domain state**）。

### 9.6 复合 patch 格式

`v1.4.4` 的 `DomainPatch` 将支持 `compound-patch`，用有序子 patch 表达批量与复杂操作，同时保持与 `v1.4.3` 单便签 patch 格式的向后兼容。

## 10. 一句话总结

`v1.4.4` 把 Undo/Redo 从单便签扩展到批量操作和组织类操作，迁移归拢 / 拆分 / 合并到通用历史，移除旧的 `undoLastArrange` toast 机制，并新增调整便签尺寸作为最后一个提交，同时严格保持废纸篓视图的安全边界。
