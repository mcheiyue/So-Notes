# SoNotes v1.5.1-v1.6.0 规划建议：备份信任链收口与体验再出发

---

## 1. 背景

`v1.4.0` 到 `v1.5.0` 已经形成一条清晰的阶段路线：

- `v1.4.0`：技术债治理，建立 **Domain state（领域状态）**、**Viewport state（视口状态）** 与 **UI state（界面状态）** 的拆分方向。
- `v1.4.1`：菜单与操作入口整合。
- `v1.4.2`：托盘状态提示与快速捕获层修复。
- `v1.4.3`：Undo/Redo 基础架构。
- `v1.4.4`：Undo/Redo 批量操作与旧机制迁移。
- `v1.4.5`：撕下便签主窗口内浮层原型。
- `v1.4.6`：撕下便签 Tauri 独立窗口。
- `v1.4.7`：图片文件存储底层模型。
- `v1.4.8`：独立图片便签与图片文件一致性。
- `v1.4.9`：本地 zip 备份 / 恢复。
- `v1.5.0`：WebDAV 远端备份。

这条路线的特点是：每个小版本只承载一个清晰主题，先打底，再接体验，再补数据可靠性，最后把远端能力限定为“备份仓库”而不是同步系统。

`v1.5.1-v1.6.0` 建议继续沿用这个节奏。不要把 `v1.5.x` 做成一个含糊的“修修补补区间”，而是拆成若干个小而明确的版本：先把备份信任链做硬，再处理凭据、定时、保留、可观测和架构债，最后用 `v1.6.0` 开一个新的体验主题。

---

## 2. 总体原则

### 2.1 备份优先于同步

WebDAV 继续只作为远端备份仓库：

- 不做实时同步。
- 不做自动拉取覆盖本地。
- 不做多端自动合并。
- 不做便签级冲突解决。
- 不把远端文件作为运行时数据源。

用户可见文案继续使用“备份 / 恢复”，不使用“同步”“云同步”“多端同步”。

### 2.2 先可验证，再自动化

定时远端备份不应早于备份验证能力。否则应用只是在更频繁地制造用户无法判断质量的远端 zip。

推荐顺序是：

```text
验证备份包 -> 建立 WebDAV 协议边界与测试夹具 -> 安全保存凭据 -> 架构债收口 -> 定时上传与最小活动记录 -> 保留策略 -> 完整活动日志
```

### 2.3 凭据安全优先于便利

如果系统密钥链尚未实现，则宁可不记住密码，也不把密码或应用令牌写入普通 JSON 配置。

如果实现“记住密码”，必须完成：

- 系统密钥链写入、读取、清除闭环。
- 清除配置时一并删除 secret。
- 密钥链读取失败时提示用户重新输入。
- 错误、日志、Debug 输出和测试快照均脱敏。

### 2.4 架构债要有单独版本

`v1.4.0` 留下的旧 `useStore` 与 `legacyDomainBridge` 过渡路径不建议夹在产品功能版本中处理。它应该拥有独立小版本，用依赖地图和退出条件推进，而不是一次性大拆。

### 2.5 v1.6.0 只选一个体验主线

`v1.6.0` 可以开始新的体验增强，但不建议同时做捕获、搜索、图片、标签和托盘高级交互。延续 `v1.4.x` 的版本节奏，一个版本只解决一个主要问题。

## 4. v1.5.1：WebDAV 与恢复链路加固

### 4.1 定位

`v1.5.1` 已发布，并已在 `CHANGELOG.md` 中记录。本节作为复盘索引，不再作为待实施计划。

它的主题不是扩功能，而是把 WebDAV 与恢复链路从“能用”推进到“可验证、可回滚、可防御”。

### 4.2 已覆盖方向

- zip 恢复按实际读取字节校验大小，不信任伪造 header。
- 恢复后图片缓存失效与预热。
- Undo/Redo 多次 `set()` 合并为原子更新。
- WebDAV 配置 Debug 输出脱敏。
- WebDAV 内网地址与 redirect 防护。
- WebDAV 下载 token 改为安全随机值。
- WebDAV 配置原子化写入。
- 批量操作领域撤销 / 重做历史补齐。

### 4.3 后续文档建议

可补一份 `v1.5.1` 复盘短文档，记录：

- 哪些问题是 `v1.5.0` 上线后暴露的真实风险。
- 哪些边界已经补齐。
- 哪些能力留到 `v1.5.2+`，例如备份验证、系统密钥链、定时备份。

### 4.4 非目标

- 不新增定时备份。
- 不改备份包格式。
- 不新增同步语义。
- 不加入新的体验主线。

### 4.5 验收标准

- `v1.5.0` 已知恢复与 WebDAV 安全问题得到修复。
- 修复路径有对应测试覆盖。
- 用户可见能力不改变 WebDAV 作为远端备份仓库的定位。

## 5. v1.5.2：备份验证与恢复演练

### 5.1 目标

让用户在真正覆盖恢复前，可以确认一个备份包是否可信、完整、可恢复。

该版本不改变 zip 格式，不提供便签级恢复，也不浏览备份包正文内容。它只回答一个问题：

> 这个备份能不能安全恢复？

### 5.2 范围

#### 5.2.1 本地 zip 验证

建议新增 Rust 命令：

```text
validate_local_backup(source_zip_path) -> BackupValidationResult
```

返回内容包括：

- 是否为 SoNotes 备份包。
- `manifest.json` 是否存在且合法。
- `data.json` 是否满足 `StorageData` 契约。
- 图片文件引用是否完整。
- 图片文件 hash 是否匹配（仅在当前备份格式已有可验证 hash 来源时启用；否则本版本只校验引用完整性与文件可读取性）。
- 备份包大小、图片文件数量、图片文件总大小。
- Board 数、Note 数、Image Note 数、Trash 中 Note 数。
- 备份创建时间、应用版本、格式版本。

#### 5.2.2 结构化验证结果

`BackupValidationResult` 不应只返回字符串错误。建议定义稳定结构，供恢复确认、活动日志、测试断言和 UI 文案复用：

```ts
type BackupValidationResult = {
  ok: boolean
  summary?: BackupSummary
  errors: BackupValidationIssue[]
  warnings: BackupValidationIssue[]
}

type BackupValidationIssue = {
  code: string
  severity: 'error' | 'warning'
  message: string
  target?: 'manifest' | 'data' | 'image_file' | 'zip_entry'
  path?: string
  noteId?: string
  imageFileId?: string
}
```

建议第一批稳定错误码：

- `not_sonotes_backup`
- `missing_manifest`
- `invalid_manifest`
- `missing_data`
- `invalid_data`
- `missing_image_file`
- `image_file_unreadable`
- `image_file_hash_mismatch`（仅在当前备份格式已有可验证 hash 来源时启用）
- `zip_size_limit_exceeded`

#### 5.2.3 远端恢复前验证

远端备份流程保持 `v1.5.0` 设计：

1. 下载远端 zip 到 WebDAV 临时目录。
2. 使用 download token resolve 受控本地路径。
3. 先执行验证。
4. 验证成功后展示摘要与二次确认。
5. 用户确认后再调用既有恢复流程。
6. 取消、失败或恢复结束后清理临时文件。

#### 5.2.4 恢复前摘要

摘要建议包含：

- 备份文件名。
- 创建时间。
- 应用版本。
- 格式版本。
- Board 数。
- Note 数。
- Image Note 数。
- 图片文件数。
- 是否包含 Trash 数据。

摘要不展示便签正文内容，避免把该版本扩成“备份内容浏览器”。

### 5.3 非目标

- 不选择单张便签恢复。
- 不合并当前数据与备份数据。
- 不浏览备份包内便签正文。
- 不改变 zip 格式。
- 不新增远端同步语义。

### 5.4 验收标准

- 用户可以在覆盖恢复前看到备份摘要。
- 非 SoNotes zip 会被拒绝，且本地数据不受影响。
- 损坏 manifest、损坏 data.json、缺失图片文件、图片文件不可读取都能给出稳定结构化失败结果。
- 如果当前备份格式已有可验证 hash 来源，hash 不匹配也会返回稳定错误码；否则不把 hash 校验作为本版本硬验收。
- 验证失败不会进入覆盖恢复流程。
- 远端验证取消后会清理临时下载文件。

## 6. v1.5.3：WebDAV 协议边界与传输稳健性

### 6.1 目标

把 WebDAV 从“按一个理想服务端实现”推进到“关键协议差异可被本地测试覆盖，真实服务端验证可以逐步补充”。

该版本重点不是要求开发者拥有多套 WebDAV 服务端，而是建立可重复的本地测试夹具、错误分类和传输边界。真实服务端兼容性可以记录，但不作为硬性完成条件。

### 6.2 范围

#### 6.2.1 本地 WebDAV mock / fixture

新增本地测试夹具，用于模拟常见 WebDAV 响应：

- `PROPFIND` 返回标准 `207 Multi-Status`。
- `PROPFIND` 使用不同 XML namespace。
- `PROPFIND` 中包含目录项和文件项。
- `getcontentlength` 缺失或非法。
- `getlastmodified` 使用不同时间格式。
- 上传返回 `201 Created`、`204 No Content`、`412 Precondition Failed`。
- 下载缺少 `Content-Length`。
- 删除返回 `204 No Content`、`404 Not Found`、`423 Locked`。
- 服务器返回 `401`、`403`、`405`、`409`、`507`。

这些 fixture 应进入自动化测试，而不是依赖人工连接多个真实服务。

第一批最低完成集建议为：

- 标准 `207 Multi-Status`。
- XML namespace 差异。
- `401` / `403` 鉴权或权限失败。
- 上传 `201 Created` / `204 No Content`。
- 删除 `404 Not Found` / `423 Locked`。
- 下载缺少 `Content-Length`。

#### 6.2.2 真实服务端记录模板

新增文档记录真实服务端验证结果，但所有未验证项允许标记为“未验证”：

| 服务端 | 测试连接 | 上传 | 列表 | 下载 | 删除 | 备注 |
|---|---|---|---|---|---|---|
| Nextcloud | 待验证 | 待验证 | 待验证 | 待验证 | 待验证 | 关注 PROPFIND namespace |
| 坚果云 | 待验证 | 待验证 | 待验证 | 待验证 | 待验证 | 关注鉴权与路径编码 |
| Synology WebDAV | 待验证 | 待验证 | 待验证 | 待验证 | 待验证 | 关注证书与路径 |
| Alist WebDAV | 待验证 | 待验证 | 待验证 | 待验证 | 待验证 | 关注 redirect |
| Nginx WebDAV | 待验证 | 待验证 | 待验证 | 待验证 | 待验证 | 关注 DELETE / MKCOL |

该表是持续补充材料，不要求当前版本完成所有真实服务端验证。只要实际测试过某个服务端，就记录版本、配置要点、失败原因和建议文案。

#### 6.2.3 PROPFIND 解析差异

补强 XML 解析：

- namespace 差异。
- `207 Multi-Status` 中单项状态差异。
- 目录项排除。
- `getcontentlength` 缺失。
- `getlastmodified` 格式差异。
- 文件名 URL 编码与 basename 校验。

#### 6.2.4 超时、重试与错误分类

建议为 WebDAV 操作明确：

- 连接超时。
- 读取超时。
- 上传超时。
- 下载超时。
- 服务器 401 / 403 / 404 / 405 / 409 / 423 / 507 等状态映射。
- 有限重试策略。
- 同名冲突处理。

错误文案仍需强调本地数据未受影响。

### 6.3 非目标

- 不新增 WebDAV 多账户。
- 不做服务商专用适配 UI。
- 不要求开发者拥有或注册多个真实 WebDAV 服务。
- 不改变备份包格式。
- 不做同步。

### 6.4 验收标准

- 至少形成一组本地 WebDAV mock / fixture 测试。
- 真实服务端兼容表允许大部分条目标记为“未验证”，但模板和记录规则必须明确。
- PROPFIND 解析覆盖常见 namespace 与状态差异。
- 网络、鉴权、权限、容量不足、目录不可用等错误有稳定分类。
- 上传 / 下载失败不会影响本地保存。
- 所有错误对象不包含凭据。

## 7. v1.5.4：WebDAV 凭据安全

### 7.1 目标

解决 WebDAV 密码 / 应用令牌的持久化体验，让安全与便利形成闭环。

当前无系统密钥链时，拒绝“记住密码”是正确选择。但长期看，远端备份如果每次都要求输入密码，会降低用户使用频率。因此建议将凭据安全作为单独小版本。

### 7.2 推荐方案

#### 7.2.1 实施前技术选型

进入实现前应先确认：

- 跨平台 keyring / credential 库选型。
- Windows Credential Manager 的 target name / service name 命名规则。
- macOS Keychain 与 Linux Secret Service 的服务名、账户名和错误映射。
- 旧配置迁移策略。
- 密钥链删除失败时的用户提示与脱敏诊断记录。

#### 7.2.2 优先接入系统密钥链

Rust 侧新增凭据存取边界：

```text
save_webdav_secret(account_key, secret)
load_webdav_secret(account_key)
delete_webdav_secret(account_key)
```

配置文件只保存：

- WebDAV 地址。
- 用户名。
- 远端目录。
- 是否存在已保存凭据。
- 密钥链引用 key。

配置文件不得保存：

- 密码。
- 应用令牌。
- Basic Auth header。
- 带凭据的 URL。

#### 7.2.3 如果暂不接入密钥链

如果该版本不实现密钥链，则建议把界面改成明确的会话模式：

- “记住密码”不显示，或明确标为不可用。
- “不记住密码”改为“本次会话使用密码 / 令牌”。
- 应用重启后密码字段为空。
- 保存配置只保存非敏感字段。
- 创建远端备份、刷新列表、下载、删除时，如果缺少密码，则提示重新输入。

#### 7.2.4 密钥链不可用时的降级

即使实现系统密钥链，也要考虑 Credential Manager / Keychain / Secret Service 不可用或读取失败的情况。

建议降级策略：

- 如果系统密钥链完全不可用，自动回退到“本次会话使用密码 / 令牌”模式。
- 如果已保存凭据读取失败，提示用户重新输入，而不是反复使用失效引用重试。
- 降级状态应在数据管理区或诊断面板中可见。
- 降级记录必须脱敏，只记录“密钥链不可用 / 读取失败”这类错误分类，不记录 secret。
- 清除配置时，即使密钥链删除失败，也要清除本地配置引用，并提示用户可能需要到系统凭据管理器手动确认。

### 7.3 清除配置规则

清除 WebDAV 配置必须：

- 删除配置文件。
- 删除系统密钥链 secret。
- 清空前端表单密码字段。
- 使内存中的旧凭据失效。
- 后续请求不能继续使用旧凭据。

### 7.4 非目标

- 不做多 WebDAV 账户。
- 不做端到端加密备份。
- 不做 OAuth 或服务商专用登录。
- 不把凭据写入 zip 备份包。

### 7.5 验收标准

- 如果接入系统密钥链，勾选“记住密码”后，重启应用仍可测试连接或创建远端备份。
- 如果采用会话密码模式，重启后密码字段为空，远端操作会明确提示重新输入密码。
- 配置文件中不包含明文密码或应用令牌。
- 清除配置后，密钥链 secret 被删除。
- 密钥链读取失败时，应用提示重新输入密码。
- 系统密钥链不可用时，可降级到会话密码模式，并留下脱敏诊断记录。
- 错误、日志和 Debug 输出均通过脱敏测试。

## 8. v1.5.5：架构债地图与入口迁移

### 8.1 目标

在进入定时备份、保留策略和活动日志之前，先收敛 `v1.4.0` 留下的状态过渡层风险。

该版本不追求一次性删除旧 `useStore.ts`，而是建立可执行的退出路径，并完成首批低风险迁移。将架构债提前，可以让后续几个后台逻辑版本在新边界上多运行一段时间，避免到 `v1.6.0` 前夕才做底层迁移。

### 8.2 范围

#### 8.2.1 依赖地图

新增一份迁移清单，按以下类别统计：

- `appController` 里的旧 store 读写。
- Canvas / engine 里的旧 store 读写。
- 组件直接执行的领域写入。
- 组件只读订阅旧 store 的路径。
- 测试中依赖旧 store 初始化的路径。

#### 8.2.2 Controller 写入边界

逐步将跨层操作收口为明确用例：

- 领域写入走 Domain action 或领域用例。
- 视口调整走 Viewport action。
- 界面状态走 UI action。
- 跨层编排留在 Controller / Facade。

#### 8.2.3 首批迁移建议

优先迁移低风险入口：

- 只影响 UI state 的开关。
- 只影响 Viewport state 的定位 / reset。
- 不涉及 Undo/Redo 的纯界面操作。
- 不涉及持久化格式的读订阅。

避免第一批迁移：

- 拖拽落位。
- Undo/Redo patch 应用。
- 备份恢复后的状态替换。
- 撕下窗口状态联动。

#### 8.2.4 旧桥接退出条件

明确 `legacyDomainBridge` 删除条件：

- 旧 store 不再作为 Domain 写入主路径。
- Domain state 的订阅、持久化和测试都不依赖旧 store 镜像。
- 旧 store 中的 Viewport / UI 迁移项已归位。
- 关键交互测试覆盖迁移前后的行为一致性。

#### 8.2.5 渲染性能边界保护

状态容器拆分不能破坏现有细粒度订阅模型，尤其是小地图、核心画布和便签列表的局部渲染连贯性。

迁移依赖地图中应专门标记：

- MiniMap 是否仍按便签 ID / 布局投影订阅，而不是订阅粗粒度根状态。
- Canvas 是否避免因 Viewport / UI 小变动触发全量 Note 重渲染。
- NoteCard 是否保持必要的局部 memo / selector 边界。
- 拖拽、框选、hover-panning、定位高亮是否仍能避免高频 React 根更新。

建议补充回归指标：

- 大看板下拖拽单张便签时，不触发所有便签重渲染。
- 小地图更新不破坏主画布拖拽流畅度。
- Viewport state 迁移后，程序定位与用户平移不会造成多余全量状态提交。

### 8.3 非目标

- 不重写全部状态管理。
- 不替换 Zustand。
- 不顺手引入 SQLite / libSQL。
- 不改变用户可见行为。
- 不把架构收敛与新体验功能混在一个版本里。

### 8.4 验收标准

- 有明确旧 store 依赖地图。
- 至少一类跨层操作不再直接依赖旧 `useStore.getState()`。
- 新增或迁移后的 Controller 用例测试通过。
- MiniMap 与核心 Canvas 的细粒度订阅边界未被破坏。
- 大看板拖拽、定位和小地图更新不出现明显全量重渲染回归。
- 文档记录下一步可删除路径与阻塞项。
- 用户可见行为保持不变。

## 9. v1.5.6：定时远端备份基础

### 9.1 目标

在不改变“WebDAV 不是同步”的前提下，让用户可以选择自动把本地快照上传到远端。

该版本只做定时上传基础，不做远端保留策略。保留策略放到 `v1.5.7`，避免一个版本同时处理调度与删除。

### 9.2 范围

#### 9.2.1 默认关闭

定时远端备份必须默认关闭。用户必须显式打开。

#### 9.2.2 固定频率

第一版建议只提供少量固定选项：

- 每 6 小时。
- 每 12 小时。
- 每天。
- 每周。

不提供 cron 表达式。

#### 9.2.3 桌面生命周期触发

纯时间间隔不适合所有桌面使用习惯。用户可能每天只打开 SoNotes 20 分钟，导致“每 6 小时”永远触发不了。

建议在固定频率之外增加一个低风险触发策略：

- **静默期备份**：本地数据有修改，且最近一段时间无编辑、拖拽、恢复等活动时，允许触发一次远端备份。
- **退出前尝试备份**：用户退出应用时，如果距离上次成功远端备份超过阈值且本地有修改，可提示或尝试创建远端备份。

退出前备份必须避免长时间阻塞关闭流程。第一版更推荐“提示用户是否先备份再退出”，而不是静默卡住退出。

#### 9.2.4 上传前 gate

每次定时或生命周期触发上传必须：

1. 确认 WebDAV 配置可用。
2. 调用 `persistenceFacade.flushNow()`。
3. flush 成功后创建临时 zip。
4. 上传到远端。
5. 记录最近结果。
6. 清理临时文件。

flush 失败时不得上传旧快照。

#### 9.2.5 最近结果可见

数据管理区应展示：

- 最近一次自动备份时间。
- 最近一次结果。
- 最近失败原因。
- 下一次计划时间。
- 是否存在退出前待备份提示。

#### 9.2.6 最小活动记录

自动备份本身是后台能力，失败时用户很难从界面直观看到过程。因此 `v1.5.6` 应随定时备份一起实现最小活动记录，而不是等到完整活动日志版本。

最小记录范围：

- 自动备份触发原因：固定频率、静默期、退出前提示。
- 是否通过 `flushNow()`。
- 是否成功创建临时 zip。
- 是否成功上传。
- 最近失败原因。
- 最近成功远端备份文件名。

完整历史列表、保留策略记录和异常保护记录留到 `v1.5.8` 扩展。

#### 9.2.7 后台任务资源边界

自动备份涉及 zip 创建、图片文件读取、hash 校验与 WebDAV 上传。即使由 Rust / Tauri 侧执行，也必须避免影响前端 UI 线程与画布交互。

规划要求：

- zip 创建、hash 校验和 WebDAV 上传不得阻塞前端 UI 线程。
- Rust 侧重 I/O 应进入合适的后台任务或 blocking 线程，不在命令主路径长时间占用。
- 前端进度更新需要节流，避免上传进度或日志写入造成 React 高频更新。
- 用户正在拖拽、框选、hover-panning 或编辑文本时，静默期备份不应抢占明显资源。
- 如果备份包过大，允许延后静默期备份，并记录“因应用活跃或资源占用延后”。

#### 9.2.8 Single-flight 与并发边界

自动备份、手动远端备份和退出前备份必须共享同一个 backup single-flight lock。

规划要求：

- 同一时间只能有一个创建 zip / 上传远端备份任务运行。
- 手动远端备份运行中，自动备份触发应跳过或合并为“已有任务进行中”，不得再创建第二个 zip。
- 自动备份运行中，用户手动触发远端备份时应提示已有任务进行中，或复用当前任务结果。
- 退出前备份不得与已运行的自动备份并发。
- 本地恢复或远端恢复流程运行期间，禁止自动备份触发。
- 新的自动触发不得无限排队；最多保留一个待触发意图，或直接跳过并记录原因。

### 9.3 非目标

- 不自动下载远端备份。
- 不自动恢复。
- 不合并多端数据。
- 不在后台静默覆盖本地。
- 不做远端保留策略。
- 不承诺实时上传每一次编辑。

### 9.4 验收标准

- 自动远端备份默认关闭。
- 开启后，应用能按固定频率或静默期策略创建远端备份。
- 退出前备份不会无提示地长时间阻塞应用关闭。
- flush 失败时不调用远端上传。
- 上传失败不影响本地保存。
- zip 创建、hash 校验和 WebDAV 上传不导致前端明显掉帧或假死。
- 上传进度、最近结果和日志更新不会形成高频 React 根更新。
- 自动备份、手动远端备份和退出前备份不会并发创建 zip 或并发上传。
- 恢复流程运行期间不会触发自动备份。
- 最小活动记录能展示最近成功、最近失败和触发原因。
- 最近结果、失败原因和下一次计划时间可见。
- 文案不使用“同步”。

## 10. v1.5.7：远端备份保留与清理

### 10.1 目标

在自动远端备份可用后，为远端备份数量提供可控边界，避免用户的 WebDAV 目录无限堆积 zip。

该版本只清理 SoNotes 自己生成、命名规范的备份包，并且必须防止“坏的新备份触发清理，删除健康旧备份”。

### 10.2 范围

#### 10.2.1 保留最近 N 个

建议第一版提供简单策略：

- 保留最近 3 个。
- 保留最近 5 个。
- 保留最近 10 个。
- 保留最近 20 个。
- 不自动清理。

默认建议为“不自动清理”或“保留最近 10 个”，视产品取舍决定。

#### 10.2.2 清理范围

只允许清理符合严格命名规则的文件：

```text
SoNotes_Backup_YYYYMMDDHHMMSS.zip
```

不清理：

- 用户目录中的其他文件。
- 命名不符合规则的 zip。
- 子目录。
- 非 zip 文件。

#### 10.2.3 异常断崖式下跌保护

清理前必须比较本次新备份与最近健康备份的摘要。如果出现明显异常，应中止自动清理并提示用户。

建议监测：

- zip 文件大小断崖式下降。
- Note 数量断崖式下降。
- Board 数量异常减少。
- Image Note 数量或图片文件数量异常减少。
- `data.json` 合法但内容接近空数据。

示例规则：

- 本次 Note 数少于最近健康备份的 30%。
- 本次 zip 体积少于最近健康备份的 30%，且图片文件数量明显减少。

触发后：

- 本次备份可以保留为可疑备份。
- 不执行远端清理。
- 在数据管理区展示警告。
- 用户可以手动确认“我知道数据量下降，允许以后以此为健康基线”。
- 只有用户确认新健康基线后，后续自动清理才可以继续使用该基线。

该版本不自动判断“用户是否真的想删除很多数据”。跨会话、崩溃恢复或状态重启后，这类意图判断不可靠；只要出现断崖式下跌，就优先保护旧备份。

#### 10.2.4 手动清理预览

如果提供手动“清理旧备份”入口，应先展示：

- 将删除的备份数量。
- 最旧备份时间。
- 最新保留备份时间。
- 是否存在异常下跌警告。

不需要展示备份内容。

#### 10.2.5 自动备份后的清理

自动上传成功后，可按配置触发保留策略。上传失败时不执行清理，避免在没有新备份的情况下删旧备份。

清理前的摘要比较、远端列表刷新和删除请求也应作为后台 I/O 处理，不得阻塞画布交互。异常断崖式下跌保护需要读取备份摘要时，应优先复用 `v1.5.2` 的验证结果或 manifest 摘要，避免重复解压大文件。

### 10.3 非目标

- 不按备份内容合并。
- 不删除无关远端文件。
- 不跨目录递归清理。
- 不提供复杂日历保留策略。
- 不自动恢复清理前的远端文件。

### 10.4 验收标准

- 保留策略只作用于规范命名的 SoNotes 备份包。
- 上传失败不会触发远端清理。
- 新备份出现大小或数量异常断崖式下跌时，不会自动清理旧备份。
- 用户未确认新健康基线前，异常下跌备份不会成为自动清理判断依据。
- 清理前摘要比较和远端删除不会造成前端 UI 假死。
- 清理失败不会影响本地保存。
- 删除远端备份前有明确范围和结果反馈。
- 删除操作不包含同步或合并语义。

## 12. v1.5.9：v1.6.0 预备与体验基线

### 12.1 目标

在进入 `v1.6.0` 前，完成体验主题定稿、关键流程冒烟与低风险反馈收口，避免 `v1.6.0` 同时承担“想清楚做什么”和“把功能做完”两件事。

`v1.5.9` 更像一个产品与工程预备版本：它可以有少量低风险修补，但不应引入新的领域模型或大型功能。

### 12.2 范围

#### 12.2.1 体验主题定稿

围绕三个候选方向做轻量评估：

- 快速捕获与捕获后定位。
- Spotlight / 搜索结果理解。
- 图片便签查看与缺失图片反馈。

输出一份 `v1.6.0` 计划书，明确只选择其中一个作为主线，并写清楚不做项。

#### 12.2.2 关键流程冒烟清单

建立一份人工或自动化冒烟清单，覆盖：

- 快速捕获新建文本便签。
- 粘贴或拖入图片创建 Image Note。
- Undo/Redo 常用领域操作。
- 撕下便签、定位、置顶、贴回。
- 本地 zip 备份与恢复。
- WebDAV 创建、列出、下载、恢复、删除。
- 自动备份、保留策略和异常下跌保护。
- 恢复后图片预览。
- 废纸篓软删除、还原、永久删除。

#### 12.2.3 三轨交互与程序定位（依赖评估，gate 本身 defer 到 v1.6.0）

如果 `v1.6.0` 候选主题包含“捕获后定位到新便签”“Spotlight 结果跳转”“图片便签查看定位”等程序触发的 Viewport Action，预备阶段**只做依赖评估与 defer 记录**，不在 `v1.5.9` 预建 Viewport Action gate 抽象。

`v1.5.9` 现状：`locateAndSelectNote()` / `locateDetachedNote()` 由模态浮层或撕下窗口触发，不与画布 active drag / edge-push / sticky drag 并发；现有单 rAF / DOM 就绪轮询行为可保留。真正需要与三轨交互、hover-panning、拖拽时序协调的 gate，应在 `v1.6.0` 落地“捕获后定位”等真实消费者时再建，并写入该版本计划书的 `Viewport Action dependency` 段。

`v1.6.0` 真正实现 gate 时再重点验证：

- Regular / God Mode / Anti-Flick 三轨交互下，程序定位不会与用户平移互相抢状态。
- hover-panning 临界状态下触发 Spotlight 跳转，不出现画面抖动或回弹。
- 拖拽过程中不执行强制定位；如必须定位，应延后到拖拽结束。
- 定位高亮只影响 UI state，不污染 Undo/Redo。
- 程序定位不会触发全量画布重渲染。

#### 12.2.4 低风险文案与反馈收口

可处理不改变数据模型的体验细节：

- 备份 / 恢复 / WebDAV 失败提示更一致。
- 快速捕获目标看板提示更明确。
- 缺失图片、恢复失败、远端失败的错误语气统一。
- 避免用户把远端备份误解为同步。

#### 12.2.5 v1.6.0 原型或草图

如果最终选择的主题涉及明显交互变化，应先在 `docs/prototypes/` 或计划书中形成原型说明。

原型只用于确认交互，不应在 `v1.5.9` 大量接入运行时代码。

### 12.3 非目标

- 不实现标签系统。
- 不实现 WebDAV 同步。
- 不新增通用文件管理能力。
- 不让撕下便签直接编辑。
- 不改变备份包格式。
- 不迁移存储引擎。
- 不同时开发多个 `v1.6.0` 候选主题。

### 12.4 验收标准

- `v1.6.0` 的主题已明确，且只有一个主线。
- `v1.6.0` 计划书已写明目标、非目标、技术边界和验收标准。
- 关键流程冒烟清单已形成，并至少完成一次基线验证。
- 若选定主题依赖程序触发 Viewport Action：`v1.6.0` 计划书已记录 `Viewport Action dependency`（含 defer 理由与拟建 gate 的验收意图）；**不**要求 `v1.5.9` 已验证 gate 与三轨交互 / hover-panning / 拖拽时序不冲突（该项属于 `v1.6.0`）。
- 文案与反馈不再把 WebDAV 暗示为同步。
- 没有引入新的持久化格式或新的领域模型。

## 13. v1.6.0：单一体验主题版本

### 13.1 推荐定位

`v1.6.0` 不建议承载同步、协作或大型数据模型变更。它更适合作为一个“信任链稳定后的体验版本”。

当前倾向主题：

> 捕获与整理体验增强

但最终主题应由 `v1.5.9` 的反馈、原型和关键流程冒烟结果决定。如果 `v1.5.9` 证明搜索定位或图片查看更值得优先，则 `v1.6.0` 应调整为对应的单一体验主题。

**定稿状态（v1.5.9 plan）**：`docs/plans/v1.5.9-prep-and-experience-baseline.md` 已将 Primary Theme 定为「捕获与整理体验增强」。实施与验收以该 plan 为准；本节历史表述保留为决策过程说明，**不再**要求 `v1.5.9` 重新“再决定一次”主题。

原因：

- 符合现有路线图的“捕获优先”原则。
- 不触碰 WebDAV 同步误解。
- 不扩大 Domain state 复杂度到标签、冲突、合并。
- 能直接改善桌面便签工具的日常使用频率。

### 13.2 候选能力

#### 13.2.1 快速捕获落点增强

可考虑：

- 捕获后在当前看板中明确高亮新便签。
- 快速捕获失败时保留输入内容，避免丢失。
- 捕获入口明确显示当前目标看板。
- 从废纸篓视图触发捕获时，明确写入当前看板而不是废纸篓。

捕获后定位属于程序触发的 Viewport Action，必须服从现有画布交互时序：不打断拖拽，不与 hover-panning 抢状态，不进入 Undo/Redo 历史。

#### 13.2.2 捕获后整理轻动作

可考虑：

- 捕获完成后提供短暂的“定位到新便签”入口。
- 支持捕获后选择颜色。
- 支持捕获后立即折叠。

这些仍然是单便签、低风险、可撤销的领域操作，不引入队列或临时素材篮。

#### 13.2.3 Spotlight 与搜索解释

可考虑：

- 搜索结果中更清楚地区分当前看板、其他看板、废纸篓。
- 定位结果时提供稳定高亮。
- 搜索空结果时给出低干扰反馈。

不建议在 `v1.6.0` 做标签筛选。

Spotlight 跳转必须特别验证 God Mode、Anti-Flick 与 hover-panning 临界状态，避免搜索定位造成 flickering 或视口回弹。

#### 13.2.4 图片便签查看体验

可考虑：

- 图片便签选中后提供更自然的查看尺寸。
- 缺失图片占位提供“重新检查图片文件”入口。
- 图片预览加载失败时展示稳定错误，而不是空白。

不建议扩展到通用文件管理能力。

### 13.3 建议只选一个主线

`v1.6.0` 最好只选一个主题：

- 如果用户反馈主要是“记录入口还不够顺”，选快速捕获。
- 如果用户反馈主要是“东西多了找不到”，选 Spotlight / 搜索。
- 如果用户反馈主要是“图片便签体验粗糙”，选图片查看。

不建议三个一起做。

### 13.4 非目标

- 标签系统。
- 剪贴板栈。
- 捕获队列。
- 托盘拖放 Dropzone。
- 撕下便签直接编辑。
- WebDAV 同步。
- 多端合并。
- CRDT / 向量时钟。
- 通用文件管理能力。

### 13.5 验收标准

根据最终主题确定，但必须满足：

- 不破坏本地保存与备份恢复链路。
- 所有新增领域操作进入 Undo/Redo 或明确说明为什么不进入。
- 新增程序定位或高亮动作不污染 Undo/Redo，不破坏三轨交互和 hover-panning 时序。
- 不扩大 WebDAV 语义。
- 不引入新的大体积内容写入 `data.json`。
- 文档和用户可见文案继续遵守 `CONTEXT.md` 的领域语言。

## 15. 风险与取舍

### 15.1 最大产品风险：用户误解为同步

WebDAV 一旦出现定时上传，用户很容易理解成“云同步”。因此所有文案都必须强调：

- 上传的是完整备份快照。
- 不会自动下载。
- 不会自动合并。
- 恢复必须手动确认。

### 15.2 最大工程风险：状态过渡层继续叠功能

旧 store 过渡期如果持续叠加新功能，后续会更难判断写入来源、撤销边界与持久化时机。

因此 `v1.5.5` 这样的架构债版本很有必要，即使它不带明显用户功能。

### 15.3 最大安全风险：凭据便利性压过安全性

记住密码必须依赖系统密钥链或等价安全存储。普通配置文件即使加一点混淆，也不应被描述为安全保存。

### 15.4 最大体验风险：v1.6.0 主题过散

`v1.6.0` 如果同时做捕获、搜索、图片查看、标签和托盘高级交互，会破坏 `v1.4.x` 以来每个版本一个主题的节奏。

---

## 16. 一句话总结

`v1.5.1-v1.5.9` 应继续围绕“备份可信、WebDAV 稳健、凭据安全、定时可解释、保留可控、活动可见、架构可退出、体验有基线”逐小版本收口；`v1.6.0` 再选择一个轻量体验主题，优先增强捕获与整理，而不是把 SoNotes 推向同步系统、协作工具或重型知识库。
