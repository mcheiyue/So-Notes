## 0. 统一约束（后续实施的硬规则）

### 0.1 行为不变（业务功能不受影响）

后续所有提交必须满足：

- 不新增用户入口、不改变交互语义、不改变数据结构对外含义；仅做结构拆分与副作用迁移。
- 如发现既有行为不一致：**优先视为回归**，除非在本文件中显式新增“行为变更条目”并经确认。

### 0.2 状态边界（不得混层）

- **Domain state（领域状态）**：便签/看板核心数据与关系，是唯一持久化来源；Undo/Redo 仅覆盖 Domain。
- **Viewport state（视口状态）**：平移/缩放/可视区域/交互运行态等高频状态，不作为持久化来源。
- **UI state（界面状态）**：面板显隐、右键菜单、选区等短暂状态，不作为持久化来源。
- **ViewMode（BOARD/TRASH）**：不持久化，启动默认 BOARD。

补充归属（必须明确）：

- `AppConfig.maxZ`：Domain（用于 z 序）
- `AppConfig.themeMode` / `AppConfig.maximized`：UI
- 保存状态反馈（`isSaving/saveStatus/saveError/lastSavedAt/saveGenerationId`）：Domain（由 `StorageService` 回写 Domain store；UI 仅消费展示）
- `stickyDrag`：Viewport（交互运行态）
- `isPinned`：UI

### 0.3 持久化策略（规则不变，只迁移位置）

- Domain Store 外部订阅自动持久化：
  - WAL：100ms 节流
  - Disk：2s 防抖
- 必须保留：`flushPersistNow()`（仅用于导入/清空/还原等少数原子场景）。
- WAL 与磁盘双源仲裁必须保留，并整体迁入 `StorageService`。
- 订阅变更判定必须使用 selector + equalityFn / 结构化对比，避免每次全量序列化或 stringify。
- **订阅回调必须“轻量”**：Zustand `subscribe` 可能在拖拽等高频变更下被频繁触发，`StorageService.attach()` 的同步回调内禁止做重量级工作（例如全量序列化/深拷贝/JSON stringify）。
  - 必须使用 **Dirty Flag + 调度**（例如 `requestIdleCallback`，无则降级为 `setTimeout`/微任务队列）将“序列化与落盘”移出同步回调，并做批量合并。

重要澄清（避免误解）：

- 旧实现以 **显式调用 `saveToDisk()`** 为主；新方案以 **订阅式自动持久化** 为主。
- 因此 v1.4.0 中的持久化部分是“**替换驱动模式**”，不是简单搬家：实施过程中必须保留过渡桥接，并在文档 §5 进行任何写入时机差异登记。

补充：Dirty Flag 调度的“临终遗言”保护（必须做）

- 仅依赖空闲调度（`requestIdleCallback`）不可靠：进程退出/窗口关闭/页面隐藏可能导致脏数据丢失。
- `StorageService` 必须绑定以下事件以 **best-effort** 触发 `flushPersistNow()`：
  - `window.beforeunload`
  - `document.visibilitychange`（进入 `hidden` 时）
  - （如有）Tauri 窗口关闭/隐藏等等价事件
- 注意：这是 Tauri WebView 环境；此处要求的是“尽力 flush + 明确失败兜底”，不得引入阻塞主线程的同步 XHR 方案。

补充：IPC 写入单飞互斥（必须做）

- 为避免 Rust 侧文件锁争用与重试耗尽：`StorageService` 在调用 `save_content` 期间必须实现 **in-flight 互斥**。
- 规则：前一个 IPC 写请求未返回 ack（成功或失败）前，禁止发射下一次写请求；期间如有新脏数据，仅标记 `isPending`，待 ack 后再发送“最新快照”。

### 0.4 DOM 副作用边界（禁止 DOM→状态反推）

- 交互“真相”必须在内存状态（engine/store），DOM 仅用于渲染。
- 任何 DOM 副作用必须通过 React hook/effect 承接（例如主题 class、`body.is-dragging` 等）。
- 拖拽“暂态渲染”允许：DOM transform/style 的临时渲染，但不得从 DOM 回推业务状态。

### 0.5 跨层用例位置（不得在 store 内做编排）

- 触及 Domain + Viewport + UI 的操作必须落在 Controller/用例层：`src/controllers/appController.ts`。
- store 仅做“本职更新”，不得直接调用其它 store 的写入动作；跨层编排由 controller 统一调度。

补充：全局交互入口必须走 controller（禁止指令穿透）

- `ShortcutsManager`、全局 `ContextMenu`（以及任何全局交互入口）必须是“**意图发射器**”：只调用 `appController` 的公开方法。
- 严禁在 UI 层（组件/快捷键/菜单）直接调用任何 store 的 actions 或 `store.getState()` 进行 Domain 写入。
- controller 内部负责校验当前交互上下文（例如：是否在输入框、是否拖拽中、是否处于 TRASH 等）后再决定是否调度 Domain/Viewport/UI 更新。

### 0.6 工程约束（不可妥协）

- 禁止：`as any`、`@ts-ignore`、`@ts-expect-error`。
- 禁止：空 catch、删除测试来“让它过”。
- 单个提交必须可回滚；每个提交必须可独立通过：
  - `npm run typecheck`
  - `npm run test`
  - `npm run build`

### 0.7 拆分后的渲染风暴防范（必须做）

拆分 store 后，组件可能同时依赖多个 store（例如 `domainStore.notesById` + `viewportStore.viewport`），若 selector 粒度或引用稳定性处理不当，容易引发冗余渲染。

- 消费者必须使用**精准 selector**，禁止“整段大对象”订阅。
- 当 selector 返回对象/数组组合时：必须使用 `zustand/shallow`（如 `useShallow`）或等价的稳定性策略，避免引用抖动触发渲染风暴。
- Domain actions 必须保持**同步纯粹状态变更**；任何异步计算/跨层编排必须放到 `appController`。

### 0.8 最终子代理审查阶段（必须做）

18 个提交全部完成、本地全量验证通过后，必须统一进入子代理审查阶段，用于确认实际实施是否符合本计划书，而不是只确认测试通过。

- 审查发生在全部 18 个 commits 完成之后；实施过程中不要求每个 commit 都委托子代理审查。
- 最终审查必须至少委托 3 个不同关注点的子代理，例如：
  - store / 持久化 / 导入导出；
  - UI / 快捷键 / 全局菜单 / Controller；
  - Canvas / 交互生命周期 / RAF 与全局监听；
  - 计划符合度与业务回归风险。
- 子代理审查必须覆盖全部 18 个 commits，并明确给出：
  1. 是否符合本计划书中每个 Commit 的目标与约束；
  2. 是否违反本文件 §0 的硬规则；
  3. 是否存在用户业务功能回归风险；
  4. 是否存在代码漏洞、功能冲突或业务逻辑问题；
  5. 是否需要补充测试、修复或行为变更登记。
- 最终审查未通过时，不得发布或合并；必须先修复阻断项并重新进行全量验证与最终审查。

## 2. 风险清单（以及必须采取的缓解手段）

| 风险 | 说明 | 缓解（必须做） |
|---|---|---|
| 跨 store 循环依赖 | 拆分后容易出现 A 写 B、B 又触发 A | 跨层写入统一走 `appController`；store 禁止写其它 store |
| 持久化竞态/写入丢失 | 订阅触发时序、节流/防抖迁移不当 | `StorageService.bootstrap()` 负责仲裁→灌入 Domain→attach 订阅；保留 generation/时间戳仲裁 |
| Canvas 监听/RAF 泄漏 | engine 生命周期管理不当导致多重监听/RAF | engine 必须有 dispose；React effect cleanup 必须调用；引入“每 Canvas 一实例” |
| 拆分后渲染风暴 | 多 store 组合订阅导致引用不稳、重复渲染 | 精准 selector + `useShallow`；避免订阅大对象；必要时拆分到多个 selector |
| 业务行为回归 | 拆分迁移过程中 selector/动作遗漏 | 每里程碑验收清单 + 手测用例；“行为变更”必须显式登记并确认 |
| 性能退化 | selector 粒度变化或序列化频繁 | selector + equalityFn；避免全量序列化；拆分后反而应更细粒度 |

对照代码复审发现的高风险缺口（必须纳入实施验收）：

- Canvas 当前仅处理 `window.blur`，缺少 `document.visibilitychange`；Commit 17 必须补齐并纳入手测。
- sticky drag 的放置确认当前从 DOM `style.transform` 反推位置；Commit 17 前必须消除该 DOM→状态反推依赖。
- `edgePushDragCompensation` / `activeNoteDrag` / `noteElementRegistry` 目前为模块级可变单例；Commit 17 中必须明确封装/归属与 dispose 清理策略。
