# SoNotes v1.4.8 实施计划：图片入口与附件一致性

---

## 1. 背景

`v1.4.7` 已经建立附件 / 图片能力的本地优先存储底座：**Note（便签）** 可以保存 `AttachmentRef` 引用，附件文件进入本地 `attachments/` 目录并按 SHA-256 内容寻址，`data.json` 只保存附件元数据与相对路径，不保存图片 base64 或二进制内容。

根据后续路线图，`v1.4.8` 的主题是“图片入口与附件一致性”。本版本不再重做附件底层模型，而是在既有附件底座上补齐用户可见入口和管理能力：让用户可以通过粘贴或拖入把图片加入便签，能在便签中看到图片预览，能移除附件引用，并能识别缺失附件与孤儿附件。

本版本仍然保持本地优先边界，不引入远端备份、在线同步或 zip 备份 / 恢复。图片预览采用 Tauri Asset Protocol + `convertFileSrc`，不再实现 Blob / Object URL 预览降级路径，避免维护两套图片来源生命周期。

---

## 2. 目标

### 2.1 图片粘贴入口

- 支持从剪贴板粘贴图片。
- 当剪贴板包含图片时，优先按图片附件处理。
- 当剪贴板不包含图片时，保持现有纯文本智能粘贴行为。
- 如果当前只选中一个未软删除便签，则把图片追加到该便签。
- 如果没有选中便签或选中了多个便签，则在当前视口中心创建新便签并附加图片。

### 2.2 图片拖入入口

- 支持把本地图片文件拖入画布空白区域。
- 第一版只支持拖到空白画布创建新便签并附加图片。
- 单次拖入多张图片时，按层叠偏移创建多张独立便签，每张便签附加一张图片。
- 不在第一版实现“拖到已有便签上追加图片”，避免与便签拖拽、框选、推墙扩展和点击命中产生交互冲突。

### 2.3 便签内图片预览

- 在便签正文区域下方显示图片附件预览。
- 图片预览只展示允许的图片附件类型：PNG、JPEG、GIF、WebP。
- SVG 不作为第一版图片入口或预览类型处理。
- 非图片附件暂不作为用户入口展示，避免把本版本扩大为泛附件管理。
- 折叠便签不展开附件预览。
- 撕下便签作为只读镜像，应同步显示图片预览，但不提供删除引用等写操作。

### 2.4 删除附件引用

- 用户可以从便签中移除某个图片附件引用。
- 移除引用只修改 **Domain state（领域状态）** 中该便签的 `attachments`，不立即删除本地附件文件。
- 附件引用增删属于领域状态变更，应进入 **Undo/Redo（撤销/重做）**。
- 如果同一附件仍被其他便签引用，移除当前引用不得影响其他便签。

### 2.5 缺失附件提示

- 附件文件缺失时，便签和看板仍可正常加载。
- 图片预览位置显示缺失附件占位提示。
- 用户可以从便签上移除缺失附件引用。
- 缺失附件不触发自动清理，不阻塞保存。

### 2.6 孤儿附件扫描 / 清理策略

- 可以扫描本地 `attachments/` 目录，识别未被任何便签引用的孤儿附件文件。
- 孤儿识别必须扫描完整 **Domain state**，包括位于 **Trash（废纸篓）** 中的便签。
- 清理孤儿附件必须是明确的用户动作。
- 软删除、还原、普通保存和启动加载都不得自动删除附件文件。

---

## 3. 非目标

本次不做以下能力：

- **远端备份 / WebDAV**：不上传、下载或连接远端存储。
- **在线同步**：不实现自动同步、自动拉取覆盖、多端合并或便签级冲突解决。
- **本地 zip 备份 / 恢复**：不实现 `SoNotes_Backup_<timestamp>.zip`、`manifest.json`、附件打包、恢复校验或失败回滚。
- **泛附件管理**：不做附件重命名、排序、批量管理、下载、打开方式管理或非图片附件预览。
- **拖到便签追加图片**：第一版不做，后续可在命中策略稳定后单独扩展。
- **base64 图片入库**：不允许把图片 base64 或二进制内容写入 `data.json`。
- **永久删除时自动删除附件文件**：永久删除便签只会让部分附件可能成为孤儿，实际清理必须由显式孤儿清理入口触发。

## 4. 已有实现边界

### 4.1 附件类型

当前核心类型位于 `src/store/types.ts`：

```ts
export interface AttachmentRef {
  id: string;
  hash: string;
  filename: string;
  mimeType: string;
  size: number;
  relativePath: string;
  createdAt: number;
}

export interface Note {
  // existing fields...
  attachments?: AttachmentRef[];
}
```

### 4.2 附件持久化封装

当前前端附件命令封装位于 `src/services/storage/attachmentPersistence.ts`：

- `writeAttachmentFromPath(sourcePath, filename, mimeType?)`
- `attachmentExists(relativePath)`
- `readAttachmentMetadata(relativePath)`

现有限制：

- 已支持从本地源路径写入附件，适合拖入本地图片文件。
- 尚不支持直接从剪贴板图片 bytes 写入附件。
- 尚不支持把受校验的附件相对路径解析为可供 `convertFileSrc` 使用的绝对路径。
- 尚不支持列出 `attachments/` 目录文件。
- 尚不支持删除孤儿附件文件。

### 4.3 Rust 附件命令

当前 Rust 附件实现位于 `src-tauri/src/attachments.rs`，已经具备：

- 流式 SHA-256。
- 内容寻址写入。
- `attachments/<hash>.<ext>` 相对路径。
- 安全路径校验与规范化边界检查。
- `spawn_blocking` 隔离同步文件 I/O。
- 同 hash 进程内写入串行化。

`v1.4.8` 应在此基础上补齐图片入口和一致性管理所需命令，而不是改写既有写入模型。

### 4.4 一致性检测工具

当前一致性工具位于 `src/services/storage/attachmentConsistency.ts`：

- `collectLiveAttachmentRefs(notes)`
- `collectLiveHashes(notes)`
- `detectMissingReferences(notes, existsFn)`
- `detectOrphanAttachments(knownFiles, notes)`

`v1.4.8` 需要为 `detectOrphanAttachments` 提供实际 `knownFiles` 来源，即后端列出附件目录文件的能力。

### 4.5 当前粘贴入口

当前粘贴入口位于 `src/components/Canvas.tsx` 的 `handlePaste`，只读取 `text/plain` 并走智能粘贴。

`v1.4.8` 应在该入口增加图片优先处理，同时保留以下现有保护：

- 输入框、文本域和可编辑区域内粘贴不拦截。
- Spotlight、Quick Capture、智能粘贴拆分面板、右键菜单打开时不处理画布粘贴。
- 拖拽交互锁定时不处理粘贴。

## 5. 业务边界决策

### 5.1 图片是附件，不是正文

图片继续作为附件引用保存，不进入 `content` 字段。

- `content` 仍表示用户输入的文本正文。
- 图片由 `attachments?: AttachmentRef[]` 表示。
- 图片预览是便签 UI 对附件引用的渲染结果，不改变正文语义。

### 5.2 图片粘贴的目标便签决策

当用户粘贴图片时：

- 如果当前只选中一个未软删除便签，则把图片追加到该便签。
- 如果没有选中便签，则在当前视口中心创建新便签并附加图片。
- 如果选中了多个便签，则创建新便签并附加图片，避免隐式批量复制图片到多个便签。

### 5.3 图片拖入的第一版策略

第一版只支持拖到空白画布创建新便签。

原因：

- 便签自身已有复杂拖拽、组拖拽、框选、推墙扩展和粘滞拖拽逻辑。
- 拖到便签追加图片需要更精细的命中与悬浮反馈，否则容易误触。
- 空白画布创建新便签已经覆盖最直接的图片收集场景。
- 多图拖入采用多张独立便签，而不是把多图塞入同一张便签，降低单个便签预览布局复杂度。

### 5.4 删除引用不等于删除文件

删除图片附件引用只修改便签引用关系，不删除文件本体。

- 文件是否仍被引用由完整 Domain state 决定。
- 未被引用的文件进入孤儿附件候选。
- 实际删除必须通过孤儿附件清理入口显式触发。

### 5.5 Trash 中的便签仍保护附件

位于 Trash 中的便签仍计入附件存活引用集合。

- 软删除不删除附件文件。
- 从 Trash 还原后附件引用应保持不变。
- 清理孤儿附件时不能把 Trash 中便签引用的附件判为孤儿。

## 6. 技术设计

### 6.1 附件写入命令扩展

图片入口按来源拆分写入路径，避免把所有图片都压到同一种 IPC 形态里。

#### 6.1.1 剪贴板图片

剪贴板图片不走前端大载荷 IPC 路径。第一版新增 Rust 原生剪贴板写入命令：

```rust
save_image_from_system_clipboard() -> AttachmentRef
```

要求：

- 前端只负责判断剪贴板中存在图片并发送轻量命令，不读取图片 Blob、ArrayBuffer 或 base64。
- Rust 侧通过 `tauri-plugin-clipboard-manager` 的 `read_image()` 读取系统剪贴板图片。
- `read_image()` 必须放入 `spawn_blocking`，不能在 async worker 或主线程中直接调用，避免平台剪贴板死锁或卡顿。
- `read_image()` 返回原始 RGBA 像素，不是 PNG / JPEG 原始文件流；Rust 侧需要用 `image` crate 将 RGBA 编码为 PNG 后再进入附件写入流程。
- 剪贴板图片第一版统一保存为 PNG，文件名可使用 `clipboard-image-<timestamp>.png` 或等价稳定命名。
- 统一 PNG 是第一版的兼容性取舍：优先保证 UI 截图、文字截图、代码截图和图表截图清晰；JPEG / WebP 编码策略留到后续按性能数据评估。
- Rust 侧复用既有 hash、扩展名、临时文件、rename、hash 锁和路径边界逻辑。
- 仍应设置剪贴板图片像素量或编码后字节数上限，避免超大截图在 Rust 编码阶段造成内存峰值；阈值集中为常量。
- 本命令只用于系统剪贴板图片，不作为本地文件拖入的默认路径。

需要新增依赖：

- `tauri-plugin-clipboard-manager`：读取系统剪贴板图片。
- `image`：将 RGBA 像素编码为 PNG。

不采用的路径：

- 不新增 `write_attachment_from_bytes(bytes, filename, mime_type)` 作为剪贴板主路径。
- 不让前端把图片 bytes 通过 Tauri IPC 传给 Rust。
- 不把剪贴板图片先转为 base64 或写入 `data.json`。

#### 6.1.2 本地图片拖入

本地文件拖入继续复用既有路径写入能力：

```ts
writeAttachmentFromPath(sourcePath, filename, mimeType?)
```

要求：

- 拖入文件不先读成前端 Blob / ArrayBuffer。
- 前端通过拖入文件的路径调用后端写入，由 Rust 侧流式 hash 并复制到 `attachments/`。
- 多图拖入必须队列化，避免同时发起大量磁盘写入和状态更新。
- 可设置单次拖入数量上限与单文件大小上限，超出时给出非阻塞提示。

### 6.2 图片预览来源能力

图片预览需要从 `relativePath` 获得可渲染来源。

首选方案：Tauri Asset Protocol + `convertFileSrc`。

流程：

```text
AttachmentRef.relativePath
└── Rust 校验并解析为 attachments/ 下的绝对路径
    └── 前端 convertFileSrc(absPath)
        └── <img src={assetUrl}>
```

理由：

- WebView 直接通过 Tauri asset protocol 加载本地图片，不需要把图片 bytes 通过 IPC 传回前端。
- 前端不需要生成 Blob / Object URL，也不需要维护 Object URL 引用计数和释放时机。
- Domain state 仍只保存附件引用和 `relativePath`，不保存绝对路径、asset URL、base64 或二进制内容。
- 图片加载失败可自然落到 `<img>` 错误状态，再由组件展示缺失占位。

需要新增或补齐：

```rust
resolve_attachment_path(relative_path) -> String
```

要求：

- 输入只能是 `AttachmentRef.relativePath`。
- Rust 必须复用附件路径校验，确认最终路径位于 `<Documents>/SoNotes/attachments/` 下。
- 返回值只作为运行时 UI 层预览输入，不写入 `data.json`，不进入 Undo/Redo。
- 前端拿到绝对路径后调用 `convertFileSrc(absPath)`，asset URL 只存在组件运行期。
- 若路径解析失败或文件不存在，返回可区分的缺失 / 非法路径错误。

Tauri 配置要求：

- 在 `src-tauri/tauri.conf.json` 中启用 `app.security.assetProtocol.enable: true`。
- 将 `app.security.assetProtocol.scope` 限制到 `"$DOCUMENT/SoNotes/attachments/**/*"` 或等价的附件目录范围。
- 当前 CSP 已包含 `img-src 'self' data: asset: http://asset.localhost;`，实施时需要复查构建后的平台 URL 是否仍被 CSP 允许。
- 不使用宽泛 scope，例如 `"*/**"` 或整个文档目录。
- `v1.4.8` 的 scope 先对齐当前实际存储根目录 `<Documents>/SoNotes/attachments/`；是否迁移到应用数据目录属于单独的存储位置决策，不在本版本顺手处理。

不提供 Object URL 降级方案：

- `v1.4.8` 只实现 Asset Protocol + `convertFileSrc` 预览路径。
- 如果某个平台 Asset Protocol 预览失败，按独立缺陷修复处理，不在第一版同时维护 Object URL 分支。
- 不再把“Rust 读回图片二进制，前端生成 Object URL”作为预览方案。

### 6.3 附件目录扫描与清理命令

为孤儿附件扫描 / 清理增加 Rust 命令：

```rust
list_attachment_files() -> Vec<String>
delete_attachment_file(relative_path) -> AttachmentDeleteResult
```

约束：

- `list_attachment_files` 只返回 `attachments/` 下的普通文件相对路径。
- 不递归进入非预期子目录。
- `delete_attachment_file` 必须复用安全路径校验。
- 前端调用删除前必须先用完整 Note 集合判定孤儿。
- 后端删除命令仍应只按路径删除，不自行推断 Domain state。

### 6.4 Store 动作

在 `useStore` 中增加领域动作：

```ts
addAttachmentToNote(noteId: string, attachment: AttachmentRef): void
removeAttachmentFromNote(noteId: string, attachmentId: string): void
```

要求：

- 目标便签不存在时安全返回。
- 目标便签位于 Trash 时不允许新增附件。
- 移除附件引用可作用于普通看板便签；Trash 中的只读管理入口不提供该操作。
- 增删引用更新 `updatedAt`。
- 增删引用写入 Undo/Redo 历史。

### 6.5 粘贴流程

建议流程：

```text
paste event
├── 如果交互锁定或输入控件内粘贴：交还浏览器默认行为
├── 如果剪贴板包含 image/* item
│   ├── preventDefault
│   ├── 校验图片类型，允许 PNG / JPEG / GIF / WebP，拒绝 SVG
│   ├── 调用 saveImageFromSystemClipboard
│   ├── Rust 侧读取系统剪贴板图片并编码为 PNG
│   ├── 生成 AttachmentRef
│   └── 单选便签则追加，否则创建新便签并附加
└── 否则继续现有文本智能粘贴
```

前端约束：

- 只做剪贴板类型探测和交互分流。
- 不读取图片 Blob / ArrayBuffer。
- 不把剪贴板图片 bytes 传入 Tauri IPC。
- 如果平台无法可靠暴露 `image/*` item，可退化为调用轻量命令后由 Rust 返回“剪贴板无图片”的可区分错误。

### 6.6 拖入流程

建议流程：

```text
dragover
└── 如果 DataTransfer 含文件，捕获阶段 preventDefault，避免浏览器跳页加载本地文件

drop
├── 捕获阶段 preventDefault
├── 如果不是空白画布目标：忽略第一版追加行为，但仍阻止浏览器默认打开文件
├── 过滤允许的图片文件：PNG / JPEG / GIF / WebP；拒绝 SVG 和非图片文件
├── 校验数量和单文件大小上限
├── 按队列调用 writeAttachmentFromPath
└── 在 drop 世界坐标附近按层叠偏移创建多张独立便签，每张便签附加一张图片
```

批量拖入的状态提交策略：

- 文件写入阶段不修改 Domain state。
- 按队列写入附件文件，收集成功的 `AttachmentRef` 与失败项。
- 写入结束后只执行一次 store `set`，批量创建便签、更新 `layoutNotesById`，并写入一条 compound Undo/Redo 历史。
- 用户撤销一次即可撤销整批拖入创建的便签。
- 部分失败时，只为成功写入的图片创建便签，并用 UI state 显示成功 / 失败摘要。

批量拖入的事务补偿策略：

- 本批次写入成功但尚未进入 Domain state 的附件引用必须暂存在局部收集器中。
- 如果批处理过程中发生不可继续错误、组件卸载、看板切换或最终 store `set` 失败，前端必须调用受校验的删除命令清理本批次已写入但未入 Domain state 的附件文件。
- 补偿删除只作用于“当前批次新写入且尚未提交引用”的附件，不扫描或删除既有附件。
- 一旦 Domain state 提交成功，后续不再做静默补偿；之后的未引用文件只能通过显式孤儿附件扫描 / 清理处理。
- 补偿失败时不得阻塞 UI 恢复，但必须记录错误并提示用户可稍后运行附件一致性检查。

### 6.7 图片预览组件

建议新增：

```text
src/components/note-render/NoteAttachments.tsx
```

职责：

- 接收 `noteId`、`attachments`、`readOnly`。
- 过滤允许的图片附件类型：PNG、JPEG、GIF、WebP；不预览 SVG。
- 通过 `resolve_attachment_path` + `convertFileSrc` 生成运行时图片来源并展示缩略图。
- 对缺失附件显示占位，并提供手动“重试”操作。
- 在非只读状态提供移除引用按钮。

约束：

- 组件不得把绝对路径或 asset URL 写回 store。
- 组件卸载不需要释放 asset URL；本版本不生成 Object URL。
- 同一个便签多图预览失败时，只影响对应图片占位，不影响其他图片和正文渲染。
- 缺失占位不是永久状态；点击“重试”时重新调用路径解析 / 存在性检查并刷新该附件预览。
- 可在窗口重新获得焦点时对当前已显示缺失占位的附件做一次轻量重试，避免临时文件锁、云盘延迟或安全软件短暂占用造成假死。
- 重试只更新 UI state，不自动删除附件引用，不触发 Undo/Redo。

### 6.8 一致性管理入口

建议在数据管理相关 UI 中新增附件一致性检查入口：

- 扫描缺失附件引用。
- 扫描孤儿附件文件。
- 展示统计数量。
- 用户确认后清理孤儿附件。
- 清理确认必须提示：孤儿附件清理是不可逆的物理文件删除，并会同时清空当前 Undo/Redo 历史。

第一版可先做轻量入口：

- “检查附件一致性”
- “缺失引用：N”
- “孤儿附件：N”
- “清理孤儿附件”确认按钮，确认文案必须明确“删除文件本体，不只是移除引用，并将清空撤销历史”

清理后的领域边界：

- 后端 `delete_attachment_file` 只执行受校验路径下的物理删除，不修改 Domain state。
- 前端在清理前必须基于完整便签集合，包括 Trash 中的便签，确认目标文件确实是孤儿。
- 用户确认清理后，前端删除孤儿附件文件并清空当前 Domain state 的 Undo/Redo 历史栈。
- 清理完成后，不尝试为历史栈自动补齐已删除的物理文件，也不允许旧历史跨越物理删除继续生效。

## 9. 验收标准

### 9.1 图片粘贴

- 粘贴图片可以生成或追加图片附件。
- 单选一个未软删除便签时，图片追加到该便签。
- 未选中或多选时，图片会创建为新便签附件。
- 剪贴板图片不通过前端 bytes IPC 写入，前端只发送轻量粘贴命令。
- Rust 侧通过系统剪贴板读取图片，统一编码为 PNG 后写入附件目录。
- 超过剪贴板图片像素量或编码后字节数上限时，Rust 写入命令返回可提示错误，不创建附件引用。
- 剪贴板图片统一保存为 PNG；JPEG / WebP 编码策略不进入第一版。
- PNG、JPEG、GIF、WebP 可以进入图片入口；SVG 不进入图片入口。
- 纯文本粘贴仍保持现有智能粘贴行为。
- 输入框、文本域和可编辑区域内粘贴不被画布图片入口拦截。

### 9.2 图片拖入

- 拖入单张图片文件到空白画布可以创建新便签。
- 拖入多张图片文件到空白画布会按层叠偏移创建多张独立便签，每张便签附加一张图片。
- 非图片文件和 SVG 文件不会创建附件。
- 拖入文件时不会触发浏览器默认跳页或打开本地文件。
- 多图拖入只产生一次领域状态提交，并写入一条 compound Undo/Redo 历史。
- 多图拖入在最终领域状态提交前失败或中断时，会清理本批已写入但未入 Domain state 的附件文件。
- 拖入行为不破坏现有便签拖拽、框选、推墙扩展和粘滞拖拽。

### 9.3 图片预览

- 便签可以通过 Asset Protocol + `convertFileSrc` 显示图片附件预览。
- 预览不通过 IPC 把图片 bytes 读回前端。
- 不生成 Blob / Object URL 预览来源。
- PNG、JPEG、GIF、WebP 可以预览；SVG 不预览。
- 绝对路径和 asset URL 只存在运行时 UI 层，不进入 `data.json`、store 或 Undo/Redo。
- 图片读取失败时显示缺失占位。
- 缺失占位提供手动重试；窗口重新获得焦点时可对缺失占位做轻量重试。
- 重试不自动清理附件引用，不进入 Undo/Redo。
- 折叠便签不显示附件预览。
- 撕下便签只读显示图片，不允许移除引用。

### 9.4 删除附件引用

- 用户可以从普通便签移除图片附件引用。
- 移除引用不删除附件文件。
- 移除引用可撤销和重做。
- 共享附件不会因移除某个便签引用而影响其他便签。

### 9.5 一致性管理

- 缺失附件引用可以被识别并在 UI 中提示。
- 孤儿附件扫描包含所有便签，包括 Trash 中的便签。
- 清理孤儿附件必须经过用户确认。
- 清理确认必须说明：该动作会永久删除附件文件本体，并清空当前 Undo/Redo 历史。
- 清理后当前 Undo/Redo 历史为空，旧历史不能跨越物理删除继续生效。
- 如果旧数据恢复出缺失附件引用，便签仍稳定加载并显示缺失占位。
- 软删除、还原、启动和普通保存不会自动删除附件文件。

### 9.6 工程验证

- `npm run typecheck` 通过。
- `npm run test` 通过。
- `npm run build` 通过。
- `npm run tauri build -- --debug` 通过。
- Tauri Asset Protocol scope 仅覆盖附件目录，CSP 允许平台实际使用的 asset URL。

## 10. 风险

- 如果剪贴板图片先转 base64 写入 `data.json`，会破坏 v1.4.7 建立的轻量主存储边界。
- 如果剪贴板大图走前端 bytes IPC，可能造成前端堆、IPC 序列化和 Rust 堆压力。
- 如果 Rust 原生剪贴板读取不放入 `spawn_blocking`，可能在部分平台造成剪贴板调用死锁或界面卡顿。
- 如果 RGBA 到 PNG 编码没有尺寸或内存上限，超大截图仍可能在 Rust 侧造成内存峰值。
- 剪贴板图片统一编码为 PNG 会丢失原始图片格式信息，但可避免在第一版维护跨平台原始格式探测与多编码路径。
- 如果 PNG 编码耗时过长，用户可能感知到粘贴图片延迟；第一版通过像素量 / 字节数上限控制，JPEG / WebP 策略留待后续基于实测评估。
- 如果本地拖入文件先读成前端 Blob / ArrayBuffer，会绕开现有流式路径写入优势。
- 如果拖入文件未在捕获阶段阻止浏览器默认行为，用户拖偏时可能触发浏览器打开本地文件并破坏应用会话。
- 如果多图拖入每写入一张就触发一次 store 更新，会造成高频领域状态提交和多条碎片化 Undo/Redo 历史。
- 如果批量拖入写入成功但最终领域状态提交失败，且没有事务补偿，会制造不属于任何便签的孤儿附件文件。
- 如果图片预览直接信任 `relativePath` 或前端自行拼绝对路径，可能绕过附件目录边界。
- 如果 Asset Protocol scope 配得过宽，可能把非附件目录暴露给 WebView 图片加载。
- 如果 `<Documents>/SoNotes/attachments/` 被 OneDrive、iCloud 等系统级目录重定向接管，Asset Protocol 读取可能遇到权限、延迟或路径可用性问题。
- 如果孤儿扫描忽略 Trash 中的便签，可能误删仍可还原便签引用的附件。
- 如果孤儿附件清理不清空 Undo/Redo 历史栈，可能在后续历史操作中恢复出“引用存在但文件已被物理删除”的缺失附件状态。
- 如果永久删除便签时自动删除附件文件，可能误删共享附件。
- 如果拖到便签追加图片第一版就上线，可能与既有拖拽和选择模型冲突。
- 如果附件引用增删不进入 Undo/Redo，会与现有领域状态变更可撤销预期不一致。
- 如果预览读取不做失败降级，缺失附件可能影响整个便签渲染。
- 如果缺失附件占位没有重试机制，临时文件锁、云盘延迟或安全软件短暂占用可能造成预览长期停留在缺失状态。
- 如果把 SVG 当作普通图片预览，可能引入脚本、外链或平台解析差异带来的安全边界问题。

## 11. 开放问题

这些问题不阻塞本计划，但实施对应 commit 前需要确认：

- **Asset Protocol 配置形态**：`scope` 使用 `$DOCUMENT/SoNotes/attachments/**/*` 还是由 Rust 启动时确认路径后再收紧到等价范围。
- **存储根目录策略**：当前附件跟随 `<Documents>/SoNotes/attachments/`，后续是否迁移到应用数据目录需要单独评估数据迁移、用户可见性、备份路径和兼容性。
- **剪贴板图片大小限制**：Rust 原生剪贴板读取后的像素量上限、编码后字节数上限和本地拖入单文件上限的具体数值，第一版必须集中为常量。
- **剪贴板图片编码策略**：第一版统一 PNG；后续是否保留来源格式，需要单独评估平台剪贴板暴露的格式信息与兼容性。
- **多图拖入队列策略**：队列并发数是否固定为 1，失败后是否继续后续文件。
- **批量拖入补偿时机**：组件卸载、看板切换、最终领域状态提交失败等中断信号的具体捕获点，需要实施时结合 Canvas 生命周期确认。
- **缺失附件重试策略**：窗口 focus 自动重试是否需要节流，以及是否只重试当前视口内可见便签。
- **缺失附件移除入口文案**：是否使用“移除引用”而不是“删除图片”，避免误导用户认为文件会被删除。
- **孤儿附件清理入口位置**：第一版放入现有数据管理区域，还是新建附件管理弹窗。
