# SoNotes v1.5.3 实施计划：WebDAV 协议边界与传输稳健性

---

## 1. 背景

`v1.4.9` 建立了本地 zip 备份 / 恢复格式，`v1.5.0` 接入 WebDAV 远端备份仓库，`v1.5.1` 加固了远端恢复路径、下载 token、重定向与图片缓存边界，`v1.5.2` 又补上了恢复前验证与恢复演练。

到 `v1.5.3`，备份链路的核心格式和恢复前校验已经成型，接下来最值得补的不是“接入更多真实服务端”，而是把 WebDAV 协议边界变成可重复验证的工程资产：

- 不依赖开发者手里是否有坚果云、Nextcloud、Synology、Alist 等真实账号。
- 不把真实网络波动变成版本交付阻塞。
- 用本地 mock / fixture 覆盖 WebDAV 常见响应差异。
- 让连接、列表、上传、下载、删除的错误边界可分类、可测试、可回归。

本版本主题是 **WebDAV 协议边界与传输稳健性**。

## 2. 当前代码基线

### 2.1 已存在的复用点

- `src-tauri/src/webdav.rs`
  - 已有 `WebDavConfig`、`WebDavConnectionResult`、`WebDavRemoteBackup`、`WebDavUploadResult`、`WebDavDownloadResult`、`WebDavDeleteResult` 等前端消费类型。
  - 已有 `normalize_webdav_url`、`normalize_remote_dir`、`validate_remote_backup_filename`，对 URL、远端目录、远端文件名做了安全约束。
  - 已有 `build_webdav_http_client`、`webdav_redirect_policy`、`validate_webdav_redirect_url`，并限制重定向目标。
  - 已有 `webdav_test_connection`、`webdav_list_backups`、`webdav_create_remote_backup`、`webdav_download_backup`、`webdav_delete_backup`。
  - 已有 `parse_propfind_response` 和若干纯 XML 解析测试。
  - 已有远端下载 token 生命周期、受控临时目录、启动清理和 token resolve / cleanup。
  - 下载侧已有 1 GiB 上限，并能在无 `Content-Length` 时按流式读取继续守住上限。
- `src/services/backup/WebDavBackupService.ts`
  - 已有前端 WebDAV 服务封装。
  - 已有 download token resolve / cleanup 的前端调用。
- `src/components/BoardDock.tsx`
  - 已有 WebDAV 配置、测试连接、创建远端备份、列出远端备份、删除远端备份、下载并恢复入口。
  - `v1.5.2` 后，远端恢复已经先下载、验证、展示摘要，再进入覆盖恢复确认。

### 2.2 当前缺口

- WebDAV 失败原因主要以字符串散落在命令实现里，不利于稳定测试和前端文案演进。
- `propfind_request` 与部分请求路径直接构造 `reqwest::Client`，请求层可测性不足。
- 现有 PROPFIND 测试以解析函数为主，还没有本地 mock server 覆盖真实 HTTP 方法、状态码、响应头和响应体组合。
- PROPFIND 解析还需要更明确地覆盖命名空间差异、目录自身条目、非 200 子状态、缺失 `href`、缺失 / 非法 `getcontentlength`、URL 编码文件名等边界。
- 上传、下载、删除的状态码语义还没有形成统一的“可重试 / 不可重试 / 用户可操作”分类。
- 真实服务端兼容记录目前缺少固定模板，后续用户反馈不容易沉淀成 fixture。

## 3. 目标

### 3.1 建立 WebDAV 协议 fixture 与 mock 测试基座

新增 WebDAV 协议测试资产，第一批覆盖：

- 标准 `207 Multi-Status` PROPFIND 响应。
- 带不同 XML namespace 前缀的 PROPFIND 响应。
- PROPFIND 返回 401 / 403。
- 上传返回 201 / 204。
- 删除返回 404 / 423。
- 下载缺失 `Content-Length`。

这些测试应默认在本地、离线、稳定运行，不依赖真实 WebDAV 服务。

### 3.2 强化 PROPFIND 解析边界

列表解析需要稳定回答：

- 哪些 entry 是当前远端目录自身，应跳过。
- 哪些 entry 是合法的 SoNotes 备份 zip，应展示。
- 哪些 entry 不是备份文件，应忽略。
- 哪些 entry 子状态不是 2xx：整体 PROPFIND 失败由请求状态处理；单条 propstat 不是 2xx 时跳过该 entry，不增加前端不可读条目展示复杂度。
- 哪些 size / last modified 缺失时可以继续展示。
- 哪些 XML 格式错误必须返回可识别错误。

### 3.3 引入内部 WebDAV 错误分类

在 Rust 内部建立稳定错误分类，避免把“用户文案字符串”作为测试断言核心。

第一批错误分类建议覆盖：

- `auth_failed`
- `forbidden`
- `not_found`
- `path_conflict`
- `locked`
- `insufficient_storage`
- `method_not_allowed`
- `timeout`
- `network_unreachable`
- `redirect_rejected`
- `unexpected_status`
- `invalid_propfind_response`
- `download_too_large`
- `invalid_remote_file_name`
- `local_temp_file_error`

本版本默认保持前端返回类型中的 `error: Option<String>` 兼容；Rust 测试应优先断言内部错误分类或固定映射函数，而不是脆弱地匹配整段中文文案。

### 3.4 统一传输状态码语义

连接、列表、上传、下载、删除应有一致的状态码解释：

- 401：鉴权失败。
- 403：权限不足或访问被拒绝。
- 404：目标不存在；删除远端备份时可以保持当前“已不存在也视为无需删除”的语义。
- 405：服务端不支持当前方法或路径不是 WebDAV endpoint。
- 409：远端目录不存在、父路径冲突或上传路径不可用；上传路径中沿用现有同名冲突重试语义。
- 412：`If-None-Match: *` 触发的同名对象已存在；上传路径中进入同名冲突重试。
- 423：资源被锁定。
- 507：远端空间不足。
- 5xx：服务器异常，通常可稍后重试。

409 统一归类为 `path_conflict`，再由 `WebDavOperation` 上下文决定用户文案和是否进入上传冲突重试。

412 也归类为 `path_conflict`。当前它只用于上传同名对象已存在的冲突重试，不需要单独暴露 `PreconditionFailed` 文案。

`v1.5.3` 不新增通用自动重试机制。`retryable` 只作为内部分类或未来 UI / 活动日志提示依据；上传同名冲突重试是现有行为，本版本只固定测试，不扩大范围。

### 3.5 留下真实服务端兼容记录模板

新增一份记录模板，让未来真实用户反馈可以被转成 fixture：

- 服务端名称和版本。
- 基础 URL 形态。
- PROPFIND 响应特点。
- 上传 / 删除 / 下载状态码特点。
- 是否有特殊 header 要求。
- 可脱敏的响应样例。
- 是否已转成自动化 fixture。

## 4. 非目标

本版本不做：

- 不强制接入多个真实 WebDAV 服务端测试。
- 不要求开发者准备多个第三方账号。
- 不新增多账号 WebDAV 配置。
- 不实现系统密钥链或记住密码能力。
- 不改变 zip 备份格式。
- 不递增 `BACKUP_FORMAT_VERSION`。
- 不新增 WebDAV 同步、多端合并或冲突解决语义。
- 不新增定时备份。
- 不改变图片文件存储模型。
- 不把 SoNotes 变成通用 WebDAV 文件管理器。

## 5. 业务边界决策

### 5.1 mock 优先于真实服务端矩阵

`v1.5.3` 的兼容目标不是“我亲自测过很多服务端”，而是“我知道 WebDAV 会怎样变形，并把这些变形固定进测试”。

真实服务端记录只作为补充材料，不作为版本验收硬门槛。

### 5.2 用户文案与工程分类分离

对用户展示的错误信息应该继续清楚、简短、中文友好；但工程内部需要有稳定分类。

建议新增内部结构：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum WebDavErrorKind {
    AuthFailed,
    Forbidden,
    NotFound,
    PathConflict,
    Locked,
    InsufficientStorage,
    MethodNotAllowed,
    Timeout,
    NetworkUnreachable,
    RedirectRejected,
    UnexpectedStatus,
    InvalidPropfindResponse,
    DownloadTooLarge,
    InvalidRemoteFileName,
    LocalTempFileError,
}
```

本版本的硬约束：

- 不得非必要改变现有用户可见错误文案。
- `WebDavErrorKind` 与 `WebDavOperationError` 只作为 Rust 内部分类与测试锚点。
- Tauri 命令对外返回的 `String` 必须保持兼容，除非某个状态码此前没有明确文案。
- `v1.5.3` 默认不新增前端 `errorCode` 字段。
- 只有当测试或 UI 逻辑确实需要区分状态时，才新增可选 `errorCode`，并单独提交。

`invalid_remote_file_name` 需要区分两类场景：

- 用户主动下载 / 删除某个非法远端文件名：返回 `invalid_remote_file_name`。
- PROPFIND 列表里出现非法 entry：跳过该 entry，不把整个列表判失败。

### 5.3 请求层先可测，再考虑抽象

本版本可以把 `reqwest::Client` 创建和请求执行拆开，但不应引入过重的 WebDAV client 抽象。

建议方向：

- 保留现有命令函数签名。
- 新增内部 `*_with_client` 或 `*_inner` 函数，测试时传入本地 mock server 的 base URL 和 client。
- URL 规范化由外层调用点负责；内层请求函数接受已规范化的请求目标，不再重复调用 `normalize_webdav_url`。
- 测试可以直接构造 `http://127.0.0.1:PORT` 的请求目标传给内层函数，不需要放宽生产 URL 规范化规则。
- `build_webdav_http_client(timeout)` 继续作为生产入口。
- 不为了测试引入跨模块大接口。

### 5.4 默认不新增测试依赖

优先使用 Rust 标准库 `TcpListener` / `TcpStream` 建一个很薄的测试 server helper，覆盖方法、路径、header、body、响应状态码。

timeout 不通过手写 helper 延迟响应来测。若确实需要请求级 timeout 覆盖，可以单独评估引入 `httpmock` 或 `wiremock` 作为 dev-dependency；其他场景只有当测试 helper 明显失控时再考虑新依赖。若引入新依赖，需要单独 commit 并说明理由。

### 5.5 删除 404 语义保持兼容

当前远端删除遇到 404 时，可以理解为“目标已经不存在”。`v1.5.3` 不应把它改成用户可见失败，避免用户在清理远端列表时被无意义阻塞。

但删除 423 必须被明确分类为 `locked`，并展示资源被锁定的失败原因。

### 5.6 下载无 Content-Length 不是失败

部分 WebDAV 服务不会返回 `Content-Length`。这不应该直接失败。

正确边界是：

- 有 `Content-Length` 且超过上限：下载前失败。
- 无 `Content-Length`：允许流式下载。
- 流式读取过程中超过上限：立即失败、删除未完成临时文件、释放 token。

## 6. 技术设计

### 6.1 WebDAV 错误模型

建议新增内部类型：

```rust
#[derive(Debug, Clone, PartialEq, Eq)]
struct WebDavOperationError {
    kind: WebDavErrorKind,
    status: Option<u16>,
    retryable: bool,
}
```

`WebDavOperationError` 不保存用户文案，不包含 `message: String`。用户可见文案只由 `webdav_error_message()` 在 Tauri 命令返回前生成，避免结构体相等比较被中文文案变化拖动。

配套函数：

```rust
fn classify_webdav_status(operation: WebDavOperation, status: reqwest::StatusCode) -> WebDavOperationError
fn classify_reqwest_error(operation: WebDavOperation, error: reqwest::Error) -> WebDavOperationError
fn webdav_error_message(error: &WebDavOperationError) -> String
```

`operation` 建议覆盖：

- `TestConnection`
- `ListBackups`
- `UploadBackup`
- `DownloadBackup`
- `DeleteBackup`

这样相同状态码可以在不同操作下保留不同文案。例如 404 在列表可能是远端目录不存在，在删除单个备份时可以是已不存在。

`retryable: true` 只表示该错误未来可以用于 UI 提示或活动日志分类，不表示 `v1.5.3` 要自动重试请求。除上传同名冲突重试外，本版本不新增自动重试机制。

timeout 分类不要依赖 mock server 延迟响应。建议把分类逻辑拆成两层：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum WebDavTransportFailure {
    Timeout,
    NetworkUnreachable,
    RedirectRejected,
    Other,
}
```

`reqwest::Error` 只负责转换成 `WebDavTransportFailure`，单元测试直接断言 `WebDavTransportFailure::Timeout` 到 `WebDavErrorKind::Timeout` 的映射。这样可以测试分类逻辑，而不需要在 CI 里制造真实超时。

调用链固定为：

```text
reqwest::Error
  -> WebDavTransportFailure
  -> WebDavOperationError
  -> webdav_error_message()
```

`classify_reqwest_error()` 内部先把 `reqwest::Error` 转成 `WebDavTransportFailure`，再映射到对应的 `WebDavErrorKind`。

### 6.2 请求层拆分

建议把现有命令中的网络请求拆为两层：

```rust
pub async fn webdav_list_backups(config: WebDavConfig) -> Result<Vec<WebDavRemoteBackup>, String> {
    let client = build_webdav_http_client(Duration::from_secs(15))
        .map_err(|_| "无法初始化 WebDAV 客户端".to_string())?;
    let target = build_webdav_request_target(config)
        .map_err(|error| webdav_error_message(&error))?;
    webdav_list_backups_with_client(&client, target).await
        .map_err(|error| webdav_error_message(&error))
}
```

测试直接调用：

```rust
let target = WebDavRequestTarget::for_test(mock_server.base_url(), "SoNotes_Backups/");
webdav_list_backups_with_client(&client, target).await
```

`WebDavRequestTarget` 表示已完成 URL / 远端目录规范化的内部请求目标。生产路径通过 `build_webdav_request_target(config)` 构造；测试路径可以直接构造本地 mock target。

拆分范围：

- `propfind_request`
- `webdav_test_connection`
- `webdav_list_backups`
- `webdav_create_remote_backup`
- `webdav_download_backup`
- `webdav_delete_backup`

### 6.4 PROPFIND 解析规则

解析规则固定为：

- XML 无法解析：返回 `invalid_propfind_response`。
- `response.href` 缺失：跳过该 response。
- `href` 指向远端目录自身：跳过。
- basename 不是 `SoNotes_Backup_YYYYMMDDHHMMSS.zip`：跳过。
- `href` 中的 basename 允许先做 percent-decode，再进入远端备份文件名校验。
- percent-decode 后文件名包含路径分隔符、`..`、空字节、冒号，或解码失败：列表场景跳过该 entry，并用测试固定。
- 子状态为 2xx：作为可读备份。
- 子状态为 401 / 403：整体 PROPFIND 401 / 403 失败；单条 propstat 401 / 403 直接跳过该 entry，并在内部调试日志中记录原因。
- `getcontentlength` 缺失或非法：`size: None`。
- `getlastmodified` 缺失：`last_modified: None`。

### 6.5 本地 mock server helper

建议在 `webdav.rs` 的 `#[cfg(test)]` 区域新增轻量 helper：

```rust
struct MockWebDavServer {
    base_url: String,
}
```

能力只需覆盖测试所需最小集：

- 监听 `127.0.0.1:0`。
- 第一批只支持单请求。
- 返回一个预设响应：`status`、`headers`、`body`。
- 记录请求 `method`、`path`、`Depth`。
- 记录 `Authorization` 是否存在，但不记录完整值。

多顺序响应不要在 Commit 4 预先抽象；等 Commit 7 / Commit 8 确实需要时再最小扩展。timeout 测试不通过手写 mock server 延迟响应实现。

注意：

- 仅在测试代码中允许 `http://127.0.0.1`。
- 生产 URL 规范化仍只允许 HTTPS，保留 localhost 开发例外。
- mock helper 不进入前端、不进入生产构建。

### 6.6 前端服务边界

如果 Rust 返回结构保持不变，前端只需补少量服务测试，确认：

- 现有 `WebDavBackupService.ts` 调用不破坏。
- 错误字符串仍能被 BoardDock 展示。
- 默认不新增 `errorCode`。
- 如果确实新增可选 `errorCode`，TypeScript 类型要设为可选，避免旧调用面迁移过大，并单独提交说明。

本版本不建议重做 BoardDock 的 WebDAV UI。除非错误分类暴露到前端，否则 UI 保持现状即可。

### 6.7 下载大小上限测试边界

下载超限测试不应真的构造 1 GiB 以上的响应体。

建议把下载实现拆出内部函数：

```rust
async fn download_backup_with_limit(
    client: &reqwest::Client,
    target: WebDavRequestTarget,
    file_name: String,
    temp_root: &Path,
    max_bytes: u64,
) -> Result<WebDavDownloadResult, WebDavOperationError>
```

生产入口继续传入应用缓存目录和 `MAX_WEBDAV_BACKUP_DOWNLOAD_BYTES`，测试传入临时目录和很小的 `max_bytes`，例如 16 bytes 或 64 bytes。

`local_temp_file_error` 不通过 mock server 触发。Commit 8 应通过内部函数单元测试覆盖，例如传入不可写或不存在的临时目录，确认失败被归类为 `LocalTempFileError`，并且不生成 download token。

### 6.8 timeout 测试边界

timeout 分类测试不要使用 15s / 60s 的真实等待，也不要依赖 mock server 延迟响应。

建议方式：

- 用 `WebDavTransportFailure::Timeout` 这类内部分类输入测试映射逻辑。
- 不在 Commit 4 的 mock server helper 中加入延迟响应能力。
- 如果后续确实需要请求级 timeout 覆盖，再单独评估引入 `httpmock` / `wiremock` dev-dependency，而不是继续扩展手写 helper。
- 若必须做真实短 timeout smoke test，使用 20ms 到 100ms 级短 timeout，并且只断言分类，不断言精确耗时。

## 9. 风险与回滚

### 9.1 风险：错误分类重构扩大改动面

控制方式：

- 先只做 Rust 内部分类。
- 前端返回结构保持兼容。
- 不为了 `errorCode` 重写 BoardDock。

### 9.2 风险：mock server helper 变复杂

控制方式：

- 只支持当前测试需要的最小 HTTP 能力。
- 不做完整 WebDAV server。
- timeout 不作为继续扩展手写 helper 的理由；若确实需要请求级 timeout 覆盖，优先单独评估 `httpmock` / `wiremock` dev-dependency。
- 如果其他场景导致 helper 代码明显超过收益，再单独评估 dev-dependency。

### 9.3 风险：PROPFIND parser 行为变更影响现有列表

控制方式：

- 先用 fixture 描述目标行为。
- 保留合法 SoNotes 备份文件名过滤规则。
- 对无法确认的单条 entry 跳过，不让整个列表失败；对整体 XML 非法才失败。

### 9.4 回滚策略

如果某一批状态码分类引入回归：

- 保留 fixture。
- 回滚对应操作的分类接入。
- 先恢复到原有字符串错误路径。
- 下一小版本再继续收口。
