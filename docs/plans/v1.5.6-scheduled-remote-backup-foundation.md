# SoNotes v1.5.6 实施计划：定时远端备份基础

---

## 1. 背景

`v1.5.1` 到 `v1.5.4` 已经把备份验证、WebDAV 传输边界和系统凭据安全补齐；`v1.5.5` 又把旧 `useStore` 依赖地图与首批 Controller 入口迁移落地。按照总规划，下一步是 `v1.5.6`：**定时远端备份基础**。

本版本的核心不是新增一种备份格式，而是把现有手动远端备份能力变成可解释、可关闭、不会并发冲突的后台任务：

- 默认关闭，用户必须显式启用。
- 只上传完整备份快照，不做同步。
- 每次自动上传前必须通过 `flushNow()` gate。
- 自动、手动、退出前备份共享同一个 single-flight 约束。
- 失败只影响远端备份结果，不影响本地保存。
- 只记录最近活动结果，不做完整历史日志。

`v1.5.6` 不做远端保留策略。远端删除与保留数量控制留到 `v1.5.7`，完整活动日志留到 `v1.5.8`。

## 2. 当前代码基线

### 2.1 已有备份能力

- `src-tauri/src/backup.rs`
  - 已有 `create_local_backup`、`restore_local_backup`、`validate_local_backup`。
  - 备份包已包含 `manifest.json`、`data.json`、`attachments/`。

  - 已有系统凭据读取路径：如果前端未传 `password`，Rust 会根据已保存配置的 `credential_key` 读取系统密钥链。
  - 已有 WebDAV 临时文件启动清理。
- `src/services/backup/WebDavBackupService.ts`
  - 已有薄封装：`loadConfig`、`saveConfig`、`clearConfig`、`testConnection`、`createRemoteBackup`、`listBackups`、`downloadBackup`、`deleteBackup`。
- `src/services/storage/PersistenceFacade.ts`
  - 已有 `flushNow()`、`pause()`、`resume()`、`isPaused()`、`getStatus()`。
  - 当前手动本地 / 远端备份都通过 `flushNow()` 再进入 Rust 备份命令。
- `src/components/BoardDock.tsx`
  - 数据管理区已有 WebDAV 配置、测试连接、刷新列表、创建远端备份、删除、下载并恢复。
  - `onWebdavCreateBackup()` 当前流程为 `buildWebdavConfig()` -> `requireWebdavCredentials()` -> `flushNow()` -> `WebDavBackupService.createRemoteBackup()` -> `listBackups()`。

### 2.2 当前缺口

- 没有自动备份调度配置。
- 没有“上次自动备份结果 / 下次计划时间 / 失败原因”的状态模型。
- 手动远端备份逻辑在 `BoardDock.tsx` 内部，无法被自动触发和退出前触发复用。
- 手动远端备份、自动备份、退出前备份还没有共享 single-flight lock。
- 本地恢复 / 远端恢复期间没有全局阻止自动备份的机制。
- 当前 WebDAV 配置表单中的会话密码只存在于 `BoardDock` 内存；后台自动备份无法依赖它。
- 没有最小活动记录。用户只能看到当前面板反馈，无法判断最近一次自动备份是否成功。
- 退出菜单目前在 Rust 侧直接 `app.exit(0)`，没有给前端异步备份留出可靠流程。

### 2.3 v1.5.5 后的架构约束

`v1.5.5` 的依赖地图已经把 `BoardDock`、恢复流程、持久化路径标为高风险区域。`v1.5.6` 应避免继续把后台任务逻辑直接塞进 `BoardDock.tsx`。

本版本建议新增独立 Module：

- `RemoteBackupRunner`：统一执行一次远端备份。
- `BackupJobCoordinator`：提供 single-flight 和恢复阻塞状态。
- `ScheduledRemoteBackupService`：管理自动备份调度、静默期、下次计划时间。
- `ScheduledRemoteBackupConfigService`：保存自动备份配置和最近结果。
- `ScheduledRemoteBackupController`：React 挂载点，负责启动 / 停止调度器。

`BoardDock` 只负责配置展示、用户输入和状态展示。

## 3. 版本决策

### 3.1 自动备份只使用已保存凭据

自动备份没有用户当场输入密码的上下文，因此第一版自动备份必须满足：

- WebDAV 配置已保存。
- `passwordSaved === true`。
- 系统凭据管理器中能读取 secret。

这里必须区分两层校验：

- **启用时轻校验**：`passwordSaved === true` 只表示 `webdav-config.json` 中记录了 `password_saved` 标记且存在 `credential_key`，允许用户打开自动备份开关。
- **运行时强校验**：真正执行自动备份时仍必须通过 Rust 的凭据读取路径取得 secret。用户手动删除系统凭据、换机或重装后，`credential_key` 可能仍存在，但系统凭据管理器中的 secret 已不可读，此时应记录为 `credential` 阶段失败。

因此 `passwordSaved === true` 是自动备份的必要条件，不是系统凭据真实可读的充分条件。后台任务不得把该标记当作“凭据一定可用”。

如果用户只使用“本次会话密码 / 令牌”，仍可手动创建远端备份，但不能启用自动远端备份。

原因：

- 自动备份不能依赖 `BoardDock` 表单内存。
- 不能把会话密码复制到其他运行时模块。
- 不能为了自动化便利回退到明文持久化密码。

### 3.2 调度配置不写入 `data.json`

自动备份配置和最近结果不应写入 `AppConfig` / `data.json`。

原因：

- `data.json` 会进入 zip 备份包。
- 从旧备份恢复时，不应顺带恢复“自动备份是否开启、多久一次、最近结果”这些本机运行偏好。
- 自动备份配置属于本机设置，不属于 Note / Board 领域快照。

建议新增独立本地配置文件：

```text
webdav-scheduled-backup-config.json
webdav-scheduled-backup-state.json
```

位置沿用 WebDAV 配置风格，放在 Tauri `app_config_dir()` 下。

### 3.3 不做后台同步

所有文案和接口都使用“自动备份 / 远端备份”，不使用：

- 同步
- 云同步
- 自动拉取
- 多端合并
- 云端数据源

自动备份只上传当前本地快照。它不会下载远端备份，不会自动恢复，不会合并远端数据。

### 3.4 最小活动记录只记录最近结果

`v1.5.6` 只记录最近一次自动 / 退出前 / 手动远端备份结果，用于回答：

- 最近一次是否成功。
- 触发原因是什么。
- 失败发生在哪一步。
- 成功上传的远端文件名是什么。
- 下一次预计什么时候尝试。

完整历史列表留给 `v1.5.8`。

## 4. 目标

### 4.1 定时远端备份配置

新增自动远端备份配置：

```ts
type ScheduledRemoteBackupFrequency = '6h' | '12h' | 'daily' | 'weekly';

interface ScheduledRemoteBackupConfig {
  enabled: boolean;
  frequency: ScheduledRemoteBackupFrequency;
  quietPeriodMinutes: number;
  exitPromptEnabled: boolean;
}
```

默认值：

```ts
{
  enabled: false,
  frequency: 'daily',
  quietPeriodMinutes: 5,
  exitPromptEnabled: true
}
```

UI 第一版只需要展示固定频率选项：

- 每 6 小时。
- 每 12 小时。
- 每天。
- 每周。

`quietPeriodMinutes` 第一版可以固定为 5 分钟，不一定暴露为可调输入。

### 4.2 最近结果状态

新增最近结果状态：

```ts
type RemoteBackupTrigger =
  | 'manual'
  | 'scheduled-interval'
  | 'quiet-period'
  | 'before-exit';

type RemoteBackupStage =
  | 'config'
  | 'credential'
  | 'single-flight'
  | 'restore-blocked'
  | 'flush'
  | 'create-zip'
  | 'upload'
  | 'list-refresh'
  | 'completed'
  | 'unknown';

/**
 * WebDAV 上传命令失败归一化后的阶段（窄集合，对应 4.3 失败契约方案 A）。
 * 是 RemoteBackupStage 的子集 + 'unknown'，专用于 `WebDavUploadResult.errorStage`。
 */
type RemoteBackupErrorStage = 'credential' | 'create-zip' | 'upload' | 'unknown';

interface ScheduledRemoteBackupState {
  lastStartedAt: number | null;
  lastFinishedAt: number | null;
  lastTrigger: RemoteBackupTrigger | null;
  /** 最近一次"自动 / 退出前"成功的时间，UI 自动备份区主状态。手动备份不更新此字段。 */
  lastAutomaticSuccessAt: number | null;
  /** 最近一次"手动"成功的时间，仅供展示与调试。 */
  lastManualSuccessAt: number | null;
  lastFailureAt: number | null;
  lastFailureReason: string | null;
  lastFailureStage: RemoteBackupStage | null;
  lastRemoteFileName: string | null;
  nextRunAt: number | null;
  /**
   * 最近一次"成功上传"所覆盖的磁盘 storageUpdatedAt。
   * **触发无关**：手动 / 自动 / 退出前任一成功都更新（快照是否已备份与触发源无关）。
   * 调度的 `no_local_changes` 判断与退出前"是否有未备份变化"判断只看这个字段，
   * 因此手动备份成功后，紧接着的自动调度不会重复创建远端备份。
   */
  lastSuccessfulStorageUpdatedAt: number | null;
  /**
   * 最近一次"尝试"时捕获的磁盘 storageUpdatedAt（无论成功 / 失败 / 跳过）。
   * 仅用于诊断与调试，不参与"是否需要备份"的决策，避免失败 / 跳过的
   * 捕获值污染 `no_local_changes`。
   */
  lastAttemptCapturedStorageUpdatedAt: number | null;
  consecutiveCredentialFailures: number;
  credentialActionRequired: boolean;
}
```

**字段语义边界（对应 P1 + 手动/自动语义复审）**：早期草稿用单一 `capturedStorageUpdatedAt` 同时承担"尝试捕获"和"成功覆盖"两种语义，又用单一 `lastSuccessAt` 混用手动与自动成功，会导致误判与 UI/调度状态打架。本版本明确：
- `lastSuccessfulStorageUpdatedAt`：**触发无关**，任一成功（含手动）都写，是 `no_local_changes` 与退出前判断的**唯一快照依据**。
- `lastAttemptCapturedStorageUpdatedAt`：每次尝试都可写，仅供诊断，**绝不参与决策**。
- `lastAutomaticSuccessAt` / `lastManualSuccessAt`：**展示分离**。UI 自动备份区主状态读 `lastAutomaticSuccessAt`，手动结果读 `lastManualSuccessAt`，手动备份不污染自动备份的展示语义。

`inFlight` 只属于运行时状态，应来自 `BackupJobCoordinator` 的当前 job snapshot，不写入 `webdav-scheduled-backup-state.json`。这样应用崩溃或被系统关闭后，重启不会留下一个永远 busy 的陈旧状态。

记录不得包含：

- password / token。
- Authorization header。
- 带 userinfo 的 URL。
- 便签正文。
- 备份包正文内容。

### 4.3 统一远端备份 Runner

新增 `RemoteBackupRunner`，把当前 `BoardDock.onWebdavCreateBackup()` 中的核心流程抽出去。

建议接口：

```ts
interface RunRemoteBackupInput {
  trigger: RemoteBackupTrigger;
  config: WebDavBackupService.WebDavConfig;
  refreshRemoteList?: boolean;
}

interface RunRemoteBackupResult {
  ok: boolean;
  trigger: RemoteBackupTrigger;
  startedAt: number;
  finishedAt: number;
  stage: RemoteBackupStage;
  remoteFileName: string | null;
  error: string | null;
  /**
   * 本次尝试捕获的磁盘 storageUpdatedAt（无论结果）。
   * 调度层只在 `ok === true` 时把它写入 state 的
   * `lastSuccessfulStorageUpdatedAt`；失败 / 跳过只写
   * `lastAttemptCapturedStorageUpdatedAt`（诊断用）。
   */
  attemptCapturedStorageUpdatedAt: number | null;
}
```

Runner 固定流程：

1. 进入 `BackupJobCoordinator` single-flight。
2. 如果恢复流程或已有远端备份任务运行，返回 skipped / failed result，不创建第二个 zip。
3. 调用 `persistenceFacade.flushNow()`。
4. flush 成功后读取当前 `data.json` 的 `storageUpdatedAt`，作为本次尝试的 `attemptCapturedStorageUpdatedAt`。**可测规则（对应 P2 复审）**：读盘本身是 async 边界，无法保证"中间不让出执行权"，因此不要求事件循环级别的原子性。规则改为：
   - step3 `await flushNow()` 返回后，**紧接着** `await readDiskStorageData('data.json')` + `getLatestUpdateTimestamp`，两步之间不插入其它 await。
   - flush 成功说明 `data.json` 已落盘（Rust `save_content` 会 await `IntentQueue` worker 的 oneshot ack；`persistence.rs` 同路径批处理只写该组最后一次 Save 内容、较早 Save 复用同一 ack，所以不能用 flush 调用时刻的内存 `generationId` 当捕获值，**读磁盘是必要步骤**）。
   - **备份期间若再收到 domain change，只标记下一轮 pending，不试图保证"同一事件循环内无变化"**。这样 `attemptCapturedStorageUpdatedAt` 反映的是 flush 落盘那一刻的磁盘值；即使之后用户继续编辑，也由下一轮调度处理，不影响本次结果的正确性。
5. 调用 `WebDavBackupService.createRemoteBackup(config)`。
6. 成功时记录 `remoteFileName`。
7. 手动触发可选刷新远端列表；自动触发默认不刷新列表，避免额外网络请求。
8. 释放 single-flight。

flush 失败时不得调用 `createRemoteBackup()`。

建议在不破坏旧前端兼容的前提下扩展 `WebDavUploadResult`，增加可选的 `errorStage?: RemoteBackupErrorStage`（即 `'credential' | 'create-zip' | 'upload' | 'unknown'`，类型定义见 4.2）与 `errorCode?`。活动记录应优先使用结构化 stage/code 区分“凭据失败、创建压缩包失败、上传失败”，不要解析中文错误文案。

**失败契约定调（对应 P2 复审）**：当前 `webdav_create_remote_backup`（`webdav.rs:1848`）签名是 `Result<WebDavUploadResult, String>`，所有失败分支走 `Err(webdav_error_message(...))`、命令 reject，导致返回的 `WebDavUploadResult.success` 实际永远为 `true`，无处承载 `errorStage`。前端 `createRemoteBackup`（`WebDavBackupService.ts:116`）只是直接 `invoke`，失败会以 reject 抛出。两种改法二选一，本计划**采用方案 A**：

- **方案 A（推荐，改动集中在 Rust + Service 归一化）**：
  - Rust 对**已知操作失败**（credential / create-zip / upload，见上方映射表）改为返回 `Ok(WebDavUploadResult { success: false, error_stage: Some(...), error_code: Some(...), error: 脱敏文案, remote_file_name: None })`，不再 reject。
  - `Err(String)` 只保留给**真正意外的内部错误**（如无法构造 client、序列化失败）。
  - 前端 `WebDavBackupService.createRemoteBackup` 增加防御：`catch` 到 reject 时归一化为 `{ success: false, errorStage: 'unknown', error }`，保证 Runner 永远拿到结构化结果，不必 try/catch 解析文案。
  - 既有手动备份调用方（`BoardDock`）需同步适配：从"reject → catch 显示文案"改为"读取 `result.success` / `result.errorStage`"，但用户可见文案保持不变。
- **方案 B（不推荐）**：Rust 维持 reject，仅由 Service 的 `catch` 把 `String` 错误映射成结构化失败。问题是中文文案到 stage 的映射又回到"解析文案"，与本节"不要解析中文错误文案"矛盾，故不采用。

Runner 与活动记录只依赖 `WebDavUploadResult.success` + `errorStage`，不依赖命令是否 reject。Commit 4 的 stage 区分验收据此判定。

**Rust 侧失败分支到 stage 映射点**（`webdav_upload_backup_with_client` 内）：

| 失败点                                          | stage        | 说明                                   |
| ----------------------------------------------- | ------------ | -------------------------------------- |
| `ensure_remote_dir_exists` 失败（MKCOL 401/403）    | `credential` | 凭据错误或权限不足                     |
| `ensure_remote_dir_exists` 失败（其他 HTTP）        | `upload`     | 目录创建失败，非凭据问题               |
| `tokio::fs::metadata` / `File::open` 失败           | `create-zip` | 本地 zip 文件读取失败                  |
| HTTP 401 / 403                                  | `credential` | 上传时凭据错误                         |
| HTTP 409 / 412                                  | `upload`     | 冲突（会重试，重试耗尽后仍失败才记录） |
| 其他 HTTP 错误                                  | `upload`     | 服务端错误或网络问题                   |
| `reqwest` 传输错误                              | `upload`     | 网络连接失败                           |

工作量提示：需要在 `webdav_upload_backup_with_client` 中将各 `Err` 分支改为返回带 stage 的结构化结果，而非仅 `String`。

### 4.4 自动调度服务

新增 `ScheduledRemoteBackupService`。

职责：

- 加载自动备份配置。
- 根据固定频率计算 `nextRunAt`。
- 监听 Domain state 修改或磁盘 `storageUpdatedAt`，判断是否存在未备份变化。
- 在静默期满足后尝试触发远端备份。
- 在固定时间到达后尝试触发远端备份。
- 自动触发前校验 WebDAV 已保存凭据。
- 启动时处理已过期的 `nextRunAt`。
- 对连续凭据失败执行退避 / 自动降级。
- 更新最近结果状态。

调度触发条件：

- `enabled === true`。
- WebDAV 已保存配置且 `passwordSaved === true`。
- 当前没有远端备份 / 恢复任务运行。
- 最近一次成功备份没有覆盖当前 `storageUpdatedAt`。
- 应用不处于明显活跃编辑 / 拖拽状态，或已达到固定频率触发点。

`passwordSaved === true` 只用于调度前的轻量准入。实际上传时如果 Rust 侧无法从系统凭据管理器读取 secret，应归类为 `credential` 阶段失败，而不是简单视为 `missing_saved_credential`。`missing_saved_credential` 仅用于 WebDAV 配置本身未保存凭据标记或缺少 `credential_key` 的情况。

**连续凭据失败退避**：如果自动备份在 `credential` 阶段连续失败达到阈值（建议 N=3），调度服务应自动暂停或关闭自动备份，并把状态标记为 `credentialActionRequired: true`，提示用户“需重新保存 WebDAV 密码”。在用户重新保存凭据或重新启用自动备份前，不应每个周期继续静默重试，避免后台反复刷新 `lastFailureReason`。

**重启后的过期 `nextRunAt`**：启动时如果持久化的 `nextRunAt <= now`，不要直接立即上传。应标记存在一个待触发意图，经过静默期、single-flight gate、restore gate 与 flush gate 后补跑一次，然后重新计算下一次 `nextRunAt`。这样既不会错过关机期间到期的备份，也不会在用户刚打开应用、仍处于活跃编辑时立刻上传。

静默期不是“每次编辑后都自动上传”的触发器。v1.5.6 只允许静默期延后已经到期的固定频率任务，或延后一个已经存在的待触发意图；它不因每次编辑单独生成新的远端备份，避免在 v1.5.7 的保留策略前制造大量 zip。

第一版允许以下跳过原因：

- `disabled`
- `missing_webdav_config`
- `missing_saved_credential`
- `single_flight_busy`
- `restore_in_progress`
- `flush_failed`
- `no_local_changes`
- `app_active`
- `webdav_failed`

`app_active` 用于"用户正在编辑 / 拖拽 / 框选 / hover-panning"时延后，属于延后而非失败，应记录为可解释的延后原因，不计入用户可见的"最近失败"。

**`deferred_resource`（备份包过大延后）明确推迟到 v1.5.7（对应 P3 复审）**：总规划 9.2.7 提到"备份包过大时延后静默期备份"，但当前 `backup::create_local_backup`（`backup.rs:1601`）打包前不返回 zip 大小预估，`webdav_create_remote_backup` 也是单次 await、无预检阶段——v1.5.6 **没有具体可测的数据源**支撑这个延后判断。强行实现会引入范围摇摆。因此本版本：
- **只实现 `app_active` 一种延后**，不在 v1.5.6 的跳过原因 enum 中引入 `deferred_resource`。
- "备份包过大延后"留到 **v1.5.7**：该版本本就要做保留策略与大小 / 数量比较，并能复用 v1.5.2 的验证结果 / manifest 摘要（附件数量、体积）作为可测数据源，届时再补 `deferred_resource` 更自然。

跳过不一定算失败；用户可见最近失败只记录真正失败或需要用户处理的状态。

**`app_active` 信号源（已核查真实字段，禁止实现成空判断）**：`app_active` 必须聚合以下**已存在**的信号，缺一不可，且不得退化为恒返回 false：

- **拖拽 / 平移 / 边缘推动**：`interaction.isDragging`、`interaction.isPanMode`、`interaction.edgePush`（定义在 `viewportStore.ts:46`，并镜像于 `useStore.ts:664` 的 `interaction`）。优先订阅 `useViewportStore` 的 `interaction` selector（`viewportStore.ts:171`）。
- **粘性拖拽**：`useStore` 的 `stickyDrag.status`（`useStore.ts:650`，`status !== 'active'` 之外的拖拽中状态视为活跃）。
- **框选 / 多选进行中**：`selectedIds` 非空且正在变化（`uiStore.ts` / `useStore` 的 `selectedIds`）。
- **文本编辑**：**注意——文本输入没有 store flag**（`setIsDragging` 只加 DOM class `is-dragging`，不代表文本编辑）。编辑态需用 `document.activeElement` 判断当前聚焦元素是否为 `textarea` / `input` / `[contenteditable]`，或监听便签编辑器的 `focus` / `blur`。不能假设 store 里有 `isEditing`。

实现要求（写入 Commit 6 验收）：
- `app_active` 至少覆盖上述拖拽、平移、粘性拖拽、文本编辑四类；任一为真即视为活跃、延后静默期备份。
- 必须有测试断言：模拟 `interaction.isDragging = true` 或聚焦 textarea 时，静默期触发被延后并记录 `app_active`；全部空闲时不延后。
- 固定频率到点（interval / 过期补跑）即使 `app_active` 也只延后到静默期，不无限延后。

### 4.5 退出前提示

退出前备份不能依赖浏览器 `beforeunload` 执行异步上传，因为该事件不可靠，也不适合等待 WebDAV I/O。

建议第一版只接入可控退出路径：

- Rust 托盘 / 菜单 `quit` 不直接 `app.exit(0)`。
- 改为向主窗口发送 `remote-backup-before-quit-requested`。
- 前端收到后判断是否需要退出前备份。
- 如果不需要，调用新的 `confirm_app_quit` Tauri 命令退出。
- 如果需要，弹出确认：
  - “先创建远端备份再退出”
  - “直接退出”
  - “取消”
- 用户选择备份时，Runner 以 `before-exit` 触发远端备份。
- 成功或失败后给出短反馈，再由用户确认是否退出，或自动继续退出时必须有短超时上限。

**"是否需要退出前备份"的判断条件**（对齐总规划 9.2.3）：只有同时满足以下条件才提示退出前备份，避免每次退出都打扰用户：

- `exitPromptEnabled === true`。
- WebDAV 已保存配置且 `passwordSaved === true`（否则退出前备份也跑不起来，不提示）。
- 本地有未备份变化：当前磁盘 `storageUpdatedAt` 晚于 `lastSuccessfulStorageUpdatedAt`（只看成功字段，不看尝试字段）。
- 距上次成功远端备份已超过阈值（建议复用该用户的 `frequency`，或设一个固定下限如 30 分钟，避免刚自动备份完又提示）。

不满足时直接调用 `confirm_app_quit()` 退出，不弹对话框。

明确非目标：

- 不保证系统强制关机、进程 kill、崩溃时完成备份。
- 不在 `beforeunload` 中静默执行长时间上传。
- 不让退出流程无提示卡住。

### 4.6 数据管理区展示

WebDAV 设置页新增自动备份区域：

- 自动远端备份开关。
- 固定频率选择。
- “退出前提醒备份”开关。
- 最近一次自动 / 退出前备份结果。
- 最近失败原因。
- 最近成功远端文件名。
- 下一次计划时间。
- 是否存在退出前待备份提示（对齐总规划 9.2.5）。该项反映"本地有未备份变化、退出时会提示备份"的状态，与 4.5 的退出前判断条件一致。

手动远端备份与自动备份的状态语义（对应复审）：

- **快照覆盖触发无关**：手动备份成功也更新 `lastSuccessfulStorageUpdatedAt`（它代表"当前快照是否已备份"，与触发源无关）。这样手动备份后，自动调度的 `no_local_changes` 会正确认为快照已覆盖，不会紧接着重复创建远端备份。
- **展示分离**：手动成功写 `lastManualSuccessAt`，自动 / 退出前成功写 `lastAutomaticSuccessAt`。UI 自动备份区主状态（"最近自动备份"）只读 `lastAutomaticSuccessAt`，手动结果单独展示，手动备份**不覆盖** `lastAutomaticSuccessAt` / `nextRunAt` 的展示语义。
- BoardDock 可继续用现有 `webdavFeedback` 展示最近手动结果，或读 `lastManualSuccessAt`，但不要让手动备份把"下一次自动备份"的判断变得含混。

当 `passwordSaved === false` 时：

- 自动备份开关不可开启，或开启时立即提示需要先把密码保存到系统凭据管理器。
- 手动远端备份仍可使用本次输入密码。

文案示例：

- “自动远端备份已关闭”
- “下次尝试：今天 18:30”
- “最近成功：SoNotes_Backup_20260613153000.zip”
- “最近失败：无法从系统凭据管理器读取密码，请重新输入并保存”
- “自动备份已暂停：无法读取已保存的 WebDAV 密码，请重新保存密码后再启用”

禁止文案：

- “已同步”
- “云端已更新”
- “自动同步中”

### 4.7 后台任务资源边界

对齐总规划 9.2.7。自动备份涉及 zip 创建、图片文件读取、hash 校验与 WebDAV 上传，即使主要由 Rust / Tauri 侧执行，也不得影响前端 UI 线程与画布交互。

要求：

- **重 I/O 不阻塞 async runtime / UI 线程**：zip 创建、hash 校验已在 blocking 线程（`create_local_backup` 用 `tokio::task::spawn_blocking`，见 6.4 核查结论）；WebDAV 上传是异步 I/O（`webdav_upload_backup_with_client`）。本版本无需额外迁移，但要在验收中保留"不致前端掉帧"这条回归。
- **活跃交互期间不抢占资源**：用户正在拖拽、框选、hover-panning 或编辑文本时，静默期备份不触发（对应 `app_active` 延后，信号源见 4.4）。
- **过大备份延后**：总规划 9.2.7 提到的"备份包过大时延后"留到 v1.5.7（v1.5.6 无可测的大小预估数据源，决策见 4.4）。v1.5.6 只实现 `app_active` 延后。

**前端状态更新节流的代码边界澄清**：总规划 9.2.7 要求"上传进度 / 日志更新需要节流，避免造成 React 高频更新"。但当前 `webdav_create_remote_backup`（`webdav.rs:1848`）是**单次 `await`、不 emit 任何上传进度事件**，前端拿到的是一个最终 `WebDavUploadResult`，没有逐字节 / 逐块进度流。因此：

- 本版本**不存在上传进度事件源**，不需要、也不应为此新增进度 emit 机制（那会扩大范围）。
- 真正的 React 高频更新风险来自 **scheduler 的状态订阅 / snapshot 变更**：`subscribe(listener)` 与 `getSnapshot()`（6.5）在每次 `notifyDomainChanged`、timer tick、阶段切换时都可能通知订阅者。
- 节流要求落在订阅侧：`ScheduledRemoteBackupController` 与 BoardDock 订阅 scheduler snapshot 时，应避免每次 domain 变化都触发 React 根更新。建议 snapshot 变更做去抖 / 合并，或只在用户可见字段（最近结果 / 下次时间 / 待备份提示）真正变化时才 setState。
- `notifyDomainChanged` 本身会被高频调用（每次编辑），scheduler 内部应只记录"最后修改时间"等轻量值、用 timer 驱动决策，不得每次 domain 变化都触发一次 React 渲染或一次磁盘读。

### 6.5 调度服务

新增：

```text
src/services/backup/ScheduledRemoteBackupService.ts
```

建议接口：

```ts
function startScheduledRemoteBackup(options): ScheduledRemoteBackupHandle

interface ScheduledRemoteBackupHandle {
  stop(): void;
  notifyDomainChanged(storageUpdatedAt?: number): void;
  requestRun(trigger: RemoteBackupTrigger): Promise<RunRemoteBackupResult | null>;
  getSnapshot(): ScheduledRemoteBackupSnapshot;
  subscribe(listener): () => void;
}
```

调度策略：

- 固定频率用 `setTimeout` 计算下一次触发，不用 `setInterval`，避免任务耗时导致重入。
- 启动时如果持久化的 `nextRunAt` 已经过期，创建一个待触发意图，经静默期与各 gate 通过后补跑一次，再重新排程。
- 静默期用最后一次 Domain 修改时间计算，但只在固定频率已到期或已有待触发意图时生效。
- 应用处于活跃输入、拖拽、框选、hover-panning 时不触发静默期备份。
- 固定频率到点但应用活跃时，可延后到静默期。
- 页面不可见时可以触发，但必须先通过 single-flight 与 flush gate。
- 网络失败不影响本地保存，只更新最近失败。
- 凭据阶段连续失败达到阈值（建议 N=3）后，自动暂停或关闭调度，并标记需要用户重新保存密码。

Domain 修改来源：

- 优先订阅 `useDomainStore`，利用 `legacyDomainBridge` 的镜像状态。
- 不新增旧 `useStore` 订阅。
- 记录 `storageUpdatedAt` 时以 flush 后磁盘 `data.json` 为准。

**`storageUpdatedAt` 语义声明**：`storageUpdatedAt`（`StorageService.ts:179`）是"写盘时刻"而非内容指纹。每次 `serializeDomainState` 落盘时用 `Date.now()` 刷新，包括纯主题切换、看板视口移动等非便签内容变化。因此 `no_local_changes` 判断的是"自上次成功备份以来是否有过写盘"，粒度粗于"便签内容是否变化"。**v1.5.6 接受这种粗粒度**（推荐，简单可靠），不排除 config-only 变化。如果未来需要内容指纹级别的变化检测，需额外实现，不在本版本范围内。

**`getLatestUpdateTimestamp` 复用**：`tauriPersistence.ts:21` 已有 `getLatestUpdateTimestamp(data)`，内部处理了 `storageUpdatedAt` 缺失时回退到 `getLegacyStorageUpdatedAt(notes)` 的兼容逻辑。Runner 的 step4 和 scheduler 的 `no_local_changes` 判断应点名复用 `readDiskStorageData('data.json')`（`BoardDock` 已在用，见 `BoardDock.tsx:361`）+ `getLatestUpdateTimestamp`，而非直接读裸 `storageUpdatedAt` 字段，避免漏掉 legacy 回退。

**store 双轨制时序**：`PersistenceController.tsx:8` 从旧 `useStore.getState()` 取状态落盘，而 `ScheduledRemoteBackupController` 订阅新 `useDomainStore`。两者经 `legacyDomainBridge` 镜像，链路为：`domainStore 改` → `镜像到 useStore` → `StorageService bridge 回调` → `debounce 2s` → `写盘`。因此 controller 收到 `notifyDomainChanged` 的时刻，磁盘 `storageUpdatedAt` **尚未更新**。domain 订阅仅作"该尝试了"的**触发信号**，真正的 `attemptCapturedStorageUpdatedAt` **必须在 `await flushNow()` 之后读磁盘**，不能用订阅回调里的时间。flush 的 debounce（2s）+ 重入合并（`StorageService.ts:250` 的 `do-while(diskPending)`）保证 flush 完成后磁盘是最新的，对 Runner 有利。实现规则见 4.3 step4 的可测规则：`await flushNow()` 后紧接着读磁盘、两步间不插入其它 await；备份期间再来的 domain change 只标记下一轮 pending，不追求同一事件循环内无变化。

**凭据失败处理**：scheduler 启用前只做 `passwordSaved === true` 的轻校验；Runner 实际执行时如果 Rust 侧 `resolve_webdav_operation_secret` / `resolve_operation_secret_core` 无法读取系统凭据，应返回 `credential` 阶段失败并递增 `consecutiveCredentialFailures`。达到阈值后设置 `credentialActionRequired`，暂停后续自动触发，直到用户重新保存 WebDAV 密码或重新启用自动备份。手动远端备份仍可使用本次输入密码，不受该退避状态影响。

**跨窗口场景（已核查当前机制）**：撕下窗口（detached note）的数据流是**单向的、主窗口 → detached 推送的只读快照**：

- `detachedNoteSnapshotSync.ts` 中，主窗口订阅 `useStore`，通过 `emitTo(detached-note-<id>, SNAPSHOT, ...)` 把便签快照推给 detached 窗口（节流 100ms）。
- `DetachedNoteWindow.tsx` 只 `emit` `READY` / `LOCATE` 事件，**没有任何内容编辑回写到主窗口 domain**（当前 detached 窗口是只读展示，不调用 `updateNote` / `updateTitle`）。
- 因此 **v1.5.6 不存在"detached 窗口编辑绕过主窗口 scheduler"的问题**：所有真实 domain 变更都发生在主窗口 `useStore` / `useDomainStore`，scheduler 订阅主窗口 domain 即可捕获全部变化。

验收条件（写入 Commit 7）：
- 不需要为 detached 窗口新增跨窗口编辑→scheduler 的通知通道。
- 但必须加一条**回归断言**：确认 detached 窗口仍是只读快照（无 `updateNote` / `updateTitle` 等 domain 写入路径）。**如果未来版本让 detached 窗口可直接编辑**，则编辑必然要先回写主窗口 domain（否则无法持久化），届时 scheduler 自然能通过主窗口 domain 订阅捕获；需要在那个版本补充"detached 编辑→主窗口 domain→notifyDomainChanged"的链路测试。本版本只需声明该前提并留回归断言守住。

- 退出前备份不应无限等待。

## 8. 风险与防护

### 8.1 用户误解为同步

风险：

- 自动上传容易被理解为云同步。

防护：

- UI 只使用“自动远端备份”。
- 说明“不自动下载，不自动恢复”。
- 不在任何文案里使用“同步”。

### 8.2 后台任务依赖会话密码

风险：

- 自动备份在 BoardDock 关闭后没有密码上下文。

防护：

- 自动备份只允许使用系统凭据保存模式。
- 会话密码只用于手动备份。
- 缺少 saved credential 时不触发自动上传。

### 8.3 并发创建 zip

风险：

- 手动备份、自动备份、退出前备份同时创建 zip 或上传。

防护：

- 所有入口共享 `BackupJobCoordinator`。
- 自动触发不排队无限任务。
- 恢复期间阻止自动备份。

### 8.4 flush 与备份快照不一致

风险：

- 自动备份上传旧磁盘快照。

防护：

- Runner 内统一 `flushNow()` gate。
- flush 失败直接结束，不调用 Rust 远端上传。
- 成功后记录 `lastSuccessfulStorageUpdatedAt`（失败 / 跳过不写该字段，避免污染 `no_local_changes`）。

### 8.5 退出前备份阻塞关闭

风险：

- WebDAV 上传慢，退出流程卡住。

防护：

- 不在 `beforeunload` 里做异步上传。
- 只在可控退出路径提示用户。
- 用户始终可以选择直接退出。

### 8.6 活动记录泄漏敏感信息

风险：

- 最近失败原因可能包含凭据或 header。

防护：

- 继续复用 WebDAV 脱敏错误分类。
- 写入最近状态前做脱敏校验。
- 测试覆盖 password / token / Authorization 不出现在 state 文件。

### 8.7 后台任务影响前端流畅度

风险：

- zip 创建 / hash / 上传或频繁的 scheduler 状态通知拖慢画布交互、造成掉帧。

防护：

- 重 I/O 已在 blocking 线程 / 异步 I/O（见 4.7、6.4），本版本不新增上传进度事件源。
- 活跃交互期间延后静默期备份（`app_active`）。
- scheduler snapshot 订阅做合并 / 去抖，`notifyDomainChanged` 只更新轻量值、由 timer 驱动决策，不每次编辑触发 React 根更新或磁盘读。

## 9. 验收标准

`v1.5.6` 完成时应满足：

- 自动远端备份默认关闭。
- 用户必须显式开启自动远端备份。
- 未保存系统凭据时，不能启用自动远端备份。
- 开启后可按固定频率或静默期策略触发远端备份。
- 自动触发前必须通过 `persistenceFacade.flushNow()`。
- flush 失败时不调用远端上传。
- 自动备份、手动远端备份、退出前备份不会并发创建 zip 或并发上传。
- Rust 创建 zip / hash 阶段运行在 blocking 线程，不长时间占用 async runtime。
- zip 创建、hash 校验和 WebDAV 上传不导致前端明显掉帧或假死。
- scheduler 的 snapshot 订阅与 `notifyDomainChanged` 不形成高频 React 根更新（节流落在订阅侧，详见 4.7）。
- 本地恢复 / 远端恢复期间不会触发自动备份。
- 最近结果展示最近成功、最近失败、触发原因、远端文件名和下一次计划时间。
- 数据管理区能展示"是否存在退出前待备份提示"。
- 最近活动记录不包含凭据、Authorization header 或便签正文。
- 退出前备份不会无提示长时间阻塞关闭流程。
- 上传失败不影响本地保存。
- 不自动下载、不自动恢复、不删除远端旧备份。
- 用户可见文案不使用“同步”。

## 10. 与后续版本的关系

### v1.5.7：远端备份保留与清理

`v1.5.6` 上传成功后只记录结果，不删除任何远端文件。`v1.5.7` 再基于最近健康备份、异常下跌保护和规范命名规则实现保留策略。

### v1.5.8：完整活动日志与可观测性

`v1.5.6` 的最近结果状态应作为 `v1.5.8` 活动日志的种子，但不在本版本扩展为历史列表。

### v1.5.9：v1.6.0 体验基线

`v1.5.9` 可把自动备份加入关键流程冒烟清单：

- saved credential 自动备份。
- flush 失败阻断。
- 手动备份与自动备份 single-flight。
- 恢复期间自动备份跳过。
- 退出前提示不阻塞。
