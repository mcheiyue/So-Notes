# SoNotes v1.5.7 实施计划：远端备份保留与清理

---

## 1. 背景

`v1.5.6` 已经把定时远端备份的调度、静默期、单飞控制和最近结果状态跑通了。下一步不再是“能不能上传”，而是“上传之后怎么把 WebDAV 目录控制住，同时不误删健康旧备份”。

`v1.5.7` 的目标很明确：

- 只清理 SoNotes 自己生成、命名严格规范的远端备份包。
- 提供最近 `N` 个保留策略，默认不自动清理。
- 自动清理前要先做健康判断，防止坏的新备份把旧备份清掉。
- 手动清理要先预览，再确认。
- 清理失败不能影响本地保存，也不能把一次成功备份改成失败。

这版依然不做同步，不做合并，不碰无关远端文件。

## 2. 当前代码基线

### 2.1 已有可复用能力

- `src-tauri/src/backup.rs`
  - 已有 `BackupSummary` 和 `BackupValidationResult.summary`。
  - 已有恢复前验证能力，说明“摘要”这条数据链已经存在。
  - `build_summary()` 当前是 `backup.rs` 内部私有函数，主要在验证 / 恢复检查路径里使用；`v1.5.7` 需要在备份创建路径内复用它，而不是让 `webdav.rs` 重新解析 zip。
- `src-tauri/src/webdav.rs`
  - 已有 `validate_remote_backup_filename()`，严格校验 `SoNotes_Backup_YYYYMMDDHHMMSS.zip`。
  - 已有 `generate_current_remote_backup_filename()`，但没有“从文件名解析时间戳”的函数。
  - 已有 `webdav_list_backups()` 和 `webdav_delete_backup()`。
  - `filter_backup_entries()` 已经会过滤目录、非 2xx 条目和非规范命名文件。
- `src-tauri/src/scheduled_backup.rs`
  - 已有定时备份配置和最近状态的本地配置文件落盘。
  - 配置 / 状态都放在 `app_config_dir()` 下，和 `data.json` 分开。
- `src/services/backup/ScheduledRemoteBackupService.ts`
  - 已有自动远端备份调度、静默期、最近成功 / 失败 / 下次计划时间。
  - 已有 `before-exit` 触发路径。
- `src/services/backup/WebDavBackupService.ts`
  - 已有 `listBackups()` 和 `deleteBackup()` 的前端封装。
- `src/components/BoardDock.tsx`
  - 已有 WebDAV 列表、刷新、删除、创建远端备份入口。
  - 已有定时备份设置区，适合继续扩展保留策略。

### 2.2 当前缺口

- 没有远端保留策略。
- 没有“最近健康备份基线”的状态。
- 没有断崖式下跌保护。
- 没有清理预览，也没有批量删除流程。
- `webdav_create_remote_backup()` 的成功结果还没把摘要和 zip 大小完整带回前端。
- `BackupResult` 当前只有 note / board / attachment 数量，没有 zip 文件大小；`BackupSummary.imageFileTotalBytes` 是图片附件总字节数，不能替代 zip 体积。
- 现有 `lastFailureReason` 只适合备份失败，不适合记录清理失败。

### 2.3 代码边界

- 删除安全仍然要以 Rust 的严格文件名校验为最后一道门。
- 保留策略应该复用现有 WebDAV 列表结果，不自己重新爬目录。
- 摘要应来自本次备份创建链路，不要为了清理再把新 zip 解压一遍。
- 这版只扩展自动备份相关配置 / 状态，不把保留配置塞进 `data.json`。

## 3. 版本决策

### 3.1 默认关闭自动清理

第一版默认值建议是 `不自动清理`。

原因很简单：这版第一次引入“删除远端文件”行为，默认值比省空间更重要。用户启用自动备份后，先确保能稳定上传，再决定是否让系统自动删旧包。

### 3.2 只清理严格命名备份

只允许清理以下格式：

```text
SoNotes_Backup_YYYYMMDDHHMMSS.zip
```

不清理：

- 用户自己放进去的文件。
- 不符合命名规则的 zip。
- 子目录。
- 非 zip 文件。

### 3.3 断崖式下跌保护优先

自动清理前，要比较“本次新备份”与“最近健康备份基线”。

若新备份出现明显下降，就直接停掉自动清理，不碰旧备份。重点看：

- note 数量。
- board 数量。
- image note 数量。
- 图片文件数量。
- zip 体积。

可参考的初始规则：

- 基线 note 数 `>= 10` 时，本次 note 数少于基线的 30%。
- 基线 note 数在 `5..=9` 时，本次 note 数降到 `0` 或 `1`。
- 基线 note 数 `< 5` 时，不使用比例阈值，只在本次 note 数为 `0` 且 board 数也异常接近空时触发。
- 基线 board 数 `>= 3` 时，本次 board 数少于基线的 50%；基线 board 数 `>= 2` 且本次为 `0` 时也触发。
- 基线图片文件数 `>= 5` 时，本次图片文件数少于基线的 30%。
- zip 体积只有在两次都能拿到 `zipSizeBytes` 且基线 zip `>= 1 MiB` 时参与判断；单独 zip 变小不触发，必须同时伴随 note / board / 图片数量下降。

触发后：

- 本次备份保留为可疑备份。
- 不执行自动清理。
- 状态区提示警告。
- 用户可以手动确认“我知道数据量下降，允许以后以此为健康基线”。

### 3.4 自动清理触发时机

本版建议把自动清理接在“自动备份成功”之后，优先覆盖 `scheduled-interval` 和 `quiet-period` 两类自动触发。

`before-exit` 备份先只保证上传成功，不在退出路径里额外跑远端 delete，避免把退出流程拉长。

实现时不要依赖 `ScheduledRemoteBackupState.lastTrigger` 判断是否是 `before-exit`。`ScheduledRemoteBackupService.runBackup(trigger)` 已经持有本轮触发源，应该直接用当前函数参数判断：

- `trigger === 'scheduled-interval' || trigger === 'quiet-period'` 才允许自动清理。
- `trigger === 'manual' || trigger === 'before-exit'` 不触发自动清理。
- 备份失败时不进入清理分支，因此不需要通过“最近一次 state”倒推触发源。

### 3.5 保留数量变更不立即自动删除

用户修改保留数量时，只保存配置，不立即发起自动删除。

原因：

- 降低保留数量可能一次性删除很多远端文件，不能藏在配置保存动作里发生。
- 自动清理必须建立在一次成功的新自动备份之后。
- 想立刻清理的用户可以走手动预览和确认流程。

因此场景“从保留 10 个改为保留 5 个，远端当前有 12 个”时：

- 保存配置后不立即删除 7 个。
- 下一次 `scheduled-interval` / `quiet-period` 自动备份成功后，按新策略尝试清理。
- 用户也可以手动点“预览清理”，确认后立即按新策略清理。

### 3.6 手动清理先预览

如果用户主动清理旧备份，必须先预览，再确认。

预览至少要给出：

- 将删除多少个备份。
- 最旧要删除的时间。
- 最新保留的时间。
- 是否存在异常下跌警告。

### 3.7 健康基线确认规则

健康基线确认只把“当前这一次可疑备份”设为新基线，不取最近 N 次平均。

要求：

- UI 必须二次确认，明确提示“确认后后续自动清理会以此备份数量为健康基线”。
- 确认后写入该备份的 `remoteFileName`、摘要、`zipSizeBytes`、`confirmedAt`。
- 如果下一次备份相对新基线继续断崖下降，仍然再次触发保护。
- 被确认的基线仍然只保存摘要和文件名，不保存便签正文或凭据。

健康基线的自动更新顺序必须固定：

- 无健康基线时：第一次成功的自动备份只初始化健康基线，不执行自动清理。
- 有健康基线且本次不异常：先把本次备份更新为健康基线，再按保留策略清理。
- 有健康基线且本次异常：不更新健康基线，写入待处理异常警告，不执行自动清理。
- 有待处理异常警告时：后续自动清理继续暂停，直到用户确认新基线或手动清除该警告。

### 3.8 无历史基线时的行为

如果 `retention.healthBaseline === null`，自动清理不能运行。

首次成功自动备份只做两件事：

- 写入健康基线。
- 记录本次清理结果为 `skipped_no_baseline` 或同等语义。

这不是失败，也不需要报错。用户仍可通过手动预览和确认执行清理；手动清理会展示“当前还没有历史健康基线，自动断崖保护从下一次自动备份开始生效”。

### 3.9 保留策略与保护对象的协同

保留策略按“先选最近 N 个，再强制加入保护对象”的方式计算。

保护对象包括：

- 当前刚上传成功的备份。
- 当前健康基线文件。
- 待处理异常警告对应的可疑备份。

计算规则：

- 先从所有严格命名备份里选出最近 `N` 个。
- 再把保护对象并入保留集合。
- 删除候选 = 严格命名备份 - 保留集合。
- 保护对象不一定计入 `maxKeepCount` 上限；为安全起见，实际保留数量可以临时超过 `N`。
- 有待处理异常警告时，自动清理直接暂停；手动清理预览仍可计算，但必须排除保护对象并显示警告。

因此，当健康基线或可疑备份已经落在最近 `N` 个之外时，它们不会被自动删除。比严格卡住数量更重要的是保住用户可回退的安全点。

### 3.10 摘要复用优先

自动清理的健康判断应复用本次备份创建链路里已经拿到的摘要和 zip 大小，不要为了算保留策略再重新解压新包。

## 4. 技术设计

### 4.1 配置 / 状态扩展

建议继续复用：

```text
webdav-scheduled-backup-config.json
webdav-scheduled-backup-state.json
```

不另起第三份 retention 文件。

配置里新增保留策略字段，默认关闭。状态里新增一个轻量 retention 子状态，至少包含：

- 最近健康基线摘要。
- 最近一次清理结果。
- 最近一次异常警告。

Rust 侧必须显式处理旧 JSON 默认值，不然新增字段后老配置会因为缺字段反序列化失败。

建议做法：

- 为新增 enum / struct 提供 `Default`。
- 在 `ScheduledRemoteBackupConfigFile` 新字段上使用 `#[serde(default)]`。
- 在 `ScheduledRemoteBackupState` 或其新增 retention 子字段上使用 `#[serde(default)]`。
- 如果字段很多，优先给内部 file struct 做兼容层，再转换成前端消费结构。

示意：

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
struct ScheduledRemoteBackupConfigFile {
    enabled: bool,
    frequency: ScheduledRemoteBackupFrequency,
    quiet_period_minutes: u32,
    exit_prompt_enabled: bool,
    #[serde(default)]
    retention_policy: RemoteBackupRetentionPolicy,
}
```

测试必须覆盖“旧 JSON 没有 `retentionPolicy` 也能成功加载并得到默认关闭策略”。

### 4.2 上传摘要回传

`backup.rs` 里已经能构建 `BackupSummary`，`v1.5.7` 应该把它从 `create_local_backup_inner()` 往上带出去，再透传到 `webdav_create_remote_backup()` 的成功结果。

建议补充：

- 本次备份摘要。
- 本次 zip 文件大小 `zipSizeBytes`。

实现要点：

- `build_summary()` 不从 `webdav.rs` 调用。它留在 `backup.rs` 内，在 `create_local_backup_inner()` 已经拥有 `storage_data` 和 `manifest` 的位置调用。
- 建议在 `BackupResult` 上新增 `summary: Option<BackupSummary>` 和 `zipSizeBytes: Option<u64>`。
- `create_local_backup_inner()` 在构造 `manifest` 后、返回 `BackupResult` 前调用 `build_summary(&manifest, &storage_data)`。
- `zipSizeBytes` 从最终 zip 路径的 `std::fs::metadata(&resolved_path).len()` 获取。
- 不把 `BackupSummary.imageFileTotalBytes` 当 zip 大小使用；它只表示附件图片总字节数。
- 远端上传成功后，将摘要和 `zipSizeBytes` 一起放进 `WebDavUploadResult`。

这样前端做断崖判断时，不用再回头解压新 zip。

### 4.3 保留策略引擎

新增一个纯策略模块，专门做这些事：

- 解析严格的 SoNotes 远端备份文件名。
- 按时间顺序选出保留 / 删除候选。
- 计算预览结果。
- 比较新摘要和健康基线，给出异常原因。

这个模块只处理数据，不直接发网络请求。

必须新增文件名解析函数。现有代码只有校验和生成，没有解析时间戳；保留策略不能用字符串随便切完就排序。建议前端策略模块提供：

```ts
interface ParsedRemoteBackupFileName {
  readonly fileName: string;
  readonly timestampText: string;
  readonly createdAt: number;
}

function parseRemoteBackupFileName(
  fileName: string,
): ParsedRemoteBackupFileName | null;
```

要求：

- 严格匹配 `SoNotes_Backup_YYYYMMDDHHMMSS.zip`。
- 拒绝非法月份、日期、小时、分钟、秒。
- `createdAt` 使用本地时区或固定解析策略，但必须在测试中写死，避免按运行环境漂移。
- `proposeRetentionCleanup()` 只用解析出的 `createdAt` 排序，不依赖 WebDAV `lastModified`。
- 同一秒文件名冲突时，以 `fileName` 做稳定排序兜底。

建议核心函数：

```ts
function proposeRetentionCleanup(input: {
  backups: readonly WebDavRemoteBackup[];
  policy: RemoteBackupRetentionPolicy;
  protectedFileNames: readonly string[];
}): RemoteRetentionPreview;

function detectBackupCliffDrop(input: {
  baseline: RemoteBackupHealthBaseline;
  candidate: RemoteBackupHealthBaseline;
}): RemoteRetentionAnomaly | null;
```

`proposeRetentionCleanup()` 遇到无基线不负责报错；无基线跳过属于自动清理编排层的职责。

### 4.4 自动清理执行

真正的删除流程可以单独做成执行器，职责是：

- 调 `listBackups()`。
- 再次过滤严格命名文件。
- 按时间排序。
- 留下最近 `N` 个，删除其余。
- 顺序删除，遇到意外失败就停。
- 删除前后都给出明确结果。

这里不要把删除逻辑塞回 `BoardDock`。

并发锁策略：

- 前端清理执行器复用 `BackupJobCoordinator`，新增 job kind：`remote-retention-cleanup`。
- 清理获取不到 single-flight 时直接跳过或返回 busy，不排队。
- 自动清理和手动清理都走同一个执行器，因此不会同时删除。
- 清理不复用 Rust 侧 `webdav_create_backup_lock()`。那个锁只保护 create zip + upload；保留清理通过前端 single-flight 避免与备份 / 恢复并发。
- 删除前 Rust 侧仍然由 `webdav_delete_backup()` 的 `validate_remote_backup_filename()` 做最后校验。

如果未来需要抵御绕过前端的并发 Tauri 调用，可以在 Rust 侧再引入独立 `webdav_retention_cleanup_lock()`。但 `v1.5.7` 不新增一个“批量删除 Rust command”时，前端 single-flight + 单文件 delete 校验已经足够。

批量删除性能取舍：

- 第一版保留 TS 层顺序调用 `webdav_delete_backup`，因为保留策略通常只删除个位数到几十个文件，IPC 开销可接受，而且能复用现有鉴权、错误分类和文件名校验。
- 不并发 delete。并发删除会让失败位置和部分成功结果更难解释。
- 如果后续真实场景出现一次删除上百个备份的性能问题，再新增 Rust 内部批量 helper，例如 `pub(crate) webdav_delete_backups_with_client(...)`，复用同一个 reqwest client 和认证上下文。
- 本版不要求把 `webdav_delete_backup_with_client()` 暴露给前端；它可以继续作为 Rust 内部测试 / 单文件删除 helper。

批量删除结果不复用现有 `WebDavCleanupResult`。现有 `WebDavCleanupResult` 对应下载 token 本地清理，语义太窄。保留策略新增自己的结果类型，例如：

```ts
interface RemoteRetentionCleanupResult {
  readonly success: boolean;
  readonly policy: RemoteBackupRetentionPolicy;
  readonly attemptedCount: number;
  readonly deletedCount: number;
  readonly missingCount: number;
  readonly retainedCount: number;
  readonly stoppedAtFileName: string | null;
  readonly failedFileName: string | null;
  readonly error: string | null;
}
```

删除错误处理：

- 已删除文件算成功，不能回滚。
- `404` 按幂等成功处理，记入 `missingCount`。
- `401` / `403` / `423` / `5xx` / 网络错误停止后续删除，返回 `success: false`。
- 结果里必须保留 `deletedCount` 和 `failedFileName`，让 UI 能说明“已删除多少、在哪个文件停止”。

这里的 `404` 同时覆盖“列表之后、删除之前，远端文件被其他客户端删掉”的竞态：不算失败，不中断清理。

实现边界：

- 不新增批量删除 Rust command。
- TS 层 `RemoteBackupRetentionService` 调用已有 `WebDavBackupService.deleteBackup(config, fileName)` 循环删除。
- Tauri command 仍然是现有的 `webdav_delete_backup`，参数仍是 `{ config, remoteFileName }`。
- `RemoteRetentionCleanupResult` 是前端 service 的结果类型；若未来把批量清理下沉 Rust，再补同名 Rust struct 和 command。
- 保留策略引擎不直接调用 Rust 私有 `filter_backup_entries()`。它只消费 `webdav_list_backups()` 已经返回的 `WebDavRemoteBackup[]`，再做一层前端严格解析与排序。

### 4.5 状态与失败语义

清理失败不能覆盖“本次备份成功”的语义。

建议把清理结果单独记到 retention 子状态里，而不是复用 `lastFailureReason`：

- 备份成功还是备份成功。
- 清理失败只是清理失败。
- 可疑备份只是可疑备份，不自动更新为健康基线。

待处理异常警告必须持久化到 `webdav-scheduled-backup-state.json`，应用重启后仍然可见。建议字段：

```ts
interface RemoteRetentionWarning {
  readonly kind: 'cliff-drop';
  readonly suspiciousRemoteFileName: string;
  readonly baselineRemoteFileName: string | null;
  readonly reasonCodes: readonly RemoteRetentionAnomalyCode[];
  readonly createdAt: number;
}
```

只要该字段存在，自动清理暂停。用户确认后，将 suspicious 备份写入 `healthBaseline`，并清空 `pendingWarning`。

### 4.6 BoardDock 接线

WebDAV 设置区新增保留策略选择和警告展示：

- 自动清理开关 / 保留数量选择。
- 最近健康基线提示。
- 异常下跌警告。
- “设为健康基线”确认入口。
- 手动“预览清理” / “清理旧备份”入口。

按钮和列表操作要有独立 busy 态，避免和创建远端备份、刷新列表、单个删除混在一起。

保留数量变更后只显示“新策略将在下次自动备份成功后生效，可手动预览并立即清理”，不自动执行删除。

异常警告展示位置：放在定时备份设置区的最近结果状态下方、手动清理按钮上方。这样用户在调整保留策略前会先看到“当前自动清理暂停”的原因。

### 4.7 测试策略

重点回归这几类：

- 旧配置 / 旧状态 JSON 还能正常加载。
- 严格命名以外的文件永远不会进入删除候选。
- 摘要回传正常，清理不需要再解压新 zip。
- 自动清理失败不会把备份结果改成失败。
- 可疑备份不会自动成为新基线。
- 手动预览只展示数量和时间，不展示内容。

---

## 5. 非目标

- 不做同步语义。
- 不做内容合并。
- 不做递归删除。
- 不删除无关远端文件。
- 不自动恢复清理前的远端文件。
- 不把 cleanup 设计成一个独立的云端生命周期系统。
- 不在这版里做复杂日历保留策略。

## 7. 风险与防护

### 7.1 旧配置加载失败

新增字段如果没有默认值，老 JSON 会直接炸。

防护：

- Rust 侧用默认值兜底。
- TS 默认对象同步补齐。
- 增加旧文件兼容测试。

### 7.2 误删健康旧备份

这是最大风险。

防护：

- 默认不自动清理。
- 只清理严格命名文件。
- 断崖判断失败就停。
- 可疑备份不自动覆盖基线。

### 7.3 小样本误判

基线样本太小的时候，比例阈值容易抖。

防护：

- 基线 note 数 `< 5` 时不使用比例阈值。
- 基线 note 数 `5..=9` 时只在本次降到 `0` 或 `1` 时触发。
- 基线 zip `< 1 MiB` 时 zip 体积不参与断崖判断。
- 先保守停清理，不急着自动删。

### 7.4 清理拖慢交互

删多个远端文件会有网络 I/O。

防护：

- 全部走异步流程。
- UI 只显示状态，不同步阻塞渲染。
- 预览只算本地列表，不再额外解压。

### 7.5 状态语义混淆

清理失败不应看起来像备份失败。

防护：

- 备份结果和 retention 结果分开记。
- UI 文案也分开显示。

## 8. 验收标准

- 保留策略只作用于严格命名的 SoNotes 备份包。
- 上传失败不会触发远端清理。
- 新备份出现明显大小 / 数量断崖下降时，不会自动清理旧备份。
- 用户未确认新健康基线前，可疑备份不会成为自动清理依据。
- 清理前预览能给出数量和时间边界。
- 修改保留数量不会立即删除，除非用户走手动预览并确认。
- 批量删除出现部分失败时，结果能说明已删除数量、已不存在数量和失败文件。
- 清理失败不会影响本地保存，也不会把备份成功状态改掉。
- 清理过程不会让前端 UI 假死。
- 删除操作不包含同步或合并语义。
