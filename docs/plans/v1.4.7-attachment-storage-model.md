# SoNotes v1.4.7 实施计划：附件 / 图片存储底层模型

---

## 1. 背景

`v1.4.6` 已经完成撕下便签 Tauri 独立窗口，SoNotes 的下一阶段从桌面窗口体验转向本地数据模型演进。根据后续路线图，`v1.4.7` 的主题是建立附件 / 图片能力所需的底层存储模型，为 `v1.4.8` 的图片入口与附件一致性、`v1.4.9` 的本地 zip 备份 / 恢复打基础。

当前 SoNotes 的持久化数据仍以 `data.json` 为核心：`StorageData` 包含 `notes`、`boards`、`currentBoardId` 与 `config`。所有 **Note（便签）** 当前只保存标题、正文、颜色、位置、尺寸偏好、折叠状态和 `deletedAt` 等字段，不包含附件引用。导入、导出与恢复流程当前也只处理 JSON 文本，不处理二进制文件。

本版本的重点不是让用户立刻粘贴或预览图片，而是先建立可演进、可兼容、可备份的本地附件存储边界，避免未来把图片 base64 直接写入 `data.json`。

---

## 2. 目标

### 2.1 建立附件引用模型

- 为 **Note** 增加可选附件引用字段。
- 新增 `AttachmentRef` 类型，用于描述附件元数据和本地相对路径。
- `AttachmentRef` 只保存引用信息，不保存二进制内容。
- 没有附件的旧数据仍可正常读取、保存、导入和导出。

### 2.2 建立本地附件目录结构

- 在 SoNotes 本地数据目录下预留 `attachments/` 目录。
- 附件文件按内容哈希寻址，避免重复文件多次写入。
- 附件目录与 `data.json` 分离，保持主 JSON 文件轻量。
- 附件路径必须使用相对路径，避免用户目录、绝对路径或平台差异进入 **Domain state（领域状态）**。

### 2.3 建立附件文件基础操作

- 新增 Tauri/Rust 侧附件文件基础命令，用于写入、读取元数据、删除和检查存在性。
- 写入附件时计算 SHA-256，并以哈希结果决定文件名。
- 重复写入相同内容时复用已有附件文件。
- 文件操作失败不能破坏已有 `data.json`。

### 2.4 扩展导出 / 备份结构预留

- 明确未来备份包应包含 `data.json` 与 `attachments/`。
- 本版本只为导出 / 备份流程预留附件收集与校验边界，不实现完整 zip 备份。
- 当前纯 JSON 导出仍保持可用。
- 未来 `v1.4.9` 再落地 `SoNotes_Backup_<timestamp>.zip`。

---

## 3. 非目标

本次不做以下能力：

- **图片入口**：不实现图片粘贴、拖入、文件选择添加图片。
- **图片预览 UI**：不在 **Note** 中渲染图片缩略图、图库或附件列表。
- **泛附件复杂管理**：不实现附件重命名、排序、批量管理、下载或打开方式管理。
- **远端备份 / WebDAV**：不涉及 WebDAV、远端上传、下载或同步。
- **本地 zip 备份 / 恢复正式实现**：不在本版本实现完整 zip 打包、解包、恢复 UI。
- **base64 图片入库**：不允许把图片或其他大体积二进制内容写入 `data.json`。
- **附件进入 Undo/Redo 复杂历史**：本版本不把附件增删作为完整可撤销用户操作落地；后续图片入口版本再定义交互历史。
- **永久删除策略最终化**：本版本建立引用和清理基础，但是否立即删除共享附件文件需要通过引用计数或孤儿扫描策略确认后再执行。

## 4. 业务边界决策

### 4.1 附件不是 Note 的正文

附件是 **Note** 的附加引用，不进入 `content` 字段，也不以 Markdown base64 或 HTML blob 形式混入正文。

- `content` 继续表示用户输入的文本正文。
- 附件由 `attachments?: AttachmentRef[]` 表示。
- 没有附件时，`attachments` 可以缺失或为空数组。

### 4.2 附件文件不是 Domain state 的事实来源

**Domain state** 保存附件引用关系，附件文件本体保存在本地文件系统中。

- `data.json` 记录哪些 **Note** 引用了哪些附件。
- `attachments/` 保存实际文件。
- 附件文件缺失时，**Note** 本身仍应可读取。
- 缺失附件属于一致性问题，不应导致整个看板或便签加载失败。

### 4.3 内容哈希优先于原文件名

附件文件以 SHA-256 内容哈希寻址，原文件名只作为展示元数据保存。

- 相同内容的文件只需存储一份。
- `filename` 不参与实际存储路径决策。
- `relativePath` 由应用生成，不接受外部导入的任意路径直接写入。

### 4.4 软删除不立即删除附件文件

**Soft delete（软删除）** 只把 **Note** 移入 **Trash（废纸篓）**，附件引用仍属于该 **Note**。

- 软删除后附件文件必须保留，便于还原。
- 从废纸篓还原后附件引用应保持不变。
- 软删除与还原不触发附件文件清理。

### 4.5 永久删除需要谨慎处理共享附件

**Permanent delete（永久删除 / 硬删除）** 会彻底移除 **Note**。如果该 **Note** 引用附件，需要判断附件是否仍被其他 **Note** 引用。

- 被其他 **Note** 引用的附件文件不得删除。
- 未被任何 **Note** 引用的附件可以进入孤儿清理候选。
- 本版本优先实现孤儿识别能力，避免在永久删除路径中直接做不可逆文件删除导致误删。

## 5. 当前代码边界

### 5.1 数据模型

当前核心类型位于 `src/store/types.ts`：

- `Note`：当前没有 `attachments` 字段。
- `Board`：不涉及附件。
- `StorageData`：包含 `schemaVersion`、`storageUpdatedAt`、`notes`、`boards`、`currentBoardId`、`config`。
- `STORAGE_SCHEMA_VERSION` 当前为 `1`。

`StorageData` 写入 `data.json` 时由 `serializeDomainState` / `serializeState` 生成，读取时由 `normalizeStorageDataMetadata`、`migrateAndSanitize` 与 `normalizeNotes` 修补旧数据。

### 5.2 持久化路径

当前磁盘数据路径由 Rust 侧 `src-tauri/src/lib.rs` 管理：

```text
<Documents>/SoNotes/data.json
```

Rust 侧 `src-tauri/src/persistence.rs` 当前不解析 JSON 内容，只负责：

- `fs4` 排他锁。
- `.tmp` 原子写入。
- 连续 Save 合并。
- Import / Restore intent 的 `.bak` 保护能力。

附件文件适合放在同一个 SoNotes 数据目录下：

```text
<Documents>/SoNotes/attachments/
```

### 5.3 导入导出

当前导入导出核心位于：

- `src/utils/dataTransfer.ts`
- `src/services/transfer/DataTransferService.ts`
- `src/utils/fileSystem.ts`

当前 `ExportData` 是纯 JSON：

```ts
type ExportData = {
  version: 1;
  type: 'FULL_BACKUP' | 'SINGLE_BOARD';
  source: 'so-notes';
  timestamp: number;
  payload: {
    boards: Board[];
    notes: Note[];
    config?: AppConfig;
    currentBoardId?: string;
  };
};
```

本版本不直接改成 zip 备份格式，但需要在计划和类型设计中预留未来 `data.json + attachments/ + manifest.json` 的结构。

## 6. 技术设计

### 6.1 AttachmentRef 类型

建议新增类型：

```ts
type AttachmentRef = {
  id: string;
  hash: string;
  filename: string;
  mimeType: string;
  size: number;
  relativePath: string;
  createdAt: number;
};
```

字段说明：

| 字段 | 说明 |
|---|---|
| `id` | 附件引用 ID，用于 **Note** 内部稳定引用 |
| `hash` | 文件内容 SHA-256，用于去重与完整性检查 |
| `filename` | 原始文件名，仅用于展示 |
| `mimeType` | MIME 类型，用于未来预览与打开方式判断 |
| `size` | 文件大小，单位 byte |
| `relativePath` | 相对 SoNotes 数据目录的路径，例如 `attachments/<sha256>.<ext>` |
| `createdAt` | 引用创建时间 |

### 6.2 Note 类型扩展

建议在 `Note` 上增加可选字段：

```ts
type Note = {
  // existing fields...
  attachments?: AttachmentRef[];
};
```

兼容策略：

- 旧数据没有 `attachments` 字段时视为无附件。
- `migrateAndSanitize` 可补齐为 `[]`，也可保持字段缺失；建议在运行时选择统一形态，避免组件和导出逻辑反复判空。
- `StorageDataInput` 继续允许旧数据缺失该字段。

### 6.3 schemaVersion 策略

建议将 `STORAGE_SCHEMA_VERSION` 从 `1` 升级到 `2`。

升级含义：

- `v1`：无附件字段，纯文本 **Note** 数据。
- `v2`：允许 **Note** 携带 `attachments` 引用。

迁移策略：

- 读取 `v1` 数据时，为每个 **Note** 补齐 `attachments: []` 或按统一运行时形态处理。
- 写回时输出 `schemaVersion: 2`。
- 不改变 `Board`、`Trash`、`ViewMode`、`Viewport state` 或 `UI state` 语义。

### 6.4 附件路径策略

建议附件文件路径：

```text
attachments/<sha256>.<ext>
```

其中：

- `<sha256>` 来自文件内容。
- `<ext>` 从 MIME 类型或原文件扩展名推断。
- 如果无法可靠推断扩展名，可以只使用哈希文件名或使用安全默认扩展名，MIME 类型统一落到 `application/octet-stream`。
- `relativePath` 必须由 Rust 侧或可信工具函数生成，不接受外部 JSON 直接提供的任意路径。

### 6.5 Rust 侧附件命令

建议新增最小命令集合：

```rust
write_attachment(bytes, filename, mime_type) -> AttachmentWriteResult
attachment_exists(relative_path) -> bool
delete_attachment_if_unreferenced(relative_path, referenced_hashes) -> AttachmentDeleteResult
read_attachment_metadata(relative_path) -> AttachmentFileMetadata
```

本版本重点是文件落盘和元数据能力，不需要提供图片预览所需的 blob URL 或缩略图服务。

实现约束：

- 附件写入必须限制在 SoNotes 数据目录内。
- SHA-256 必须采用流式分块计算，不允许为了计算哈希而把完整附件一次性读入内存。
- `relativePath` 需要做路径穿越防护，禁止 `..`、绝对路径和跨盘路径。
- Rust 侧拼接附件路径后，需要做路径规范化校验，确认最终路径仍位于 SoNotes 数据目录或 `attachments/` 目录内。
- 写入时使用临时文件 + rename，避免半写文件。
- 已存在相同哈希文件时直接复用。

### 6.6 导出 / 备份预留

当前 JSON 导出继续保持原行为。为了未来备份格式演进，本版本需要明确目标结构：

```text
SoNotes_Backup_<timestamp>.zip
├── data.json
├── manifest.json
└── attachments/
    └── <sha256>.<ext>
```

`v1.4.7` 可先实现或记录以下基础能力：

- 从 `StorageData.notes[].attachments` 收集被引用附件。
- 校验引用附件是否存在。
- 识别 `attachments/` 下未被任何 **Note** 引用的孤儿文件。
- 孤儿识别应以完整 **Domain state** 为输入，扫描所有 **Note**，包括位于 **Trash** 中的 **Note**，构建存活哈希集合后再与 `attachments/` 目录做差集。
- 保持现有 JSON 导出入口不变，避免提前引入 zip UI 和恢复流程。

完整 zip 打包、恢复校验和失败回滚属于 `v1.4.9`。

### 6.7 导入兼容预留

当前 `processImport` 已支持旧数据兼容、ID 重映射、看板名冲突重命名和无效便签跳过。附件模型引入后需要预留：

- 导入 JSON 时保留合法 `attachments` 引用，但不信任外部 `relativePath`。
- 如果导入包不包含实际附件文件，则附件引用应标记为缺失或跳过。
- 单板导出与选中便签导出必须只收集被导出的 **Note** 实际引用的附件。
- 外部导入的附件 hash 与文件内容必须一致，否则拒绝该附件文件。

这些能力可在 `v1.4.9` 正式 zip 备份 / 恢复中落地，本版本先把类型和校验入口设计清楚。

## 9. 验收标准

### 9.1 旧数据兼容

- 旧版 `schemaVersion: 1` 或缺失 schema 的 `data.json` 能正常读取。
- 没有 `attachments` 字段的 **Note** 被视为无附件。
- 启动后保存不会丢失现有便签、看板、废纸篓状态或配置。

### 9.2 附件引用模型

- `Note` 支持保存 `attachments` 引用。
- `AttachmentRef` 包含 hash、原文件名、MIME、大小、相对路径与创建时间。
- `data.json` 中不出现图片 base64 或二进制内容。

### 9.3 附件目录

- 应用能在本地数据目录下创建或识别 `attachments/`。
- 附件文件按 SHA-256 内容哈希命名。
- 大文件写入时，哈希计算使用流式分块处理，不随附件大小线性占用整文件内存。
- 相同内容重复写入时复用已有文件。
- 附件路径不能逃出 SoNotes 数据目录。
- 规范化后的附件路径仍必须位于 SoNotes 数据目录或 `attachments/` 目录内。

### 9.4 删除与一致性

- 软删除 **Note** 不删除附件文件。
- 还原 **Note** 后附件引用仍存在。
- 永久删除 **Note** 后，系统能识别可能变为孤儿的附件。
- 被多个 **Note** 引用的附件不会被误删。
- 位于 **Trash** 中的 **Note** 仍计入附件存活引用集合。

### 9.5 导出 / 备份预留

- 当前纯 JSON 导出入口仍可使用。
- 导出逻辑能识别 **Note** 上的附件引用。
- 文档和类型为未来 `data.json + attachments/ + manifest.json` 备份结构留出边界。
- 不在本版本承诺完整 zip 备份 / 恢复。

### 9.6 工程验证

- `npm run typecheck` 通过。
- `npm run test` 通过。
- `npm run build` 通过。
- `npm run tauri build -- --debug` 通过。

## 10. 风险

- 如果直接把图片 base64 写入 `data.json`，会迅速放大主存储文件，影响启动、保存和 WAL 仲裁性能。
- 如果计算附件哈希时一次性读取完整文件，未来支持大文件后可能造成 Tauri 后端内存占用过高。
- 如果 `relativePath` 信任外部导入数据，可能出现路径穿越或误删用户文件风险。
- 如果只做字符串级路径过滤，不做规范化路径边界校验，畸形路径仍可能绕过附件目录限制。
- 如果永久删除 **Note** 时直接删除附件文件，可能误删仍被其他 **Note** 引用的共享文件。
- 如果 schemaVersion 升级缺少旧数据测试，可能影响现有用户数据读取。
- 如果过早实现 zip 备份，会把 `v1.4.7` 扩大到 `v1.4.9` 的恢复回滚问题，增加版本风险。
- 如果附件文件写入与 `data.json` 写入没有明确顺序，可能出现引用已写但文件缺失，或文件已写但引用未保存的中间状态。

## 11. 开放问题

这些问题不阻塞规划文档，但实施前需要在对应 commit 中确认：

- **附件引用字段是否统一补齐为空数组**：旧数据读取后是保留 `attachments` 缺失，还是统一写为 `attachments: []`。
- **哈希文件扩展名策略**：无法可靠识别扩展名时，使用无扩展名、MIME 推断扩展名，还是保留原扩展名。
- **孤儿附件清理时机**：永久删除时只标记候选，还是提供显式扫描 / 清理入口。
- **附件文件写入顺序**：先写附件文件再写 `data.json`，还是先生成引用再通过事务性流程一起确认。
- **导入含附件引用但无文件时的策略**：保留缺失引用用于提示，还是跳过该附件引用。
- **schemaVersion 迁移链位置**：继续放在 `migrateAndSanitize` 内联处理，还是为 v2 建立显式迁移函数。

---

## 12. 一句话总结

`v1.4.7` 只为附件 / 图片能力建立本地优先的底层存储模型：让 **Note** 可以引用附件，让文件本体进入 `attachments/` 并按 SHA-256 内容寻址，同时保持旧数据兼容、`data.json` 轻量和未来备份结构可演进；图片入口、预览 UI、zip 备份和 WebDAV 都留到后续版本。
