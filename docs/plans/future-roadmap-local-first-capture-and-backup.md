# SoNotes 后续路线图：本地优先、快速捕获与可控备份

---

## 1. 背景

SoNotes 当前已经形成清晰的产品核心：以 **Note（便签）** 为最小信息单元，以 **Board（看板）** 组织空间，并通过 **Trash（废纸篓）** 提供软删除与恢复机制。v1.4.0 以后，项目也已经开始把 **Domain state（领域状态）**、**Viewport state（视口状态）** 与 **UI state（界面状态）** 拆分，并将跨层交互入口逐步收口到 `appController`。

此前根目录 `ROADMAP.md` 已过时，且其中以标签功能为主线的规划不再作为后续方向。本路线图替代旧路线思路，聚焦 SoNotes 已经验证有效的使用循环：

> 快速捕获 → 放到当前看板 → 在空间里整理 → 可撤销地编辑 → 本地可靠保存 → 必要时备份恢复

后续功能不应把 SoNotes 推向重型知识库、协作工具或多端自动同步系统，而应强化桌面便签工具的低摩擦捕获、本地可靠性和可控恢复能力。

---

## 2. 总体原则

### 2.1 本地优先

- 用户数据的真实来源仍然是本地 **Domain state**。
- 远端能力只能作为备份与恢复辅助，不作为实时协作或多端状态合并基础。
- 默认不引入必须联网才能成立的核心体验。

### 2.2 捕获优先

- 优先提升托盘、快捷键与快速捕获入口的稳定性和可理解性。
- 捕获入口应把内容明确写入当前 **Board**，并尊重 **ViewMode** 的边界。
- 不增加高风险、跨平台不稳定的托盘交互。

### 2.3 可撤销优先

- 所有会改变 **Domain state** 的常用操作，都应逐步纳入 Undo/Redo。
- Undo/Redo 不覆盖 **Viewport state** 和 **UI state**。
- 操作历史应提升用户信任感，而不是扩大状态复杂度到难以维护。

### 2.4 备份优先于同步

- 下一阶段禁用“同步”承诺，只使用“备份 / 恢复”表述。
- WebDAV 如进入规划，只作为远端备份仓库。
- 不承诺多端自动合并、实时同步或便签级冲突解决。

---

## 3. 明确非目标

近期路线不包含以下能力：

- 标签功能。
- 云同步或 WebDAV 同步。
- 剪贴板栈、捕获队列、临时素材篮。
- 托盘双击语义。
- 托盘中键操作。
- 文本或文件直接拖到托盘图标。
- 悬停托盘唤出 Dropzone。
- 撕下便签后的直接编辑。
- 将图片或附件以 base64 写入 JSON。
- 多端自动合并、冲突 UI、CRDT 或向量时钟。

---

## 4. 阶段一：托盘低风险增强

### 4.1 目标

强化 SoNotes 作为常驻托盘便签工具的可达性，同时只使用跨平台风险较低、当前架构容易承接的交互。

### 4.2 范围

保留并增强：

- 单击托盘图标显隐窗口。
- 右键菜单作为稳定操作入口。
- tooltip 状态提示。

### 4.3 建议 tooltip 内容

tooltip 可用于展示轻量状态，例如：

- 当前看板名称。
- 保存状态：保存中、已保存、保存失败。
- 快速捕获提示。

示例：

```text
SoNotes · 当前看板：主板 · 已保存
```

### 4.4 不做

- 不把双击托盘图标作为核心语义。
- 不设计中键操作。
- 不做托盘图标拖放。
- 不做托盘悬停 Dropzone。

### 4.5 验收标准

- 现有左键单击显隐窗口行为保持不变。
- 右键菜单仍可稳定触发快速捕获、从剪贴板创建便签、新建空白便签、重置窗口等入口。
- tooltip 能反映基础状态，但 tooltip 不成为必须依赖的唯一入口。

## 5. 阶段二：通用 Undo/Redo

### 5.1 目标

将 Undo/Redo 从当前局部的归拢撤销，扩展为覆盖主要 **Domain state** 变更的通用能力。

### 5.2 覆盖范围

Undo/Redo 应覆盖：

- 新建便签。
- 编辑标题与正文。
- 移动便签。
- 缩放便签。
- 改色。
- 折叠 / 展开。
- 软删除。
- 从废纸篓还原。
- 批量操作。
- 归拢。
- 拆分。
- 合并。

### 5.3 不覆盖范围

Undo/Redo 不覆盖：

- 画布平移。
- 画布缩放。
- 搜索框输入。
- 弹窗开关。
- 右键菜单显隐。
- hover 状态。
- 框选过程。
- 临时选区框绘制过程。

### 5.4 状态边界

- Undo/Redo 只记录 **Domain state** 的可逆变更。
- **Viewport state** 与 **UI state** 不进入操作历史。
- 组合操作应作为一个用户意图进入历史，例如“合并为一张”“批量改色”“批量软删除”。

### 5.5 历史记录实现约束

Undo/Redo 不应无节制保存完整状态快照。拖拽、缩放、批量移动等高频操作必须按用户意图合并后再入栈。

- 不允许在拖拽或缩放过程中逐帧推入历史记录。
- 拖拽开始到松手，应合并为一个可撤销操作。
- 缩放开始到结束，应合并为一个可撤销操作。
- 批量操作应作为一个整体 Command 入栈。
- 优先采用 Command / patch 风格记录 `undo` 与 `redo` 所需的最小差异。
- 如采用快照方案，必须具备合并、节流、容量上限与内存裁剪策略。
- 历史栈必须有明确上限，避免大看板或长时间拖拽造成内存膨胀。

### 5.6 验收标准

- 常用编辑操作可通过撤销恢复到前一个领域状态。
- 重做不会影响画布视口位置、搜索输入、菜单状态等界面状态。
- 批量操作撤销后，便签集合与所属看板关系恢复一致。
- 拖拽、缩放等高频操作不会产生大量中间历史记录。
- 历史栈超过上限时能按既定策略裁剪，不造成内存持续增长。

## 6. 阶段三：撕下便签 / 只读镜像视图

### 6.1 目标

允许用户将某个 **Note** 从主画布“撕下”为一个独立的只读镜像视图，用于临时悬浮查看。原始便签仍属于当前 **Board**，画布中的便签仍然是唯一可编辑来源。

该能力强化桌面便签的空间感，但不改变 **Domain state** 的事实来源。

### 6.2 核心语义

撕下便签不是复制，也不是剪切。它只是为同一个 **Note** 创建一个额外的只读渲染视图。

- 画布中的 Note 是唯一 source of truth。
- 撕下视图只读，不提供标题或正文编辑入口。
- 用户在画布中修改 Note 后，撕下视图同步映射最新内容。
- 关闭或贴回撕下视图，不应创建新 Note，也不应删除原 Note。
- 撕下视图本身默认不进入持久化数据。

### 6.3 三个按钮

撕下视图提供三个明确操作：

| 按钮 | 行为 | 状态影响 |
|---|---|---|
| 定位到画布所在 | 显示主窗口，切回 Note 所在 Board，定位、选中并高亮原便签 | 只影响 Viewport/UI state |
| 置顶 | 对撕下视图启用或取消 always-on-top | 只影响窗口运行态 |
| 贴回画布 | 关闭撕下视图，回到原始画布便签 | 不修改 Domain state |

“贴回画布”不表示复制或粘贴一份新便签，只表示收回这个镜像视图。

### 6.4 推荐实施路线

第一版建议分两步：

1. **主窗口内浮层原型**：先在主窗口中实现只读浮层，验证交互语义、按钮行为和渲染复用，不引入 Tauri 多窗口复杂度。
2. **Tauri 独立窗口版本**：在原型成立后，再用 Tauri `WebviewWindow` 创建 `detached-note-{noteId}` 独立窗口，并通过窗口事件同步 Note 快照。

独立窗口版本需要处理：

- 动态窗口 label。
- 分离窗口生命周期。
- 主窗口到分离窗口的 Note 数据同步。
- 分离窗口到主窗口的定位、置顶、贴回事件。
- 避免同一 Note 重复打开多个分离窗口。

### 6.5 多窗口失焦与同步约束

独立窗口版本必须特别处理主窗口与撕下视图之间的 focus / blur 关系。用户点击撕下视图时，主窗口不应被误判为离开应用而自动隐藏。

- 主窗口的失焦隐藏逻辑必须识别 SoNotes 自有窗口集合。
- 从主窗口切到撕下视图，不应触发主窗口的自动隐藏。
- 从撕下视图回到主窗口，应保持定位、高亮与视图状态可预期。
- Note 数据同步必须定向发送到对应 `detached-note-{noteId}` 窗口。
- 不应使用全局广播推送所有 Note 状态。
- 撕下视图只能订阅 Note 快照，不得反向触发 **Domain state** 修改。
- 关闭撕下视图时，必须清理窗口映射与事件监听。

### 6.6 组件拆分建议

现有 `NoteCard` 已经有 `isStatic` 只读模式，但它同时包含拖拽、编辑、选择、右键菜单、DOM 注册等画布职责。撕下便签不应直接复用完整 `NoteCard` 作为独立窗口主体。

建议先抽取纯展示部分：

- 便签背景、阴影、边框、颜色计算。
- 标题与正文只读展示。
- 折叠态展示。
- 尺寸与视觉度量。

之后由 `NoteCard` 与撕下视图共享这部分视觉渲染能力。

### 6.7 不做

- 不在撕下视图中直接编辑标题或正文。
- 不为撕下视图创建第二份 Note 数据。
- 不把撕下视图默认写入 `StorageData`。
- 不让撕下视图参与画布选区、多选、拖拽归拢或右键菜单。
- 不在第一版承诺应用重启后恢复所有撕下窗口。
- 不让点击撕下视图触发主窗口自动隐藏。
- 不用全局事件广播推送全部便签状态。

### 6.8 验收标准

- 同一 Note 在画布修改后，撕下视图能同步展示最新内容。
- 撕下视图无法直接修改 Note。
- “定位到画布所在”能准确切回对应 Board，并高亮原便签。
- “置顶”只影响撕下视图窗口或浮层，不影响主窗口 Pin 状态。
- “贴回画布”关闭撕下视图，不创建副本，不删除原便签。
- 用户在主窗口与撕下视图之间切换焦点时，主窗口不会异常隐藏。
- Note 同步只发送给对应撕下视图窗口，不广播到无关窗口。

## 7. 阶段四：附件 / 图片存储模型

### 7.1 目标

为图片与附件能力建立本地优先的数据模型，避免把二进制内容塞入 JSON，保持当前主存储结构可演进。

### 7.2 推荐模型

`Note` 只保存附件引用元数据，附件文件独立存储。

```ts
type AttachmentRef = {
  id: string
  hash: string
  filename: string
  mimeType: string
  size: number
  relativePath: string
  createdAt: number
}
```

文件本体建议按内容哈希寻址：

```text
attachments/<sha256>.<ext>
```

### 7.3 设计原则

- `Note` 不直接保存图片 base64。
- `data.json` 只保存附件引用。
- 相同文件可通过哈希去重。
- 导出、备份、恢复时按引用收集附件。
- 恢复时应能检测缺失附件与孤儿附件。

### 7.4 与备份格式的关系

附件模型应先于远端备份完成，因为备份格式需要一次性考虑 `data.json` 与 `attachments/` 的一致性。

### 7.5 验收标准

- 没有附件的旧数据仍可正常读取。
- 带附件的便签可以被完整导出与恢复。
- 删除便签、永久删除便签与附件引用之间的关系有明确规则。
- 不出现把大体积图片写入 `data.json` 的路径。

## 8. 阶段五：带时间戳的备份 / 恢复

### 8.1 目标

建立稳定、可验证、面向未来附件能力的备份包格式。

### 8.2 备份文件命名

每次备份生成独立快照，不覆盖唯一远端文件。

```text
SoNotes_Backup_<timestamp>.zip
```

示例：

```text
SoNotes_Backup_2026-05-30_231500.zip
```

### 8.3 备份包结构

```text
data.json
attachments/
```

当前没有附件时，`attachments/` 可以为空或不存在。

### 8.4 交互策略

- 手动备份是第一入口。
- 定时备份是可选开关。
- 恢复时必须由用户明确选择某个时间点。
- 恢复前应提示当前数据会受到影响。
- 恢复失败必须保持本地数据不被破坏。

### 8.5 验收标准

- 同一天多次备份不会互相覆盖。
- 用户能从多个时间戳备份中选择恢复目标。
- 备份包可以完整包含当前 Domain 数据与被引用附件。
- 恢复时能处理附件缺失、JSON 不合法、版本不兼容等失败路径。

## 9. 阶段六：WebDAV 远端备份

### 9.1 定位

WebDAV 只作为远端备份仓库，不作为同步系统。

### 9.2 范围

WebDAV 能力只包括：

- 上传带时间戳的备份 zip。
- 列出远端备份快照。
- 下载用户选择的备份快照。
- 从用户选择的快照执行恢复。
- 可选定时上传备份。

### 9.3 不做

- 不做多端自动合并。
- 不做实时同步。
- 不做便签级冲突解决。
- 不自动覆盖本地数据。
- 不把远端文件作为当前运行时数据源。

### 9.4 风险控制

- 所有远端恢复都必须是显式用户动作。
- 自动定时备份只能上传新快照，不能自动拉取并覆盖本地。
- 远端备份列表应展示时间戳、大小与可读状态。
- 下载后应先校验备份包结构，再进入恢复流程。

### 9.5 验收标准

- WebDAV 断网、鉴权失败、上传失败不会影响本地保存。
- 远端已有多个备份时，应用不会把它们解释为需要合并的状态。
- 用户可以明确知道自己正在上传备份、下载备份或恢复备份。

## 10. 建议实施顺序

| 优先级 | 阶段 | 价值 | 主要风险 |
|---|---|---|---|
| P1 | 托盘低风险增强 | 提升入口可达性 | 平台差异、事件语义误判 |
| P2 | 通用 Undo/Redo | 提升编辑信任感 | 操作历史边界、批量操作一致性 |
| P3 | 撕下便签 / 只读镜像视图 | 强化桌面便签感 | 多窗口同步、只读边界、窗口生命周期 |
| P4 | 附件 / 图片存储模型 | 为图片与备份打基础 | 文件生命周期、缺失附件、孤儿附件 |
| P5 | 带时间戳的备份 / 恢复 | 建立可靠快照格式 | 恢复失败回滚、版本兼容 |
| P6 | WebDAV 远端备份 | 提供远端兜底 | 网络失败、用户误解为同步 |

## 11. v1.4.x 小版本推进建议

当前最新发布版本为 `v1.4.5`。后续建议继续沿用 `v1.4.x` 小版本推进，每个版本只承载一个明确主题，避免一次性引入过多架构风险。

| 版本 | 主题 | 主要范围 | 明确不做 |
|---|---|---|---|
| `v1.4.2` | 托盘低风险增强 | tooltip 状态提示、当前看板名、保存状态、托盘菜单稳定性检查 | 托盘双击、中键、拖放、悬停 Dropzone、剪贴板栈 |
| `v1.4.3` | Undo/Redo 基础架构 | 新建、编辑标题/正文、移动、改色、折叠/展开；建立 Command / patch 历史机制 | 批量操作、废纸篓、归拢、拆分、合并、永久删除撤销 |
| `v1.4.4` | Undo/Redo 批量与复杂操作 | 复合 DomainPatch 扩展、软删除、废纸篓还原、批量移动、批量改色、批量软删除、归拢、拆分、合并、调整便签尺寸 | 永久删除撤销、TRASH 视图 Undo/Redo、Viewport/UI state 撤销 |
| `v1.4.5` | 撕下便签主窗口内浮层原型 | 主窗口内只读镜像、定位到画布所在、贴回画布、画布修改后同步展示 | 独立系统窗口、OS 级置顶、重启恢复撕下状态、撕下视图直接编辑 |
| `v1.4.6` | 撕下便签 Tauri 独立窗口 | `detached-note-{noteId}` 独立窗口、always-on-top、定向同步、定位回主窗口、生命周期清理 | 创建第二份 Note、全局广播全部便签状态、持久化撕下窗口状态 |
| `v1.4.7` | 附件 / 图片存储底层模型 | `AttachmentRef`、`attachments/` 目录、SHA-256 内容寻址、旧数据兼容、导出/备份结构预留 | WebDAV、泛附件复杂管理、base64 图片写入 JSON |
| `v1.4.8` | 图片入口与附件一致性 | 图片粘贴、拖入、预览、删除引用、缺失附件提示、孤儿附件扫描 / 清理策略 | 远端备份、在线同步 |
| `v1.4.9` | 本地 zip 备份 / 恢复 | `SoNotes_Backup_<timestamp>.zip`、`data.json`、`attachments/`、`manifest.json`、恢复校验与失败回滚 | WebDAV、多端合并 |
| `v1.4.10` | WebDAV 远端备份 | WebDAV 配置、测试连接、上传 / 列出 / 下载 / 恢复带时间戳备份包、可选定时上传 | 实时同步、自动拉取覆盖本地、便签级冲突解决、远端运行时数据源 |

### 11.1 版本切分原则

- 每个小版本只解决一个主要问题。
- 低风险体验增强先行，架构型能力后置。
- 能先用本地能力验证的，不直接进入远端或多窗口版本。
- 任何涉及 **Domain state**、持久化格式或跨窗口同步的版本，都必须有明确回滚与失败路径。

### 11.2 建议推进节奏

```text
v1.4.2  托盘低风险增强
v1.4.3  Undo/Redo 基础架构
v1.4.4  Undo/Redo 批量与复杂操作
v1.4.5  撕下便签主窗口内浮层原型
v1.4.6  撕下便签 Tauri 独立窗口
v1.4.7  附件 / 图片存储底层模型
v1.4.8  图片入口与附件一致性
v1.4.9  本地 zip 备份 / 恢复
v1.4.10 WebDAV 远端备份
```

## 12. 术语约定

### Backup（备份）

把当前本地数据快照保存到外部位置。备份可以是本地 zip，也可以上传到 WebDAV。

### Restore（恢复）

用户明确选择某个备份快照，并将其导入或覆盖到本地数据。

### Sync（同步）

暂不承诺。除非未来引入便签级操作日志、冲突 UI、附件一致性协议或 CRDT 等机制，否则不使用“同步”描述 WebDAV 能力。

## 13. 一句话总结

SoNotes 下一阶段应优先强化“托盘可达性”和“领域状态可撤销”，随后以只读镜像方式实现撕下便签，再建立面向图片 / 附件的本地存储模型，并以带时间戳的 zip 快照实现可控的备份 / 恢复，最后接入 WebDAV 作为远端备份仓库，而不是同步系统。
