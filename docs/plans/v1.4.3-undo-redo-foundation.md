# SoNotes v1.4.3 实施计划：Undo/Redo 基础架构

---

## 1. 背景

SoNotes 已经完成 **Domain state（领域状态）**、**Viewport state（视口状态）** 与 **UI state（界面状态）** 的概念拆分，并开始通过 `appController` 收口跨层交互入口。当前项目中存在一个局部撤销能力：`undoLastArrange` 只服务于归拢、合并、拆分后的 toast 回退，不是通用 Undo/Redo。

`v1.4.3` 的目标不是一次性覆盖所有可逆操作，而是先建立可维护的通用历史机制，并只接入低风险、单便签、用户意图边界清楚的 **Domain state** 操作。

本版本必须把业务边界确认清楚：Undo/Redo 应提升用户信任感，不能破坏输入框原生编辑撤销、拖拽手感、废纸篓安全边界或视口操作体验。

---

## 2. 目标

### 2.1 建立通用历史基础设施

- 新增独立的 Undo/Redo 历史层，记录可逆 **Domain state** 变更。
- 历史记录采用 Command / patch 风格，只保存撤销和重做所需的最小差异。
- 历史栈必须有容量上限，避免长时间使用后内存持续增长。
- 新操作入栈后必须清空 redo 栈。

### 2.2 接入 v1.4.3 范围内的单便签操作

本版本只覆盖以下操作：

- 新建空白便签。
- 新建带内容的单张便签。
- 编辑便签标题。
- 编辑便签正文。
- 移动单张便签。
- 改变单张便签颜色。
- 折叠 / 展开单张便签。

### 2.3 快捷键入口

- `Ctrl+Z` / `Cmd+Z`：撤销。
- `Ctrl+Y` / `Cmd+Y`：重做。
- `Ctrl+Shift+Z` / `Cmd+Shift+Z`：重做。
- 当焦点位于 `input`、`textarea` 或 `contenteditable` 内时，不劫持原生文本编辑撤销 / 重做。
- 当 `Spotlight` 或快速捕获层打开时，不触发画布 Undo/Redo。

### 2.4 测试补强

- 覆盖历史栈的 push、undo、redo、清空 redo、容量裁剪。
- 覆盖每个接入操作的撤销与重做。
- 覆盖快捷键在普通画布、输入框聚焦、快速捕获打开、废纸篓视图下的行为边界。

---

## 3. 非目标

本次不做以下能力：

- 批量操作撤销 / 重做。
- 软删除撤销。
- 废纸篓还原撤销。
- 永久删除撤销。
- 归拢、拆分、合并接入通用历史。
- 跨看板移动、复制、重复便签接入通用历史。
- Board 创建、重命名、排序、删除的撤销 / 重做。
- 画布平移、画布缩放、看板视口位置撤销。
- 搜索输入、菜单开关、选区、框选过程、hover、高亮、toast 显隐撤销。
- 与现有 `undoLastArrange` toast 机制合并。

---

## 4. 业务边界决策

### 4.1 历史只记录 Domain state

Undo/Redo 只记录便签、看板及其关系中属于 **Domain state** 的可逆变更。以下状态不得进入历史：

- **Viewport state**：画布平移、缩放、视口尺寸、边缘推动过程。
- **UI state**：选区、右键菜单、Spotlight、快速捕获层、BoardDock、toast、hover、高亮。

撤销或重做后，可以为了可理解性更新选区或高亮，但这类变化只能作为附带 UI 反馈，不能成为历史记录的事实来源。

### 4.2 输入框原生撤销优先

便签标题和正文当前通过 `NoteCard` 的 `input` / `textarea` 编辑，并在 `onChange` 中调用 `updateTitle` / `updateNote`。全局 Undo/Redo 不应在输入框聚焦时拦截 `mod+z` 或 `mod+shift+z`。

推荐边界：

- 用户正在编辑标题或正文时，快捷键留给浏览器 / WebView 的原生文本撤销。
- 用户离开输入框后，再按全局撤销，撤销最近一次已提交的便签编辑意图。
- 编辑历史不记录每个字符，按一次编辑会话合并：获得焦点时记录旧值，失去焦点或提交点记录新值。
- 如果用户尚未失去焦点，但触发全局按钮、窗口失焦或全局 Undo/Redo，应先尝试提交当前编辑会话，再执行后续动作。

### 4.3 编辑提交点

标题和正文编辑应以“编辑会话”为历史单位：

- 获得焦点：记录编辑前标题或正文。
- onChange：继续保持当前即时写入体验，不延迟 UI 更新。
- 失去焦点：如果值发生变化，入栈一个可撤销编辑操作。
- 全局提交点：点击便签外的全局按钮、窗口失焦、关闭当前交互入口，或执行全局 Undo/Redo 前，应先结算当前编辑会话。
- 如果值未变化，不入栈。

推荐先不新增手动提交快捷键，避免与原生输入体验冲突。结算编辑会话时还应避开输入法组合输入状态，避免在 composition 过程中错误提交半成品文本。

实现上建议将该能力收敛成一个明确入口，例如 `commitActiveEditSession()`，由失焦、窗口失焦、全局按钮和全局快捷键入口复用，避免各组件重复实现提交判断。

### 4.4 移动提交点

移动便签当前已有明确意图边界：拖拽过程中更新位置，结束时调用 `finalizeLayoutChange` 刷新 `updatedAt`。`v1.4.3` 应沿用这个边界。

推荐边界：

- 拖拽开始时记录单张便签起始位置。
- 拖拽过程中不入栈。
- 拖拽结束并确认位置变化后，入栈一个移动操作。
- sticky drag 放置成功时按同样规则入栈。
- 取消 sticky drag、窗口失焦导致的暂停或恢复，不入栈。

### 4.5 新建便签边界

新建便签的 undo 应移除该便签，redo 应恢复同一张便签的完整快照。

推荐边界：

- redo 必须恢复原 note id，而不是生成新 id。
- redo 恢复时必须维护 `notesById`、`allNoteIds`、`boardNoteIds`、`layoutNotesById` 与 `config.maxZ` 的一致性。
- 如果用户在 undo 后执行了其它新操作，redo 栈清空，新建便签不再可重做。

### 4.6 改色与折叠 / 展开边界

改色与折叠 / 展开都是单便签、低频、意图明确的操作，适合在 `v1.4.3` 接入。

推荐边界：

- 改色只记录旧颜色与新颜色。
- 折叠 / 展开只记录旧折叠状态与新折叠状态。
- 双击标题栏触发折叠 / 展开，与按钮触发使用同一历史入口。
- 废纸篓只读展示中的操作不进入本版本 Undo/Redo。

### 4.7 废纸篓安全边界

本版本不让 Undo/Redo 进入 **Trash（废纸篓）** 管理语义。

推荐边界：

- `TRASH` 视图下不响应全局 Undo/Redo 快捷键。
- `TRASH` 视图下按 Undo/Redo 默认静默无动作，不弹 toast。
- 永久删除继续依赖明确确认，不提供撤销承诺。
- 软删除、还原、清空废纸篓、批量永久删除留到后续版本重新评估。

### 4.8 现有归拢撤销边界

`undoLastArrange` 继续保留为局部 toast 回退能力。本版本不把归拢、拆分、合并迁移到新历史层。

推荐边界：

- 不删除 `undoLastArrange`。
- 不把 toast 的“撤销”按钮改接通用 Undo。
- 后续版本再决定是否将组织类操作统一迁移。

## 5. 技术设计约束

### 5.1 历史层位置

优先在 `src/store/domainStore.ts` 附近建立领域历史能力，而不是混入 **Viewport state** 或 **UI state**。

当前代码仍处于过渡期：`domainStore` 已提供独立 **Domain state** 与写入动作，但运行时主要路径仍大量经过 `useStore`，并通过 `legacyDomainBridge` 将 legacy store 同步到 `domainStore`。因此 `v1.4.3` 可以采用渐进策略：

1. 先实现纯函数式历史模型与测试，不绑定 UI。
2. 再为 legacy 运行路径提供最小接入点。
3. 后续版本逐步把更多领域写入迁移到 `domainStore`。

现阶段历史层的运行态写入目标必须是 `useStore`。原因是当前 `legacyDomainBridge` 只负责 `useStore` 到 `domainStore` 的单向同步，`domainStore` 写入不会反向驱动主界面更新。历史模型可以放在 `domainStore` 附近并保持纯领域语义，但实际 Undo/Redo 应用 patch 时必须作用到 `useStore` 的领域切片，避免出现历史状态已变而界面无响应的断层。

本版本不新增 `domainStore -> useStore` 反向桥，也不引入双向领域同步。等运行态领域写入迁移完成后，再评估是否把历史应用目标从 `useStore` 切回 `domainStore`。

### 5.2 Command / patch 数据形态

建议每条历史记录包含：

```ts
type HistoryEntry = {
  id: string;
  label: string;
  createdAt: number;
  undo: DomainPatch;
  redo: DomainPatch;
};
```

其中 `DomainPatch` 只描述最小领域差异，例如：

- 便签新增 / 移除。
- 便签字段变更。
- 便签位置变更。

不建议保存完整应用状态快照。

### 5.3 容量与裁剪

- 默认历史容量建议为 100 条。
- 超过容量时丢弃最旧记录。
- 新操作入栈后必须清空 redo 栈。
- 容量裁剪不能破坏当前可撤销 / 可重做边界。
- 大内容编辑只保存编辑会话前后文本，不保存每次按键。
- `v1.4.3` 不引入可配置容量；后续出现明确长历史需求时再评估。
- 历史记录不持久化到磁盘，应用重启后清空。

### 5.4 失败处理

撤销 / 重做执行时，如果目标便签不存在、已进入本版本不支持的状态，或关联看板不存在，应失败并保持当前状态不变。

推荐返回值：

- `true`：成功应用。
- `false`：没有可执行历史或目标状态不满足。

失败不应抛出用户可见异常，也不应部分应用 patch。

## 7. 验收标准

- 在看板视图中，新建便签后按 Undo 会移除该便签，按 Redo 会恢复同一便签。
- 编辑标题或正文后，输入框失焦再按 Undo，可恢复编辑前内容。
- 编辑标题或正文后，如果窗口失焦、点击全局按钮，或执行全局 Undo/Redo 前触发编辑会话结算，仅在内容变化时入栈。
- 输入框聚焦时，`Ctrl+Z` / `Cmd+Z` 只触发文本框原生撤销，不触发全局 Undo。
- 拖拽单张便签后，Undo 只回到拖拽开始前的位置，不回放拖拽中间帧。
- 改色后 Undo/Redo 能在旧颜色和新颜色之间切换。
- 折叠 / 展开后 Undo/Redo 能恢复前一折叠状态。
- `TRASH` 视图下按 Undo/Redo 无动作、无 toast、无 **Domain state** 变化。
- Spotlight 打开、快速捕获层打开时，全局 Undo/Redo 不改变看板便签。
- 执行新操作后 redo 栈被清空。
- 历史栈超过 100 条后会裁剪最旧记录，且不破坏当前可撤销 / 可重做边界。
- `undoLastArrange` 既有 toast 回退能力继续可用。
- 现有测试与新增测试通过。

## 8. 风险

- 标题 / 正文当前每次 `onChange` 都即时写入，若编辑会话提交点设计不稳，可能造成历史噪音或和原生文本撤销冲突。
- legacy `useStore` 与新 `domainStore` 仍在过渡期，历史层接入点需要避免双写或漏同步。
- 拖拽、sticky drag、边缘推动共享移动链路，若开始位置捕获不准确，Undo 可能恢复到错误位置。
- 新建便签 redo 需要恢复同一 id 和 normalized 关系，不能简单重新调用 `addNote`。
- 如果快捷键启用范围过宽，会破坏快速捕获、Spotlight 或输入框的既有体验。
- 如果编辑会话提交点遗漏窗口失焦或全局操作入口，可能出现用户以为已完成编辑、但历史栈尚未记录该意图的体验落差。

## 9. 已采纳的关键决策

### 9.1 输入编辑提交点

标题 / 正文以获得焦点到失去焦点作为一次可撤销编辑会话。

如果用户编辑后没有失焦，但触发全局按钮、窗口失焦或全局 Undo/Redo，应先尝试提交该编辑会话。只有旧值和新值确实不同才入栈。

### 9.2 废纸篓视图快捷键

`TRASH` 视图下暂不响应全局 Undo/Redo，按键默认静默无动作，不显示 toast。

如果后续需要提示，应优先放在可见按钮等主动操作入口，而不是绑定高频快捷键。

### 9.3 历史栈容量

默认 100 条，不持久化，`v1.4.3` 不提供配置项。

新操作清空 redo 栈；超过容量时裁剪最旧记录；大文本编辑保存编辑会话前后的完整字符串，不引入字符级差异算法。

### 9.4 Store 写入目标

`v1.4.3` 的历史模型保持纯领域语义，但运行态 patch 应用目标选择 `useStore`，不直接写入 `domainStore`。

这是过渡期决策：当前主界面仍以 `useStore` 为事实来源，`legacyDomainBridge` 只把 legacy 领域状态同步到 `domainStore`，没有反向同步。若直接写入 `domainStore`，Undo/Redo 结果不会反映到界面。

### 9.5 撤销新建便签的语义

撤销新建便签表示“这张便签从未创建成功”，应从 normalized 状态中完整移除，不进入 **Trash（废纸篓）**。

这不是 **Soft delete（软删除）**，也不应设置 `deletedAt`。重做时再恢复同一 `note id` 与完整领域关系。

---

## 10. 一句话总结

`v1.4.3` 先把 Undo/Redo 的地基打稳：只接入单便签、低风险、意图边界清楚的 **Domain state** 操作，并明确保护输入框、拖拽、废纸篓与视口体验。
