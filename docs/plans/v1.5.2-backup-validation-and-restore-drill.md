# SoNotes v1.5.2 实施计划：备份验证与恢复演练

---

## 1. 背景

`v1.4.9` 已经建立本地 zip 备份 / 恢复格式，备份包包含：

- `manifest.json`
- `data.json`
- `attachments/<hash>.<ext>` 图片文件

`v1.5.0` 在此基础上接入 WebDAV 远端备份仓库，`v1.5.1` 又集中修复了恢复可靠性、WebDAV 安全边界、图片缓存和 Undo/Redo 历史覆盖问题。

`v1.5.2` 的主题是 **备份验证与恢复演练**。本版本不改变 zip 格式，不做便签级恢复，不浏览备份包正文内容；只在真正覆盖恢复前回答一个问题：

> 这个备份能不能安全恢复？

---

## 2. 当前代码基线

### 2.1 已存在的复用点

- `src-tauri/src/backup.rs`

  - 已有 `create_local_backup` 与 `restore_local_backup` Tauri 命令。
  - `manifest.json` 已包含图片文件 `sha256` 与 `size`，因此 `v1.5.2` 可以在不改变 zip 格式的前提下做 hash 校验。
- `src/services/backup/BackupService.ts`
  - 已有 `createLocalBackup` 与 `restoreLocalBackup` 前端服务封装。
- `src/services/backup/WebDavBackupService.ts`
  - 已有 `downloadBackup`、`resolveDownloadedBackup`、`cleanupDownloadedBackup`。
  - 远端恢复已经走 download token，而不是让前端直接持有裸临时路径。
- `src/components/BoardDock.tsx`
  - 已有本地 zip 备份 / 恢复入口。
  - 已有 WebDAV 创建、列出、删除、下载并恢复入口。
  - 已有恢复后 `applyRestoredDiskData`，负责刷新前端状态、清理 WAL、预热图片 asset URL。

### 2.2 当前缺口

- 没有 `validate_local_backup` Tauri 命令。
- 没有 `BackupValidationResult` / `BackupValidationIssue` 结构化验证结果。
- 本地恢复当前是“选择 zip -> 二次确认 -> 直接恢复”，无法先展示备份摘要。
- WebDAV 恢复当前是“二次确认 -> 下载 -> resolve -> restore”，确认发生在验证之前。
- UI 只能展示恢复成功 / 失败结果，不能在覆盖恢复前展示 Board / Note / Image Note / 图片文件摘要。

## 3. 目标

### 3.1 新增只读验证入口

新增 Rust 命令：

```text
validate_local_backup(source_zip_path) -> BackupValidationResult
```

该命令只读 zip，不修改当前本地数据、WAL、`data.json`、`attachments/` 或前端状态。

### 3.2 结构化验证结果

新增结构：

```ts
type BackupValidationResult = {
  ok: boolean
  summary?: BackupSummary
  errors: BackupValidationIssue[]
  warnings: BackupValidationIssue[]
}

type BackupSummary = {
  app: string
  formatVersion: number
  appVersion: string
  createdAt: number
  noteCount: number
  boardCount: number
  imageNoteCount: number
  textNoteCount: number
  trashNoteCount: number
  imageFileCount: number
  imageFileTotalBytes: number
}

type BackupValidationIssue = {
  code: string
  severity: 'error' | 'warning'
  message: string
  target?: 'backup_file' | 'zip' | 'manifest' | 'data' | 'image_file' | 'zip_entry'
  path?: string
  noteId?: string
  imageFileId?: string
}
```

`createdAt` 沿用现有 `manifest.created_at` 的时间单位，不在 `v1.5.2` 做单位转换。当前为毫秒级 Unix 时间戳，前端只负责格式化展示。

`ok` 等价于 `errors.length === 0`。只有 `warnings`、没有 `errors` 时，`ok: true`，可以展示摘要并允许用户继续恢复。第一版可以暂不产生 `warnings`，但保留字段作为后续兼容扩展。

### 3.3 恢复前摘要

本地 zip 恢复与 WebDAV 远端恢复都应在覆盖恢复前展示摘要：

- 备份创建时间。
- 应用版本。
- 备份格式版本。
- Board 数。
- Note 数。
- Text Note 数。
- Image Note 数。
- Trash 中 Note 数。
- 图片文件数。
- 图片文件总大小。

摘要不展示便签正文内容。

摘要统计来源必须明确：

- `textNoteCount`、`imageNoteCount`、`trashNoteCount` 从已通过 `StorageData` 契约校验的 `data.json` 统计。
- `imageFileCount` 来自已校验的 manifest 图片文件条目。
- `imageFileTotalBytes` 使用已通过 size / hash 校验的 manifest `size` 汇总。
- 摘要生成不得读取或返回便签正文内容。

### 3.4 远端恢复前验证

远端恢复流程调整为：

1. 用户选择远端备份。
2. 应用下载到受控临时位置。
3. 使用 download token resolve 本地路径。
4. 执行 `validateLocalBackup(localPath)`。
5. 验证通过后展示摘要与二次确认。
6. 用户确认后调用 `restoreLocalBackup(localPath)`。
7. 成功、失败、取消都清理 download token。

## 4. 非目标

本版本不做：

- 不改变 zip 文件结构。
- 不递增 `BACKUP_FORMAT_VERSION`。
- 不浏览或展示备份包内便签正文。
- 不做便签级恢复。
- 不合并当前数据与备份数据。
- 不自动下载远端备份。
- 不自动恢复。
- 不新增定时备份。
- 不新增 WebDAV 同步或多端合并语义。
- 不引入通用文件管理能力。

## 5. 业务边界决策

### 5.1 验证复用恢复校验，但不进入写入阶段

`validate_local_backup` 应尽量复用 `restore_local_backup_inner` 现有的 zip entry、manifest、`StorageData` 契约、图片文件 hash 和大小校验逻辑。

但验证命令必须停在“校验与摘要”阶段，不进入 staging 目录写入、不替换当前 `data.json` 或 `attachments/`。

`validate_local_backup` 的通过 / 失败边界必须与现有 `restore_local_backup` 保持一致；现有恢复支持的旧数据兼容路径，例如缺少 `kind` 的旧 Text Note，不得在验证阶段被误判为 `invalid_data`。

### 5.2 结构化错误优先于字符串

现有恢复错误可以继续返回 `String`，但 `v1.5.2` 新增验证命令必须返回结构化 `BackupValidationIssue`。

第一批稳定错误码：

- `not_sonotes_backup`
- `unreadable_backup_file`
- `invalid_zip`
- `missing_manifest`
- `invalid_manifest`
- `unsupported_format_version`
- `missing_data`
- `invalid_data`
- `invalid_zip_entry`
- `duplicate_zip_entry`
- `missing_image_file`
- `image_file_unreadable`
- `image_file_hash_mismatch`
- `image_file_size_mismatch`
- `zip_size_limit_exceeded`
- `image_file_count_limit_exceeded`
- `image_file_total_size_limit_exceeded`

### 5.3 Hash 校验不改变备份格式

当前 `BackupManifest.attachments` 已包含 `sha256`，因此 `v1.5.2` 可以验证图片文件内容 hash。

如果未来遇到旧备份包缺少 hash 字段，应作为 `invalid_manifest` 或兼容策略另行规划；本版本不新增格式扩展。

### 5.4 Manifest 与 zip 错误码固定映射

结构化错误码必须稳定，不使用“或”：

- 备份文件无法打开或无权限：`unreadable_backup_file`
- 文件可打开但不是合法 zip：`invalid_zip`
- `unreadable_backup_file` 的 `target` 为 `backup_file`
- `invalid_zip` 与 zip 整体大小限制的 `target` 为 `zip`
- `manifest.json` 缺失：`missing_manifest`
- `manifest.json` 不是合法 JSON 或字段契约不合法：`invalid_manifest`
- `manifest.app !== "SoNotes"`：`not_sonotes_backup`
- `manifest.formatVersion` 不支持：`unsupported_format_version`
- `data.json` 缺失：`missing_data`
- `data.json` 不是合法 JSON 或不满足 `StorageData` 契约：`invalid_data`
- 重复的 `manifest.json`、`data.json` 或图片文件 entry：`duplicate_zip_entry`
- `invalid_zip_entry` 与 `duplicate_zip_entry` 的 `target` 为 `zip_entry`

### 5.5 验证失败不阻止用户继续选择其他备份

验证失败时：

- 不修改当前本地数据。
- 不调用恢复命令。
- 本地 zip 流程保持在数据管理区。
- WebDAV 流程必须清理已下载临时文件。
- UI 展示结构化失败原因的用户友好文案。

### 5.6 确认发生在验证之后

本地恢复和远端恢复的“覆盖恢复确认”应在验证成功、摘要可见之后出现。

原因：

- 用户应先知道将恢复什么。
- 验证失败时不应出现“是否覆盖当前数据”的惊吓确认。
- 远端恢复下载失败或校验失败时不应进入恢复确认。

## 6. 技术设计

### 6.1 Rust 类型

建议在 `src-tauri/src/backup.rs` 中新增：

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct BackupValidationResult {
    pub ok: bool,
    pub summary: Option<BackupSummary>,
    pub errors: Vec<BackupValidationIssue>,
    pub warnings: Vec<BackupValidationIssue>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct BackupSummary {
    pub app: String,
    pub format_version: u32,
    pub app_version: String,
    pub created_at: u64,
    pub note_count: u32,
    pub board_count: u32,
    pub text_note_count: u32,
    pub image_note_count: u32,
    pub trash_note_count: u32,
    pub image_file_count: u32,
    pub image_file_total_bytes: u64,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct BackupValidationIssue {
    pub code: String,
    pub severity: String,
    pub message: String,
    pub target: Option<String>,
    pub path: Option<String>,
    pub note_id: Option<String>,
    pub image_file_id: Option<String>,
}
```

`severity` 第一版可用字符串 `"error"` / `"warning"`，避免额外 enum 序列化复杂度。

### 6.2 Rust 校验函数拆分

当前 `restore_local_backup_inner` 同时承担：

- 打开 zip。
- 读取并校验 entry。
- 解析 manifest。
- 解析 data。
- 收集图片文件内容。
- 校验 `StorageData` 契约。
- 写入 staging。
- 替换本地数据。

`v1.5.2` 建议抽出只读检查阶段，但验证流程不应为了生成摘要长期持有所有图片文件内容。当前恢复流程可以继续读取图片内容写入 staging；验证流程应优先采用“读取 -> 计算 hash / size -> 丢弃内容”的方式。

建议结构：

```rust
struct InspectedBackup {
    manifest: BackupManifest,
    data: StorageDataForRestore,
    image_entries: Vec<ValidatedImageFileEntry>,
    summary: BackupSummary,
}

struct ValidatedImageFileEntry {
    zip_entry_path: String,
    sha256: String,
    size: u64,
}

fn inspect_backup_zip(source: &Path) -> Result<InspectedBackup, Vec<BackupValidationIssue>>
```

如果为了最小改动，第一版仍复用当前恢复逻辑中的 `HashMap<String, Vec<u8>>`，必须在 commit 中明确这是临时复用选择，并保留后续改为流式验证的空间。

无论采用哪种实现，恢复流程的现有行为和错误文案都不应在 `Commit 3` 中改变。

### 6.3 前端服务层

`src/services/backup/BackupService.ts` 新增：

```ts
export interface BackupSummary { ... }
export interface BackupValidationIssue { ... }
export interface BackupValidationResult { ... }

export async function validateLocalBackup(sourceZipPath: string): Promise<BackupValidationResult> {
  return invoke<BackupValidationResult>('validate_local_backup', { sourceZipPath });
}
```

服务层不做业务判断，只保持 Tauri 命令薄封装。

### 6.4 本地恢复 UI

`BoardDock.tsx` 本地恢复流程调整为：

1. `openZipDialog()`。
2. `validateLocalBackup(sourceZipPath)`。
3. 若 `ok === false`，展示错误，不调用 `restoreLocalBackup`。
4. 若 `ok === true`，展示摘要并二次确认。
5. 用户确认后执行现有 flush / pause / restore / apply / resume 顺序。

本版本可以继续使用 `window.confirm` 展示摘要；如果文案过长，再拆成 UI 面板，不作为第一版硬要求。

### 6.5 WebDAV 远端恢复 UI

当前 WebDAV 恢复在下载前就二次确认。`v1.5.2` 调整为：

1. 用户点击远端备份恢复。
2. 先提示“将下载并验证远端备份”，或直接进入下载状态。
3. 下载成功后 resolve token。
4. 调用 `validateLocalBackup(localPath)`。
5. 验证失败：展示错误并 cleanup token。
6. 验证成功：展示摘要与覆盖恢复确认。
7. 用户取消：cleanup token，不调用恢复。
8. 用户确认：执行现有恢复流程。

### 6.6 文案

验证失败文案示例：

- “这不是 SoNotes 备份包，本地数据未受影响。”
- “备份文件缺少 manifest.json，本地数据未受影响。”
- “备份包中的图片文件校验失败，本地数据未受影响。”
- “备份包超过允许大小，本地数据未受影响。”

验证成功确认文案示例：

```text
备份验证通过。

将恢复：
3 个看板
42 条便签（文本 36，图片 6）
2 条废纸篓便签
6 个图片文件

当前本地数据将被替换。是否继续？
```

## 7. 测试计划

### 7.1 Rust 测试

新增或调整 `src-tauri/src/backup.rs` 测试：

- 验证成功：无图片文件。
- 验证成功：包含 Image Note 与图片文件 hash。
- 验证成功：包含 Trash 中 Image Note。
- 必测：`source_zip_path` 指向不存在路径时返回 `unreadable_backup_file`。
- 可选或平台条件测试：无权限文件返回 `unreadable_backup_file`，避免 Windows / CI 权限模型差异导致测试不稳定。

- 图片文件 hash 不匹配返回 `image_file_hash_mismatch`。
- 图片文件总大小超限返回 `image_file_total_size_limit_exceeded`。
- 验证命令对损坏 zip、缺 manifest、缺 data、hash mismatch 等失败都不创建 staging 目录、不修改当前 `data.json` 或 `attachments/`。

### 7.3 BoardDock 交互测试

## 10. 风险与注意事项

- `restore_local_backup_inner` 已有大量安全测试，抽取只读检查阶段时必须避免改变恢复行为。
- `validate_local_backup` 应返回结构化失败结果，而不是复用恢复命令的字符串错误作为 UI 唯一依据。
- 远端恢复确认后移会改变用户感知流程，需要明确展示“正在下载 / 正在验证 / 等待确认 / 正在恢复”。
- WebDAV 下载 token 必须在取消、失败和成功后清理。
- 摘要不得展示备份包正文内容，避免把本版本扩大成备份浏览器。
- hash 校验使用现有 manifest `sha256`，不递增备份格式版本。

---

## 11. 一句话总结

`v1.5.2` 只做一件事：在本地与远端恢复真正覆盖当前数据之前，先用只读方式验证备份包、生成结构化摘要和错误结果，让用户知道“这个备份能不能安全恢复”，同时不改变 zip 格式、不引入同步语义、不扩大为备份内容浏览或便签级恢复。
