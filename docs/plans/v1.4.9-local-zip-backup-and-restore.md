# SoNotes v1.4.9 实施计划：本地 zip 备份 / 恢复

---

## 1. 背景

`v1.4.8` 已经补齐独立 **Image Note（图片便签）**、图片文件本地预览、缺失占位以及孤儿图片文件扫描 / 清理能力。当前 SoNotes 的本地数据由 `data.json` 与 `attachments/` 共同组成：`data.json` 保存 **Domain state（领域状态）** 与图片文件引用，图片文件本体存放在本地 `attachments/` 目录中。

`v1.4.9` 的主题是“本地 zip 备份 / 恢复”。本版本要建立稳定、可验证、面向后续 WebDAV 远端备份的本地备份包格式，让用户可以手动导出一个带时间戳的 zip 快照，并在需要时从该快照恢复本地数据。

本版本只做本地备份与恢复，不引入远端能力，不承诺同步，不做多端合并。

---

## 2. 目标

### 2.1 本地备份包格式

- 生成带时间戳的备份文件：`SoNotes_Backup_<timestamp>.zip`。
- 备份包必须包含当前 `data.json`。
- 备份包必须包含当前 **Domain state** 中被引用的图片文件。
- 备份包必须包含 `manifest.json`，用于描述备份版本、生成时间、数据版本、文件清单与校验信息。
- 不把图片文件二进制、base64、绝对路径或 asset URL 写入 `data.json`。

### 2.2 手动备份入口

- 用户通过明确入口触发本地备份。
- 用户选择 zip 保存位置。
- 创建 zip 前必须先确保当前运行时最新 **Domain state** 已进入备份输入，不能只依赖磁盘上可能滞后的 `data.json`。
- 第一版可选两种实现之一：先触发并等待 `flushPersistNow` / `saveToDisk` 成功，再由 Rust 读取磁盘快照；或由前端把已序列化的当前 `StorageData` 传给 Rust 作为打包输入。
- 备份过程中应展示“正在备份 / 备份完成 / 备份失败”状态或提示。
- 备份失败不得影响当前本地保存数据。

### 2.3 本地恢复入口

- 用户通过明确入口选择一个本地 zip 备份包。
- 恢复前必须校验备份包结构。
- 恢复前必须校验 `manifest.json` 与 `data.json` 的可读性。
- 恢复前必须校验被引用图片文件是否存在于备份包中。
- 恢复必须由用户确认，不能自动覆盖当前数据。

### 2.4 恢复失败回滚

- 恢复过程必须逐条校验 zip entry 路径后再写入临时目录，不能先完整解包再校验。
- 完整校验通过后，才允许替换当前本地数据。
- 替换过程失败时，应尽量保留或恢复原有本地数据。
- 恢复失败不得留下半导入的 `data.json` 或半替换的 `attachments/` 状态。
- 恢复成功后，前端内存态、WAL、自动持久化队列、Undo/Redo 历史、选择态与图片资源缓存都必须进入与恢复快照一致的状态。

### 2.5 兼容图片便签与图片文件引用

- 备份应按完整 **Domain state** 收集被引用图片文件，包括位于 **Trash（废纸篓）** 中的便签。
- 同一图片文件被多张图片便签引用时，备份包中只需要保存一份文件。
- 恢复后，图片便签应继续通过图片文件引用展示本地图片文件。
- 图片文件内容 SHA-256 必须与图片文件引用中的 `hash` 一致，`relativePath` 文件名主体也必须与该 hash 一致。
- 缺失或异常图片文件应在恢复校验阶段暴露，不应静默生成损坏数据。

---

## 3. 非目标

本次不做以下能力：

- **WebDAV 远端备份**：不连接、上传、下载或列出远端备份。
- **在线同步**：不实现实时同步、自动拉取覆盖、多端合并或便签级冲突解决。
- **自动定时备份**：第一版只做用户手动触发。
- **增量备份**：每次备份都是完整快照。
- **备份包内编辑**：不提供浏览、修改或合并备份包内容的能力。
- **永久删除撤销**：恢复备份不是永久删除的撤销机制。
- **泛文件管理**：不引入图片文件以外的用户可见文件管理能力。
- **远端运行时数据源**：应用运行时数据源仍是本地存储，不从 zip 或远端直接运行。

## 4. 备份包格式

### 4.1 文件命名

备份文件名格式：

```text
SoNotes_Backup_<timestamp>.zip
```

建议时间戳使用本地时间并保持文件名安全：

```text
SoNotes_Backup_2026-06-08_213000.zip
```

### 4.2 zip 根目录结构

```text
data.json
manifest.json
attachments/
```

说明：

- `data.json`：当前本地领域数据快照。
- `manifest.json`：备份包元数据与校验信息。
- `attachments/`：被当前领域数据引用的图片文件集合；如果没有图片文件引用，可以为空或不存在。

### 4.3 manifest.json 建议结构

```ts
type BackupManifest = {
  app: 'SoNotes'
  backupFormatVersion: 1
  createdAt: string
  schemaVersion: number
  dataFile: {
    path: 'data.json'
    size: number
    sha256: string
  }
  attachments: Array<{
    relativePath: string
    size: number
    sha256: string
  }>
}
```

约束：

- `createdAt` 使用 ISO 8601 字符串。
- `relativePath` 必须是 `attachments/<filename>` 形态，不能包含绝对路径或路径穿越片段。
- `sha256` 用于恢复前校验文件内容。
- `schemaVersion` 来自当前 `data.json` 的持久化数据版本。

## 5. 业务边界决策

### 5.1 备份是完整快照

每次备份都生成一个完整 zip 快照，不覆盖旧备份，不做增量链。

原因：

- 用户可以清楚选择某个时间点恢复。
- 本地 zip 格式更容易验证和迁移到后续 WebDAV 远端备份。
- 避免第一版引入增量链断裂、跨包依赖和恢复顺序风险。

### 5.2 恢复是明确覆盖动作

恢复表示用户选择一个备份快照，并将本地数据恢复到该快照描述的状态。

- 恢复前必须提示当前数据会被替换。
- 恢复不是合并，不尝试保留当前未备份的新便签。
- 恢复不解决多端冲突。

### 5.3 Trash 中的图片文件引用必须进入备份

位于 **Trash（废纸篓）** 中的便签仍属于完整 **Domain state**，其引用的图片文件必须进入备份。

原因：

- 用户恢复后仍可能从废纸篓还原这些便签。
- 如果跳过 Trash 引用，恢复后会产生本不该缺失的图片文件。

### 5.4 备份不清理孤儿图片文件

备份只收集当前领域数据仍引用的图片文件，不把孤儿图片文件打入备份包。

- 孤儿图片文件清理仍由 v1.4.8 的明确清理入口负责。
- 备份过程不自动删除本地孤儿图片文件。
- 备份过程不修改 Undo/Redo 历史。

### 5.5 恢复校验优先于写入

恢复必须先完成全部校验，再进入写入阶段。

校验失败时：

- 不修改当前 `data.json`。
- 不替换当前 `attachments/`。
- 给出明确失败原因，例如结构缺失、JSON 不合法、文件校验失败或版本不兼容。

### 5.6 备份输入必须来自最新运行时状态

创建备份时不能默认认为磁盘 `data.json` 一定是最新状态。

原因：

- 用户刚完成的编辑、移动、图片便签创建或废纸篓操作可能仍在内存态、防抖保存队列或 WAL 中。
- 如果 Rust 直接读取滞后的 `data.json`，会生成缺少最新操作的备份包。
- 本地备份是用户主动要求的可信快照，必须以触发备份时的最新 **Domain state** 为准。

实现前必须二选一并写入代码注释或测试名称：

1. 前端先调用并等待 `flushPersistNow` / `saveToDisk` 成功，再调用 Rust 侧 `create_local_backup(target_path)` 读取磁盘快照。
2. 前端直接序列化当前 `StorageData` 并传给 Rust，Rust 使用该输入生成 `data.json` 与 `manifest.json`，不再把磁盘 `data.json` 作为唯一来源。

若刷新持久化失败，备份必须失败并提示用户，不能用旧磁盘数据继续打包。

### 5.7 恢复是整个本地快照替换

恢复应把本地数据恢复到备份包描述的快照，而不是在当前数据目录上做覆盖式合并。

- `data.json` 应替换为备份包中的 `data.json`。
- `attachments/` 应替换为备份包声明的图片文件集合。
- 恢复不保留当前快照之外的旧孤儿图片文件。
- 恢复后如需要清理图片资源 URL 缓存，应统一失效并重新预水合。

### 5.8 恢复数据必须符合当前 StorageData 契约

备份包通过 hash 校验只说明文件未被篡改，不说明 `data.json` 是当前应用可接受的领域数据。

恢复前必须对 `data.json` 执行完整 `StorageData` 契约校验：

- `schemaVersion` 必须是当前支持版本。
- `boards` 必须存在且结构合法。
- `currentBoardId` 必须指向存在的 **Board（看板）**。
- `config` 必须符合当前配置结构，不能携带会破坏启动的异常值。
- `notes` 必须是合法 **Note（便签）** 集合。
- `note.kind` 必须严格为 `'text' | 'image'`。
- **Text Note（文本便签）** 不得保留图片文件引用。
- **Image Note（图片便签）** 必须包含合法图片文件引用。
- **Trash（废纸篓）** 中的便签同样必须满足上述结构约束。

校验失败时必须拒绝恢复，并提示备份数据结构不兼容或已损坏。

### 5.9 自动持久化控制必须有明确入口

恢复流程需要暂停自动持久化、刷新当前数据并恢复持久化能力。实现前必须明确谁拥有这个控制权。

可选方案：

1. 新增统一 persistence coordinator，把 `flush`、`pauseAutosave`、`resumeAutosave`、`replaceStateFromRestore` 收口到同一门面。
2. 暴露受控的 `pause / resume / flush` 持久化门面给数据管理区使用，避免 `BoardDock` 直接依赖 `Canvas` 内部 ref。

不允许让“从 zip 覆盖恢复”按钮绕过自动持久化控制直接调用 Rust 恢复命令，否则 pending autosave 可能把恢复前的旧状态写回磁盘。

## 6. 技术设计

### 6.1 Rust 侧备份命令

建议在 Rust 侧新增本地备份命令，避免前端处理 zip、文件读取和校验细节。

建议命令：

```rust
create_local_backup(target_path: String) -> BackupResult
```

职责：

- 在采用“先 flush 再备份”方案时，读取当前存储目录中已确认落盘的 `data.json`。
- 在采用“前端传入 StorageData”方案时，接收已序列化数据并用它生成 zip 内的 `data.json`。
- 解析并收集被引用图片文件相对路径。
- 计算 `data.json` 与图片文件的 SHA-256。
- 生成 `manifest.json`。
- 写入 zip 到用户选择的目标路径。
- 失败时返回结构化错误。

硬约束：

- 不允许在未确认最新 **Domain state** 已进入备份输入时读取磁盘旧 `data.json` 打包。
- 同秒连续备份也不能产生相同目标文件名；如默认文件名冲突，应追加更高精度时间或短随机后缀。

### 6.2 Rust 侧恢复命令

建议新增恢复命令：

```rust
restore_local_backup(source_zip_path: String) -> RestoreResult
```

职责：

- 打开用户选择的 zip。
- 逐条读取 zip entry，先校验规范化路径，再写入临时目录。
- 校验 `manifest.json`、`data.json` 与 `attachments/`。
- 校验 `data.json` 中图片文件引用与备份包内文件一致。
- 校验通过后，以安全替换策略写入本地存储目录，并整体替换 `attachments/` 快照。
- 失败时清理临时目录并保持当前数据不变。

路径安全要求：

- zip entry 只允许 `data.json`、`manifest.json` 或 `attachments/<filename>`。
- 必须拒绝绝对路径、盘符路径、`..`、空路径、目录穿越、反斜杠绕过和规范化后越界的路径。
- 校验必须发生在写入临时目录之前，避免 Zip Slip。

### 6.3 前端入口

前端建议在现有数据管理区域增加两个明确按钮，并同时梳理旧 JSON 入口文案：

- “导出 JSON”
- “导入 JSON”
- “创建本地 zip 备份”
- “从 zip 覆盖恢复”

交互要求：

- 创建本地 zip 备份时打开保存文件对话框。
- 从 zip 覆盖恢复时打开选择文件对话框，只允许选择 `.zip`。
- 恢复前弹出确认文案，明确“当前本地数据将被替换”。
- JSON 导入 / 导出入口不得复用 zip 覆盖恢复文案，避免用户误解旧 JSON 导入与新 zip 恢复的语义。
- 备份和恢复过程应避免重复点击触发并发操作。

接线要求：

- 数据管理区只能调用受控的持久化门面或统一 coordinator，不能直接操作 `Canvas` 内部保存句柄。
- 恢复入口必须能按顺序执行：flush 当前状态、暂停自动持久化、调用恢复命令、替换前端状态、清理运行态、恢复自动持久化。
- 如无法取得自动持久化暂停能力，恢复入口不得启用。

### 6.4 安全写入策略

恢复阶段建议采用临时目录与原子替换思路：

1. 暂停或屏蔽自动持久化触发，避免恢复期间旧内存态回写。
2. 逐条读取 zip entry，先校验路径，再写入临时目录。
3. 完整校验临时目录中的 `data.json`、`manifest.json` 与 `attachments/`。
4. 将当前本地数据目录备份为临时回滚副本，或先写入新的 staged 数据目录。
5. 校验通过后替换当前 `data.json`，并将 `attachments/` 作为完整快照整体 swap。
6. 清空或重写 WAL 与批处理确认状态，避免旧 WAL 在下次启动时覆盖恢复结果。
7. 替换前端内存态，清空 Undo/Redo 历史、选择态和临时 UI 状态，并刷新图片资源缓存。
8. 替换失败时使用回滚副本恢复。
9. 成功后清理临时目录与回滚副本，并恢复自动持久化。

### 6.5 与启动仲裁的关系

恢复完成后应确保后续启动仲裁不会把旧 WAL 或旧快照错误恢复回来。

要求：

- 恢复写入成功后，当前本地持久化数据应成为最新可信数据。
- 如项目存在 WAL 或批处理确认文件，应同时更新或清理相关状态，避免恢复后被旧数据覆盖。
- 恢复完成后前端应重新加载领域数据，而不是继续使用恢复前的内存状态。
- 恢复期间 pending autosave 不得把恢复前的旧状态写回磁盘。
- 恢复完成后应清空 Undo/Redo 历史与当前选择态，避免历史命令或选区引用恢复前的便签对象。
- 恢复完成后应让图片文件路径缓存与 asset URL 缓存失效，并按恢复后的图片便签重新预水合。

## 7. 校验与错误处理

### 7.1 备份前校验

- 备份输入必须来自触发备份时的最新 **Domain state**。
- 如果采用 flush 方案，`flushPersistNow` / `saveToDisk` 必须成功，且当前 `data.json` 必须可读取。
- 图片文件引用的 `relativePath` 必须合法。
- 被引用图片文件不存在时，应允许备份失败并给出缺失文件提示；是否允许“带缺失引用备份”需在实现前明确，不建议第一版允许。

### 7.2 恢复前校验

恢复前必须检查：

- zip 文件可读取。
- 每个 zip entry 在写入临时目录前都通过路径白名单与规范化校验。
- 根目录存在 `manifest.json`。
- 根目录存在 `data.json`。
- `manifest.json` 可解析且 `app === 'SoNotes'`。
- `backupFormatVersion` 为当前支持版本。
- `data.json` SHA-256 与 manifest 一致。
- `data.json` 必须通过当前 `StorageData` 契约校验，包括 `schemaVersion`、`boards`、`currentBoardId`、`config`、`notes`、`note.kind` 与 Trash 中便签结构。
- **Text Note（文本便签）** 不得携带图片文件引用；**Image Note（图片便签）** 必须携带合法图片文件引用。
- manifest 中列出的每个图片文件都存在且 SHA-256 一致。
- `data.json` 中的图片文件引用不能指向 manifest 未声明的文件。
- 每个图片文件引用的 `hash` 必须等于对应文件内容 SHA-256。
- 每个图片文件引用的 `relativePath` 文件名主体必须与 `hash` 一致，保持内容寻址模型可验证。
- 所有相对路径均不能越出 `attachments/`。
- zip 中不得包含 manifest 未声明的额外 `attachments/` 文件；如存在，应拒绝或在实现前明确忽略策略，第一版建议拒绝。

### 7.3 失败提示

失败提示应面向用户表达为：

- “备份文件结构不完整”
- “备份文件校验失败”
- “备份版本暂不支持”
- “备份数据结构不兼容”
- “图片文件缺失或损坏”
- “恢复失败，当前数据未被修改”
- “备份前保存当前数据失败”
- “备份文件包含非法路径”

## 8. 测试计划

### 8.1 Rust 单元测试

- 生成包含 `data.json`、`manifest.json` 与图片文件的 zip。
- 没有图片文件引用时仍能生成有效 zip。
- 重复图片文件引用只打包一次。
- 同秒连续备份文件名不冲突。
- manifest 中 SHA-256 与实际文件一致。
- 恢复非法 zip 失败且不修改现有数据。
- 恢复缺失 `manifest.json` 的 zip 失败。
- 恢复缺失图片文件的 zip 失败。
- 恢复 SHA-256 不匹配的 zip 失败。
- 恢复 `StorageData` 契约不合法的 zip 失败，包括缺失 board、`currentBoardId` 指向不存在看板、非法 `note.kind`、文本便签携带图片文件引用。
- 图片文件内容 SHA-256 与图片文件引用 `hash` 不一致时恢复失败。
- 图片文件 `relativePath` 文件名主体与图片文件引用 `hash` 不一致时恢复失败。
- 路径穿越条目被拒绝。
- 含反斜杠路径、绝对路径、盘符路径和规范化后越界路径的 zip entry 被拒绝且不会写出临时目录。
- 恢复时 `attachments/` 作为完整快照替换，旧快照中但新备份未声明的图片文件不会残留。

### 8.2 前端测试

- 数据管理区展示“导出 JSON”“导入 JSON”“创建本地 zip 备份”“从 zip 覆盖恢复”入口。
- 点击创建备份会打开保存文件对话框并调用备份命令。
- 点击恢复会打开文件选择对话框并在执行前二次确认。
- 从 zip 覆盖恢复确认文案明确说明当前本地数据将被替换。
- JSON 导入入口不使用 zip 覆盖恢复文案。
- 数据管理区通过受控持久化门面或统一 coordinator 暂停、恢复自动持久化，不直接依赖 `Canvas` 内部 ref。
- 无法取得自动持久化控制能力时，从 zip 覆盖恢复入口不可执行并给出提示。
- 备份 / 恢复过程中按钮禁用，避免并发触发。
- 备份成功、备份失败、恢复成功、恢复失败都有明确提示。

### 8.3 集成验证

- 创建含文本便签、图片便签和 Trash 中图片便签的数据。
- 生成本地备份 zip。
- 清空或修改当前数据。
- 从 zip 恢复。
- 验证看板、便签、废纸篓、图片便签和图片预览恢复一致。
- 在存在未落盘脏数据时创建备份，验证备份包含最新编辑。
- 恢复后重启应用，验证旧 WAL 不会覆盖恢复结果。
- 恢复期间存在 pending autosave 时，验证旧内存态不会回写覆盖恢复数据。
- 恢复入口从数据管理区触发时，验证持久化门面调用顺序为 flush、pause、restore、replace state、cleanup runtime state、resume。

## 9. 验收标准

- 能手动生成 `SoNotes_Backup_<timestamp>.zip`。
- 创建备份前会确保最新运行时领域数据进入备份输入；保存刷新失败时不会打旧快照。
- zip 包含 `data.json`、`manifest.json` 和被引用图片文件。
- 同一天多次备份不会互相覆盖。
- 同秒连续备份默认文件名不会冲突。
- 没有图片便签的数据也能正常备份与恢复。
- 含图片便签的数据恢复后，图片文件引用与本地预览保持可用。
- Trash 中便签引用的图片文件会被备份并能恢复。
- 结构不完整、JSON 不合法、校验不匹配或版本不兼容的备份包会被拒绝。
- `StorageData` 契约不合法的备份包会被拒绝。
- 图片文件引用 `hash`、文件内容 SHA-256 与 `relativePath` 文件名主体不一致的备份包会被拒绝。
- 恶意 zip 条目不会写出临时目录。
- 恢复会整体替换 `attachments/` 快照，不遗留当前快照之外的旧图片文件。
- 恢复成功后旧 WAL、pending autosave、Undo/Redo 历史、选择态和图片缓存不会把应用带回恢复前状态。
- 恢复失败时当前本地数据不被破坏。
- 从 zip 覆盖恢复入口必须通过受控持久化门面或统一 coordinator 暂停并恢复自动持久化。
- 数据管理区文案能区分旧 JSON 导入 / 导出与新 zip 覆盖恢复。
- 文案只使用“备份 / 恢复”，不把该能力描述为“同步”。

## 10. 建议实施顺序

1. 定义备份输入来源策略：flush 后读磁盘，或前端传入序列化 `StorageData`。
2. 定义自动持久化控制入口：统一 coordinator 或受控 `pause / resume / flush` 门面。
3. 定义 `manifest.json` 类型、`StorageData` 契约校验与图片文件 hash 校验规则。
4. 实现 Rust 侧 zip 创建能力。
5. 实现 Rust 侧 zip entry 路径白名单校验与安全临时写入。
6. 实现安全恢复写入、`attachments/` 整体 swap 与失败回滚。
7. 处理恢复期间自动持久化、WAL、前端内存态、Undo/Redo、选择态与图片缓存刷新。
8. 接入前端数据管理区入口，并区分 JSON 导入 / 导出与 zip 覆盖恢复文案。
9. 补齐备份、恢复、失败路径、Zip Slip、WAL/autosave、`StorageData` 契约与图片文件引用测试。
10. 更新 README 与 CHANGELOG 的 v1.4.9 发布口径。

## 11. 与 v1.4.10 的边界

`v1.4.10` 可以在本版本备份包格式之上实现 WebDAV 远端备份，但不得反向要求 `v1.4.9` 承担远端语义。

本版本产出的 zip 备份包应可作为未来 WebDAV 上传 / 下载的文件单元，但当前只处理本地文件选择、本地 zip 创建和本地 zip 恢复。
