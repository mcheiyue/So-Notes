# SoNotes v1.5.8 实施计划：备份活动日志与可观测性

---

## 1. 背景

`v1.5.6` 已经完成定时远端备份基础，把自动 / 手动 / 退出前远端备份的最近结果写入本地状态。

`v1.5.7` 已经完成远端备份保留与清理，把健康基线、断崖式下降保护、最近清理结果和手动清理预览接入到 WebDAV 设置区。

现在的问题不再是“有没有状态”，而是：

- 用户只能看到最近一次或少量聚合状态，无法回看一串操作。
- 本地备份、恢复、远端列表、删除、自动备份、保留清理分别散在不同 UI feedback 中。
- 出现失败时，用户不知道是配置、凭据、flush、上传、验证、清理还是恢复阶段出错。
- 后续进入 `v1.5.9` / `v1.6.0` 前，需要一个足够轻的本地可观测性基础，帮助排查备份链路问题。

`v1.5.8` 的目标是：**把关键备份 / 恢复 / WebDAV 操作记录为本地、脱敏、有上限的活动日志，并在数据管理区展示最近活动。**

这不是遥测系统，也不是审计系统。日志不上传，不记录凭据，不记录便签正文。

### 2.2 当前缺口

- 没有完整活动历史列表。
- `ScheduledRemoteBackupState` 只适合“最近状态”，不适合继续横向扩成历史表。
- 本地备份 / 本地恢复没有历史记录。
- WebDAV 列表、下载、删除、恢复没有统一的结构化历史记录。
- 自动备份的 `success` / `failed` / `skipped` 没有保留历史。
- 保留清理成功、部分失败、断崖保护触发目前只能从最近状态看，不能回看。
- `BoardDock.tsx` 内部反馈状态较多，继续直接散写日志容易让组件更重。
- 现有 `redactStateBeforeSave()` 只覆盖定时备份 state，不覆盖未来活动日志。
- 活动日志如果直接记录错误字符串，有泄漏 URL、Authorization、password、token 的风险。

### 2.3 代码边界

- 活动日志不要写入 `data.json`。
- 活动日志不要进入 domain store，也不要影响 undo / redo。
- 活动日志不要改变备份 / 恢复 / 删除的成功失败语义。
- 活动日志写入失败不应让原操作失败；最多在控制台或活动日志 UI 中降级提示。
- Rust 侧负责文件持久化和第二层脱敏，TS 侧负责根据业务上下文组装事件。
- `BoardDock` 可以新增小型展示组件和调用 helper，但本版本不做大规模 UI 架构迁移。
- `v1.5.5-use-store-dependency-map.md` 中提到的 `CanvasEngine` 拖拽落位迁移、旧 `useStore.ts` 删除评估，不并入本版本主线；`v1.5.8` 只处理活动日志所需的局部备份服务边界。

## 3. 版本目标

`v1.5.8` 应完成：

- 新增本地备份活动日志持久化文件。
- 新增前端 `BackupActivityLogService`，统一 append / load / clear / redact。
- 记录最近若干条关键活动，至少覆盖：
  - 创建本地 zip 备份。
  - 从本地 zip 恢复。
  - 创建远端备份。
  - 刷新远端备份列表。
  - 删除远端备份。
  - 从远端备份恢复。
  - 自动远端备份成功 / 失败 / 跳过。
  - 保留策略清理成功 / 部分失败 / 跳过。
  - 断崖式下降保护触发。
  - WebDAV 凭据缺失、凭据读取失败或会话降级类原因。
- 数据管理 / WebDAV 设置区展示最近 10 条活动。
- 活动日志有上限、有脱敏、有结构化错误分类。
- 提供清空活动日志入口。

## 4. 非目标

本版本不做：

- 不上传活动日志。
- 不生成远端诊断报告。
- 不记录便签正文、看板名称、图片内容、绝对本地路径。
- 不记录密码、应用令牌、Authorization header、带凭据 URL、下载 token。
- 不引入复杂查询、过滤、导出或搜索。
- 不把活动日志作为合规审计能力。
- 不改变备份文件格式。
- 不改变 WebDAV 协议兼容范围。
- 不做自动恢复、同步、合并或冲突解决。
- 不把 `ScheduledRemoteBackupState` 改造成历史日志表。

## 5. 版本决策

### 5.1 活动日志独立持久化

新增独立文件：

```text
backup-activity-log.json
```

存放在 `app_config_dir()` 下，和以下文件同级：

- `webdav-config.json`
- `webdav-scheduled-backup-config.json`
- `webdav-scheduled-backup-state.json`

原因：

- 活动日志是应用配置 / 诊断数据，不属于用户便签数据。
- 不应影响 `data.json` 的保存、备份、恢复和 undo / redo。
- 可以复用 Rust 侧 app config 目录和原子写入经验。

### 5.2 Rust 持久化，TS 组装事件

建议新增 Rust 模块：

```text
src-tauri/src/backup_activity.rs
```

Rust 提供命令：

```rust
backup_activity_list
backup_activity_append
backup_activity_clear
```

TS 新增服务：

```text
src/services/backup/BackupActivityLogService.ts
```

TS 负责：

- 根据当前操作组装 `operation` / `trigger` / `stage` / `summary` / `fileName`。
- 在 append 前做第一层脱敏。
- 给业务代码提供小而稳定的 helper。

Rust 负责：

- 原子读写 JSON 文件。
- 追加时裁剪最大条数。
- 解析失败时返回明确错误。
- append 前做第二层脱敏。
- 校验活动条目的稳定字段；如果前端输入缺少 `id` 或 `id` 为空，Rust 侧兜底生成。
- Rust 只在 `id` 缺失 / 为空时兜底，不覆盖 TS 传入的有效 `id`，避免 UI 侧引用与持久化结果不一致。

### 5.3 有界日志

持久化最多保留最近 `100` 条。

UI 默认展示最近 `10` 条。

原因：

- 足以排查最近的备份 / 恢复问题。
- 不需要日志轮转、分页和复杂清理。
- 避免频繁自动备份长期运行后无限增长。

### 5.4 操作成功与日志失败解耦

业务操作成功后，如果活动日志写入失败，不应把业务操作改成失败。

示例：

- 远端备份上传成功，但写日志失败：UI 仍显示备份成功。
- 远端清理部分失败，写日志失败：保留策略 state 仍按原逻辑保存。
- 本地恢复成功，写日志失败：不得回滚恢复。

日志写入失败可以：

- `console.warn()`。
- 下次打开活动日志区时显示“活动日志加载失败”。

### 5.5 最近状态继续存在

`ScheduledRemoteBackupState` 不删除。

它继续负责：

- 状态区快速展示。
- 自动备份调度判断。
- 凭据失败阈值。
- 健康基线与断崖保护状态。
- 保留策略最近结果。

活动日志负责：

- 回看历史。
- 解释最近几次发生了什么。
- 给失败阶段和脱敏错误摘要提供统一展示。

两者关系：

- 状态用于控制流程。
- 日志用于解释流程。

### 5.6 只记录文件名，不记录本地绝对路径

活动日志字段可以记录：

- `remoteFileName`
- `localFileName`
- `downloadedRemoteFileName`

不记录：

- `C:\Users\...\backup.zip`
- `D:\...\data.json`
- WebDAV 完整 URL
- 用户名
- download token

本地备份成功 UI 仍可在即时 feedback 中展示完整路径，但活动日志只保存 basename。

### 5.7 记录 skipped，但控制噪音

自动备份应记录关键跳过原因：

- `no-local-changes`
- `missing-config`
- `missing-credential`
- `credential-action-required`
- `single-flight`
- `retention-disabled`
- `retention-baseline-initialized`
- `retention-cliff-drop`

不记录纯调度延迟：

- 应用活跃导致等待 quiet period。
- 定时器重新安排下一次运行。

原因：

- 跳过结果回答“自动备份为什么没上传”。
- 延迟事件太密，会污染最近 10 条。

## 6. 活动日志数据模型建议

### 6.1 顶层文件结构

```ts
interface BackupActivityLogFile {
  readonly version: 1;
  readonly entries: BackupActivityEntry[];
}
```

### 6.2 活动条目

```ts
type BackupActivityOperation =
  | 'local-backup'
  | 'local-restore'
  | 'remote-backup'
  | 'remote-list'
  | 'remote-delete'
  | 'remote-restore'
  | 'scheduled-remote-backup'
  | 'retention-cleanup'
  | 'retention-cliff-drop'
  | 'credential-status';

type BackupActivityStatus =
  | 'success'
  | 'failed'
  | 'skipped'
  | 'partial'
  | 'cancelled';

type BackupActivityLevel =
  | 'info'
  | 'warning'
  | 'error';

interface BackupActivityEntry {
  readonly id: string;
  readonly operation: BackupActivityOperation;
  readonly status: BackupActivityStatus;
  readonly level: BackupActivityLevel;
  readonly startedAt: number;
  readonly finishedAt: number;
  readonly trigger?: RemoteBackupTrigger | null;
  readonly stage?: string | null;
  readonly reasonCode?: string | null;
  readonly errorCode?: string | null;
  readonly message?: string | null;
  readonly remoteFileName?: string | null;
  readonly localFileName?: string | null;
  readonly summary?: BackupActivitySummary | null;
  readonly metrics?: BackupActivityMetrics | null;
}
```

业务调用方不需要手写 `id`。`BackupActivityLogService` 在 append 前生成稳定 `id`，Rust append 命令再做兜底校验。

`id` 生成职责：

- TS 是主生成方。
- Rust 是防御性兜底方。
- Rust append 不覆盖 TS 已生成的非空 `id`。
- 未来如果按 `id` 定位、去重或关联 UI 项，持久化后的 `id` 必须与 TS 侧看到的 `id` 一致。

### 6.3 摘要字段

```ts
interface BackupActivitySummary {
  readonly noteCount?: number | null;
  readonly boardCount?: number | null;
  readonly textNoteCount?: number | null;
  readonly imageNoteCount?: number | null;
  readonly trashNoteCount?: number | null;
  readonly imageFileCount?: number | null;
  readonly imageFileTotalBytes?: number | null;
  readonly zipSizeBytes?: number | null;
}
```

`summary` 只记录统计信息，不记录正文、标题、看板名称和图片路径。

恢复场景的 `summary` 来源：

- 本地 zip 恢复与远端恢复成功时，优先复用恢复前 `validateLocalBackup()` 返回的 `BackupValidationResult.summary`。
- `RestoreResult` 只提供 `noteCount` / `boardCount` / `attachmentCount` 粗粒度计数，不能填满 `textNoteCount` / `imageNoteCount` / `trashNoteCount` / `imageFileTotalBytes`。
- 如果实现路径上拿不到验证阶段 summary，只能从 `RestoreResult` 填 `noteCount` / `boardCount` / `imageFileCount`，其余细分字段保持 `null`，不得为了日志临时扩展 Rust 恢复结果。

### 6.4 指标字段

```ts
interface BackupActivityMetrics {
  readonly retainedCount?: number | null;
  readonly deletedCount?: number | null;
  readonly missingCount?: number | null;
  readonly attemptedCount?: number | null;
  readonly failedFileName?: string | null;
  readonly anomalyCodes?: string[] | null;
}
```

`metrics` 用于远端保留清理、断崖保护等场景。

### 6.5 错误与消息

建议规则：

- `reasonCode` 存稳定分类，例如 `flush_failed`、`missing_credential`、`invalid_zip`。
- `errorCode` 存 WebDAV / 验证层已有 code，例如 HTTP `401` / `423` 或 `BackupValidationIssue.code`。
- `message` 存短的脱敏摘要，最长建议 `240` 字符。
- UI 文案不要只依赖 `message`，应优先根据结构化字段生成。

## 7. 脱敏规则

### 7.1 禁止进入日志的内容

不得记录：

- WebDAV 密码。
- 应用令牌。
- Authorization header。
- Basic / Bearer token。
- 带 userinfo 的 URL，例如 `https://user:pass@example.com`。
- WebDAV `serverUrl`。
- WebDAV `username`。
- 本地绝对路径。
- 下载 token。
- 便签正文。
- 便签标题。
- 看板名称。
- 图片文件原始路径或 hash stem 以外的业务路径。

### 7.2 字符串脱敏

TS 与 Rust 都要对 `message` / `reason` 类字段做防御性处理。

职责边界：

- TS 是业务语义层，尽量在组装活动时只传入结构化字段和已脱敏摘要。
- Rust 是持久化兜底层，防止绕过 TS 直接调用命令时写入敏感内容。
- Rust 规则可以比 TS 更保守、更粗暴；不要求两端逐字输出一致。
- 维护时以“不得写入敏感信息”为唯一一致性目标，不以两端替换文本完全相同为目标。

建议规则：

- 包含 `password` / `token` / `authorization` / `secret` 的字符串，替换为通用描述。
- 匹配 `Authorization: ...` 的内容，替换为 `Authorization: [REDACTED]`。
- 匹配 `Bearer ...` 或 `Basic ...` 的内容，替换为 `[REDACTED]`。
- 匹配带 userinfo 的 URL，移除 userinfo。
- 超长字符串裁剪到固定长度。

### 7.3 文件名归一

- `localFileName` 只能来自 basename。
- `remoteFileName` 只能存单个文件名，不存目录。
- 包含路径分隔符的文件名要降级为 `null` 或 basename。
- 保留策略失败文件名应沿用已校验的远端文件名。

## 8. 接入方案

### 8.1 本地 zip 备份

接入点：

- `BoardDock.tsx` 的 `onZipBackupClick()`

记录：

- 用户取消保存对话框：不记录。
- flush 失败：记录 `local-backup / failed / stage=flush`。
- `createLocalBackup()` 成功：记录 `local-backup / success`，带 `localFileName`、summary、zipSizeBytes。
- `createLocalBackup()` 返回失败或抛错：记录 `local-backup / failed`，带脱敏错误摘要。

注意：

- 不记录完整 `backupPath`。
- 不改变现有 `zipFeedback` 文案。

### 8.2 本地 zip 恢复

接入点：

- `BoardDock.tsx` 的 `onZipRestoreClick()`

记录：

- 用户取消打开对话框：不记录。
- 验证失败：记录 `local-restore / failed / stage=validation`，`errorCode` 取第一条 `BackupValidationIssue.code`。
- 验证通过但用户取消覆盖确认：记录 `local-restore / cancelled / stage=confirm`。
- flush 失败：记录 `local-restore / failed / stage=flush`。
- `restoreLocalBackup()` 返回失败：记录 `local-restore / failed / stage=restore`。
- 恢复成功并应用到内存：记录 `local-restore / success`，带计数摘要。
- 恢复成功但无法读取磁盘应用到内存：记录 `local-restore / partial`。

注意：

- 恢复日志不得包含源 zip 的完整路径。
- 验证错误只记录 code / target / 脱敏 message，不记录便签内容。
- 成功与 partial 场景的细分摘要优先来自本次恢复前已经验证通过的 `BackupValidationResult.summary`；不要依赖 `RestoreResult` 提供完整 `BackupSummary`。
- 如果验证 summary 不可用，只记录 `RestoreResult` 能提供的粗粒度计数，其余 `BackupActivitySummary` 字段保持 `null`。

### 8.3 手动远端备份

接入点：

- `BoardDock.tsx` 的 `onWebdavCreateBackup()`
- `RemoteBackupRunner.ts`

记录：

- 缺少配置 / 凭据：记录 `remote-backup / failed` 或 `credential-status / failed`。
- single-flight busy：记录 `remote-backup / skipped / reasonCode=single_flight`。
- flush 失败：记录 `remote-backup / failed / stage=flush`。
- 上传成功：记录 `remote-backup / success`，带 `remoteFileName`、summary、zipSizeBytes。
- 上传失败：记录 `remote-backup / failed`，带 `stage`、`errorCode`、脱敏 message。
- 上传成功后刷新列表失败：不把远端备份改成失败；可记录一条 `remote-list / failed / stage=list-refresh`。

### 8.4 远端列表刷新

接入点：

- `BoardDock.tsx` 的 `onWebdavListBackups()`

记录：

- 刷新成功：记录 `remote-list / success`，`metrics.retainedCount` 可存返回条目数量。
- 刷新失败：记录 `remote-list / failed`，带脱敏错误摘要。

注意：

- 列表中每个文件不单独生成日志。
- 不记录 WebDAV 服务器地址。

### 8.5 远端删除

接入点：

- `BoardDock.tsx` 的 `onWebdavDeleteBackup()`

记录：

- 用户取消确认：可记录 `remote-delete / cancelled`，但建议第一版不记录，避免噪音。
- single-flight busy：记录 `remote-delete / skipped / reasonCode=single_flight`。
- 删除成功：记录 `remote-delete / success`，带 `remoteFileName`。
- 删除失败：记录 `remote-delete / failed`，带 `remoteFileName` 与脱敏错误摘要。

### 8.6 远端恢复

接入点：

- `BoardDock.tsx` 的 `onWebdavRestore()`

记录：

- 用户取消初始下载确认：不记录。
- single-flight busy：记录 `remote-restore / skipped / reasonCode=single_flight`。
- 下载失败：记录 `remote-restore / failed / stage=download`。
- 下载 token 解析失败：记录 `remote-restore / failed / stage=resolve-download`。
- 验证失败：记录 `remote-restore / failed / stage=validation`，使用 `BackupValidationIssue.code`。
- 用户取消覆盖确认：记录 `remote-restore / cancelled / stage=confirm`。
- flush 失败：记录 `remote-restore / failed / stage=flush`。
- `restoreLocalBackup()` 失败：记录 `remote-restore / failed / stage=restore`。
- 恢复成功但无法应用到内存：记录 `remote-restore / partial`。
- 恢复成功：记录 `remote-restore / success`，带 `remoteFileName` 与计数摘要。

注意：

- 不记录 `downloadToken`。
- cleanupDownloadedBackup 失败只 `console.warn()`，不建议单独生成用户可见活动。
- 成功与 partial 场景的细分摘要优先复用下载后验证阶段的 `BackupValidationResult.summary`。
- 如果验证 summary 不可用，只记录 `RestoreResult` 能提供的粗粒度计数，其余 `BackupActivitySummary` 字段保持 `null`。

### 8.7 自动远端备份

接入点：

- `ScheduledRemoteBackupService.ts`

建议新增依赖：

```ts
appendActivity?: (entry: BackupActivityAppendInput) => Promise<void>;
```

记录：

- 缺少 WebDAV 配置：`scheduled-remote-backup / failed / stage=config`。
- 未保存凭据：`scheduled-remote-backup / failed / stage=credential`。
- 凭据失败次数过多：`scheduled-remote-backup / skipped / reasonCode=credential_action_required`。
- 无本地变更：`scheduled-remote-backup / skipped / reasonCode=no_local_changes`。
- flush 失败：`scheduled-remote-backup / failed / stage=flush`。
- 上传成功：`scheduled-remote-backup / success`，带 trigger、remoteFileName、summary、zipSizeBytes。
- 上传失败：`scheduled-remote-backup / failed`，带 trigger、stage、errorCode、脱敏 message。
- before-exit 路径也记录，但不得吞掉原本要抛给退出确认流程的错误。

注意：

- 活动日志写入要包在 `try/catch` 中，不影响 `saveScheduledState()`。
- 单测中可以注入 mock append，验证调用次数和关键字段。
- before-exit 失败路径必须显式验证：append 活动后，原始错误仍抛到 `handleQuitRequest()`，并继续进入备份失败确认对话框。
- append 失败也不得替换 before-exit 的原始备份错误；日志失败只能 `console.warn()`。

### 8.8 保留策略清理

接入点：

- 自动：`ScheduledRemoteBackupService.ts` 在 `orchestratePostBackupRetentionCleanup()` 返回 patch 后记录。
- 手动：`BoardDock.tsx` 的 `onExecuteCleanup()`。

记录：

- 首次建立健康基线并跳过清理：`retention-cleanup / skipped / reasonCode=baseline_initialized`。
- 保留策略未启用：不记录。
- retentionCount 为 null 或 <= 0：不记录。
- 清理成功：`retention-cleanup / success`，带 deletedCount / missingCount / retainedCount。
- 清理部分失败：`retention-cleanup / partial`，带 failedFileName / error。
- 清理执行抛错：`retention-cleanup / failed`。
- single-flight busy：`retention-cleanup / skipped / reasonCode=single_flight`。

注意：

- 清理失败仍不改变备份成功状态。
- 自动清理日志应附带原备份 `remoteFileName`，但不要把它显示成“备份失败”。

### 8.9 断崖式下降保护

接入点：

- `RetentionCleanupOrchestrator.ts` 返回包含 `cliffDropDetectedAt` / `cliffDropDeferred` / anomaly codes 的 patch 后。
- `BoardDock.tsx` 的 `onConfirmBaseline()` / `onDismissCliffWarning()` 可记录用户处理。

记录：

- 触发保护：`operation=retention-cliff-drop / status=skipped / level=warning`，带 anomalyCodes、可疑 remoteFileName、最新摘要。
- 用户确认新健康基线：`retention-cliff-drop / success / reasonCode=baseline_confirmed`。
- 用户只清除警告：`retention-cliff-drop / skipped / reasonCode=warning_dismissed`。

注意：

- 触发保护不是错误，而是保护机制生效；UI level 用 `warning`。

### 8.10 凭据与密钥链状态

接入点：

- `BoardDock.tsx` 的 WebDAV 保存 / 清除配置反馈。
- `ScheduledRemoteBackupService.ts` 的 credential 失败分支。
- `WebDavBackupService.createRemoteBackup()` catch 分支。

记录：

- 未保存凭据导致自动备份不可用。
- 凭据读取失败或 keychain 不可用导致会话模式降级。
- 清除 WebDAV 配置时 secret cleanup warning。

注意：

- 只记录分类与脱敏摘要。
- 不记录 serverUrl、username、credential key。

## 9. UI 方案

### 9.1 展示位置

建议放在 WebDAV 设置区的状态区域下方，保留策略区域上方或下方均可。

理由：

- 活动主要围绕备份 / 恢复 / WebDAV。
- 用户打开 WebDAV 设置时最需要排查自动备份状态。
- 不新增顶层导航和复杂设置页。

### 9.2 展示内容

最近 10 条活动，每条建议展示：

- 图标：成功、失败、警告、跳过。
- 时间：`MM-DD HH:mm`。
- 操作：本地备份 / 本地恢复 / 远端备份 / 自动备份 / 远端恢复 / 清理。
- 结果：成功 / 失败 / 跳过 / 部分完成 / 已取消。
- 文件名：可选，单行截断。
- 错误摘要：失败时显示短文案。

不要展示：

- 服务地址。
- 用户名。
- 本地完整路径。
- 原始堆栈。
- 长错误全文。

### 9.3 交互

- 打开 WebDAV 设置时加载最近活动。
- 操作完成后刷新最近活动。
- 设置区打开时可以每 `5s` 随定时备份状态轮询一次活动日志，避免自动备份在后台完成后 UI 不更新。
- 活动日志轮询应复用既有定时备份状态轮询节奏，不新增第二个高频定时器。
- 轮询结果与当前 entries 无变化时不要 `setState`，避免 WebDAV 设置区打开时产生无意义重渲染。
- 提供“清空活动”按钮，点击前确认。
- 清空只清活动日志，不清定时备份状态、健康基线、WebDAV 配置。

### 9.4 空状态和错误状态

- 无活动：显示“暂无备份活动”。
- 加载失败：显示“活动日志加载失败”，保留重试按钮。
- 清空失败：显示脱敏错误。

## 12. 风险与防护

### 12.1 日志泄漏敏感信息

这是本版本最大风险。

防护：

- TS / Rust 双层脱敏。
- 不存 serverUrl、username、password、token、downloadToken。
- 文件名只取 basename。
- message 裁剪。
- 增加敏感字段搜索与单测。

### 12.2 日志写入影响备份流程

日志是辅助能力，不应改变主流程。

防护：

- append 调用包 `try/catch`。
- append 失败只降级提示或 `console.warn()`。
- 不在 Rust 备份 / 恢复核心函数内部强制写活动日志。

### 12.3 最近状态与活动日志不一致

例如备份成功，状态保存成功，但日志写入失败。

防护：

- 接受“状态权威、日志辅助”的关系。
- UI 不用活动日志推导调度状态。
- 文档明确日志不是审计系统。

### 12.4 BoardDock 继续变重

`BoardDock.tsx` 已经承载大量数据管理逻辑。

防护：

- 复杂逻辑放进 `BackupActivityLogService`。
- UI 展示可拆小组件，例如 `BackupActivityList`。
- 本版本不做大规模 store 迁移，避免和可观测性目标互相拖累。

### 12.5 自动备份日志过多

频繁跳过或列表刷新可能刷掉有用记录。

防护：

- 只记录实际 attempt 的 skipped，不记录 quiet-period 延迟。
- 保留 100 条，UI 只展示 10 条。
- 未来如仍过多，再加 operation 级过滤，不在本版实现复杂查询。

## 13. 与后续版本的关系

`v1.5.8` 完成后，备份链路应具备基本可观测性。

这会给后续版本铺路：

- `v1.5.9` 可以基于活动日志做关键流程冒烟检查和体验基线收口。
- `v1.6.0` 如果选择快速捕获、搜索或图片体验作为主线，也不会继续被备份链路的排障问题拖住。
- 后续如果要继续清理 `BoardDock` 或迁移 `useStore` 旧入口，可以以活动日志服务边界为基础，但不需要在 `v1.5.8` 一次做完。

`v1.5.8` 的结束状态应是：**用户能看懂最近备份链路发生了什么，开发者能从本地日志定位失败阶段，同时应用没有新增任何远端日志或敏感信息泄漏面。**
